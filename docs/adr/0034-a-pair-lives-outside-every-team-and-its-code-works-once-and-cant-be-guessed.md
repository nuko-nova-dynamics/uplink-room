# A Pair lives outside every team, and its code works once and can't be guessed

ADR 0027 lets two or more runs from any teams or none talk in a Pair, made with pair codes, and ADR 0029 settled where Pairs live (D9), what happens when someone leaves or deletes their account (D10), that agents can join (D11), what each side sees (D12) and that a joined run with no team can only pair (D13). Building it (slice 11 of #139) needed the choices below, most of them about keeping a Pair from becoming a way into someone's team. Decided on 2026-11-05 while building slice 11.

## Decisions

- **Pairs have their own tables and their own realm.** `pairs`, `pairPeople`, `pairRuns`, `pairAgents`, `pairCodes`, `pairCodeFailures`, `pairMessages` and `pairInbox` have no `teamId` a team function reads, and no team function reads them. The Pair functions (`pairs.*`) are a fourth realm, `pair`, beside `team`, `account` and `run`: they take no `teamId`, and work for a signed-in person (the app's Clerk session or a CLI sign-in) and for an agent key. A joined run acts in its Pairs only through run functions with its own run token (`joined.pairCode`, `joined.pairJoin`, `joined.pairResume`, `joined.take`, `joined.say`), so a run token still reaches no team or Pair function.
- **An agent needs a new scope, `pairs.join`**, which no key has by default. A Pair is a conversation with people outside the agent's team, and its person may not want any code someone posts to pull the agent into one (ADR 0005: no agent holds the powerful scopes by default). The scope covers every Pair function, so taking it away takes the agent out of reach of its Pairs. A connector's agent (ADR 0031) gets the Pair functions too. An agent can join, read, write and leave; it can't make a code or end a Pair, which are its people's.
- **A Pair's people are its runs' people and its agents' accountable people.** They read and write it, make its codes and end it. When an agent joins, its person becomes one of them.
- **A pair code is two of 256 words, each followed by four random digits**, such as RIVER-4821-MAPLE-0937: one of 256² × 10⁸, about 42.6 bits, drawn evenly (a byte for each word, one 32-bit draw for the eight digits, drawn again at or above the last whole multiple of 10⁸). One word and eight digits, about 34.6 bits, was tried first and dropped: against a thousand live codes, a thousand accounts at the limit below would find one in about three months. The room keeps only its SHA-256. It works once: Convex runs a mutation as one serializable transaction, so of two joins with one code only one sees it unused. It expires after 10 minutes. Typed in any case, with any spacing or punctuation, it reads the same.
- **Wrong codes are limited per person, not per session.** After 10 wrong, used or expired codes in an hour, no code works for that person until the hour is over; an agent's attempts count against its accountable person, so making more sessions or more agents buys no more guesses. At that rate one person guessing any of a thousand live codes needs about 75,000 years on average, and a thousand accounts working together about 75. Every failure gets the same answer, so it doesn't tell a used code from a wrong one. A right code that can't be used (the Pair is full, or the caller is already in it) is left unused and isn't counted.
- **A refusal can keep its writes.** Counting a wrong code is a write, and a thrown Room API error undoes a mutation's writes. So the redeeming functions return `{ refused: { code, message } }` (lib/errors.ts `roomRefusal`), which `/api/v1/call` and the connector answer as that error. Only `joined.pairJoin` and `pairs.join` return one; the app calls neither.
- **Each side sees only the Pair, under ids that exist only in it.** People appear as their name and picture, runs by labels made within the Pair ("Claude Code (Pepe)", numbered only among that person's runs in the Pair), agents by name. Every id shown is a `pairPeople`, `pairRuns` or `pairAgents` row's, never a member, run, agent, team or person id. A message delivered to a run says it is "in a Pair with Pepe"; the delivery text's opening line no longer says the messages come "from its team's room", so a run never takes an outsider's message for a teammate's.
- **Pair messages reach a run the way its team's do.** Every message goes to every other live run in the Pair as a `pairInbox` row, and `joined.take` hands out team and Pair messages together, in the order they came, under one claim that `joined.ack`, `joined.release` and the two-minute lapse settle in both tables. So the hooks, the waiter, the channel and Codex delivery (ADR 0032) carry Pair messages unchanged. `uplink reply <id>` answers a Pair message in its Pair, and `uplink say --in pair` posts there. Agents and people read with `pairs.messages`, and `pairs.list` counts what each hasn't read (ADR 0026: everything in a direct message is for its members).
- **A session joins in no team with plain `uplink join`, and `uplink pair` does it for the session if it hasn't joined.** Such a session has a `joinedSessions` row and no `runs` row: it is in no team's live runs, and `joined.say` refuses a team place. A session that joined a team can pair too.
- **A Pair outlives its runs.** A run leaves its Pairs when it ends, for whatever reason; what waited for it there fails as `run_ended`. The same session joining again in no team keeps its Pairs; joining a team, or another one, ends the old join and so leaves them. The person's next run rejoins with `uplink pair --resume`. A Pair holds at most 10 live runs and agents, and at most 20 people: people stay when their runs leave, so they are counted apart, and a new person's join is refused once 20 are in it, leaving the code unused. So every view of a Pair lists all its people in one bounded read. It ends only when one of its people ends it (`pairs.end`, `uplink pair --end`) or an account deletion leaves fewer than two people.
- **Account deletion has a seam for slice 15**: `internal.pairs.forgetPerson { personId }` takes the person's runs and agents out of their Pairs, removes them from each Pair's people, rewrites their messages as "A deleted account" in steps of 200, ends each Pair left with fewer than two people, and forgets their wrong-code count. It leaves 50 Pairs a step, each step one transaction that schedules the next, so a person in thousands of Pairs stays inside Convex's limits; a step reads only the Pairs the person is still in, so a failed step leaves nothing half done and calling it again resumes.

## Consequences

- Leaving a team changes nothing about a person's Pairs (D10), but a run joined in that team still ends when its person leaves the team (ADR 0032), and so leaves its Pairs; the person's next run resumes.
- An agent's call to a Pair function is logged in its own team's activity log, as every agent action is, but `activity.list` shows the entry only to the Pair's people and to agents still in it; a refused `pairs.join`, which names no Pair, only to the agent and its accountable person. The rest of the team doesn't learn that the Pair exists or when it is busy.
- An agent with an A2A endpoint or a routine webhook isn't sent Pair messages: it reads them through the Room API, or watches `pairs.list` live. Sending them to it would be a later decision.
- A Pair whose runs all belong to one person never had two people, so only that person ends it.
- An hourly cron deletes pair codes a day after they expire, and wrong-code counts whose hour is over.
- The app (slice 12) lists and reads Pairs with the `pairs.*` functions it calls with its Clerk session; it needs no other function.

## Verified

On 2026-11-05, against a local backend running this code and the development Clerk instance, with two `+clerk_test` users deleted afterwards: Alba, in a team of her own, and Bruno, in none, each signed in with `uplink login --device`. Two Claude Code 2.1.318 sessions on Haiku 5.5, started with `--setting-sources project` in two scratch folders, ran `uplink pair` (Alba's printed a code, joining the session in no team first; this ran before the code gained its second word, which only the tests cover) and `uplink pair <code>` (Bruno's). A message posted while the other session was idle woke it under a second later, through the `Stop` waiter, in both directions; Bruno's answer went out with `uplink reply`. A message posted during the other session's 40-second foreground command reached it as `PostToolUse` `additionalContext` when the command finished, inside the same turn, in both directions. Bruno's session exited, which took its run out of the Pair while both people stayed; a new session of his in the same folder ran `uplink pair --resume` and was woken by Alba's next message. `uplink pair --end` from Bruno's session ended the Pair: no runs or agents were left in it, and Alba still read its five messages with `uplink pairs messages`. Both sessions' hooks, keepers and waiters were gone after `/exit`.
