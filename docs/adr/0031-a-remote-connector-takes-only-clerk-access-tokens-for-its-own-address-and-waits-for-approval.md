# A remote connector takes only Clerk access tokens issued for its own address, and waits for its person's approval

ADR 0028 has hosted assistants (Grok Bot, ChatGPT dots, Meta Muse, Claude Duet) join through a remote MCP connector that a person adds in the assistant's settings and signs in to. This is how slice 13 of #139 builds it, under decisions D14, D15 and D16 of ADR 0029. Decided on 2026-11-05 while building it.

## Decisions

- **The connector is `<CONVEX_SITE_URL>/mcp`**, an HTTP action in Convex's default runtime. It speaks MCP's Streamable HTTP transport: POST only, a plain JSON answer to every request, no sessions and no SSE stream; GET and DELETE get 405 once authorized. It serves both protocol eras with the official MCP TypeScript SDK (`@modelcontextprotocol/server` 2.4.0): revision 2026-07-28 (per-request metadata, `server/discover`) through `createMcpHandler`, and the 2025 revisions (`initialize`) through its web-standard transport, stateless, with JSON responses, so every tool call finishes before the action returns. A request carrying an `Origin` header is refused with 403: the transport page says servers must check it, hosted assistants call from their servers, and no web page is meant to call this endpoint. Its body is read as a stream after the token is checked, up to 1 MiB and for at most 10 seconds (413 and 408 past them, and a declared `Content-Length` over 1 MiB is refused before reading): Convex puts no limit on a request's size and gives an HTTP action 64 MiB of memory. The room's other routes that read a body from outside read it the same way (`lib/requestBody.ts`), each with its own cap.
- **Discovery follows the MCP specification's authorization page (revision 2026-07-28).** `GET /.well-known/oauth-protected-resource/mcp` is the protected resource metadata (RFC 9728): `resource` is the endpoint's URL, `authorization_servers` is the first Clerk instance in `CLERK_JWT_ISSUER_DOMAIN` (as `uplink login` uses, ADR 0030), `scopes_supported` is `openid`. It is served only at that path, because RFC 9728 section 3.3 requires `resource` to equal the identifier the well-known URL was built from. A call without a token gets 401 with `WWW-Authenticate: Bearer resource_metadata="…", scope="openid"`.
- **The room takes only a JWT access token Clerk issued for exactly this endpoint, to a client other than the command line.** Clerk issues JWT access tokens with `typ: at+jwt` and, with the `aud` claim turned on, sets `aud` to the RFC 8707 `resource` the client asked for (Clerk's Backend API describes `aud_claim_enabled` as "Whether OAuth access tokens can include an aud claim derived from the RFC 8707 resource parameter"). On every call the room checks, with Web Crypto (`verifyAccessToken` in `lib/clerkTokens.ts`), RFC 9068's rules: `typ` is `at+jwt`, `iss` is exactly the issuer, RS256 by a key in its JWKS, `aud` is exactly this endpoint, not expired; then that `client_id` is present and isn't `CLERK_CLI_CLIENT_ID`. It takes a single audience only: a token valid at several resources can be replayed by any of them (RFC 8707, section 3). The `typ` check refuses Clerk's ID tokens and session tokens; anything that isn't a JWT, such as an agent key or a CLI sign-in's token, is refused before any of it. A failure is 401 with `error="invalid_token"` and the reason. Opaque access tokens are refused: checking one needs the instance's secret key and a call to Clerk, and the room couldn't see the audience itself.
- **D16 as built:** the token is checked on every call and never passed on or swapped for a token of the room's. A checked token is remembered by its SHA-256 until it expires, in the isolate's memory, so a miss only checks again. Clerk's keys (its JWKS) are cached per issuer in the same memory, shared with the command line's ID-token check: for 5 minutes, Clerk's own verifier's TTL; a `kid` the cached keys lack fetches again at most every 10 seconds, so a rotated key works within that time and tokens with made-up `kid`s can't make the room fetch on every call; callers waiting for the keys share one fetch, and a fetch gives up after 5 seconds. The check runs in the HTTP action, not in a Node action as D16 said: nothing in it needs Node (the ID-token check from ADR 0030 runs the same way).
- **A connection is one person and one OAuth client** (the token's `sub` and `client_id`), a row in `connectors`. A token from another client is another connection, waiting for its own approval, so a token issued to another client never reaches an approved connection's agent. One person can have at most 10 connections waiting; a waiting connection that hasn't called for 30 days is deleted.
- **Until its person approves it, every tool answers that it is waiting**, and the instructions start by saying so (D15). The person approves it in the app (Settings, Agents) with `connectors.approve`, a team function only a person can call, choosing the team, the agent's name and its scopes, which start at `room.read` and `messages.post` (D14). Approving adds an agent (connection `mcp`) and an `agentKeys` row whose secret is random and shown to nobody; each tool call then runs the Room API function's agent path with that key's hash, as `/api/v1/call` does with an agent key. So the agent's role, scopes, record of actions and revoking work as for every agent (ADR 0003, ADR 0005). Revoking the key, removing the agent, or its person leaving the team ends the connection; `connectors.remove` declines a waiting one or disconnects an approved one (its key is revoked), and the client's next call asks again.
- **The connector lists the team functions, named and described as `uplink-mcp` names them.** The tool catalog and the instructions live in `@uplink-room/protocol/mcp` and both servers use them. Account functions (ADR 0030) and `uplink-mcp`'s local tools (upload a file, run in a terminal) aren't listed.

## Consequences

- A deployment's Clerk instance needs, under OAuth applications, Settings: **JWT access tokens** (`oauth_jwt_access_tokens`) and the **`aud` claim** (`aud_claim_enabled`) on; **Publish CIMD support** on, for clients that identify themselves with a metadata URL; and **Publish DCR support** for hosts that register dynamically, which Clerk warns opens an unauthenticated registration endpoint. Default scopes for dynamic clients: `openid`. Both instances have them on since 2026-11-05, and DEV and production run the connector since 2026-11-06. Without them every token is refused (opaque, or with no `aud`), and the connector does nothing.
- Turning on JWT access tokens changes the instance's tokens for every OAuth application. The command line (ADR 0030) uses only Clerk's ID token, and revokes the access token it never uses; a JWT access token can't be revoked (Clerk answers 400), which the command line already ignores.
- A JWT access token works at the room until it expires (Clerk: one day), even after the person revokes the connector in Clerk. The room's own revoking (the key, or `connectors.remove`) stops it at the next call.
- The connector lists every team function, about 240 tools. A host that limits how many tools a connector has would need a shorter list.
- Grok Bot's webhook and "checks in on its own schedule" are slice 14.

## Verified

On 2026-11-05, against a local backend running this code (before its rebase onto the merged ADR 0030 work, which changed only sign-in internals) and the development Clerk instance, with JWT access tokens, the `aud` claim and DCR turned on for the check and off again afterwards, a `+clerk_test` user, and two OAuth clients made for the check, all deleted afterwards:

- The official SDK's 2025-era client (`@modelcontextprotocol/sdk` 1.32.2), pre-registered, and its 2026-07-28 client (`@modelcontextprotocol/client` 2.4.0, pinned to 2026-07-28), registered through DCR, each found the metadata from the 401, signed in through Clerk's consent screen, sent `resource=http://127.0.0.1:3213/mcp`, and got an access token with `typ: at+jwt`, `aud: "http://127.0.0.1:3213/mcp"` and its own `client_id`. Each was told it was waiting; after `connectors.approve`, each posted in #general as its agent, and `tasks.create` was refused for lacking `work.manage`. Revoking the first one's key ended it on its next call.
- Refused with 401 and the reason: an access token the command line's client got with `resource` set to the endpoint (Clerk issues one; its consent screen names "Uplink Room command line"), the command line's ID token (`typ: JWT`), a connector client's token with no `resource` (no `aud`), and a CLI sign-in token's shape.
- With the `aud` claim setting on, a token asked for without `resource` carries no `aud`, so the room refuses it.
