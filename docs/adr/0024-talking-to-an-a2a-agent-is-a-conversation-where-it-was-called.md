# Talking to an A2A agent is a conversation where it was called

On 2026-11-04 Julio sent Icarus, a Hermes Agent the team reaches over A2A 1.0, a test task, then "@Icarus hey there" in #general. Icarus answered both times ("Hi Julio. Icarus here. Your test message came through."), but the answer showed only in the run panel, and the channel showed only a chip under his message. He had no way to answer back. In his words: "shouldn't this be like a chat or a session? … how do I speak to it? there's no way to reply back", and for the channel, "if called here it should answer". His design: agents "should just answer like any other bot … they reply on the thread and they have the whole thread or channel like a thing … just like Grok works."

What the room did (ADR 0012): every message to an agent started a run of its own, with a context of its own, so the agent forgot the last exchange. The worker never posted in chat. A reply needed the run to still be followed, so once the agent reported a finished task the reply box went away.

## Decisions

**A place is one conversation with an agent.** A channel's top level, a thread, and a direct message are each one conversation per agent; a run on a task, or one started through the Room API (`runs.start`), has its own. `a2aConversations` keeps the agent's A2A context for it, the endpoint generation that context is from, the agent's last task, the open run, and the newest message the agent was sent.

**Each message continues the conversation, as A2A 1.0 describes** (spec 3.4.3, "Multi-Turn Conversation Patterns", read at tag v1.0.0, 2026-11-04):

- While the agent's task is open (Submitted, Working, Input required, Auth required), a message goes to that task: "Clients MAY use `taskId` (with or without `contextId`) to continue or refine a specific task", and for Input required, "The client continues the interaction by sending a new message with the same `taskId` and `contextId`".
- Once the task is finished, a message starts a new task in the same context, with `referenceTaskIds` naming the last one: "Clients MAY use `contextId` without `taskId` to start a new task within an existing conversation context" and "Clients SHOULD use the `referenceTaskIds` field in Message to explicitly reference related tasks". A finished task can't take more ("UnsupportedOperationError: Messages sent to Tasks that are in a terminal state … cannot accept further messages", spec 3.1.1; in 0.3, "A task which has reached a terminal state … can't be restarted. Sending a message to such a task will result in an error"). Each new task is a run of its own, so runs stay the unit of tracking: the Inbox, run states, stop, the task board and the agent's tools are unchanged.
- The room never makes up a context. "Clients SHOULD NOT provide a client-generated `contextId` to a server unless they understand how the server will process that `contextId`" (spec 3.4.1), so the first message goes without one and the room keeps the one the agent answers in.

**Agents that don't keep context, or refuse it, still get the conversation.**

- "Agents MAY accept and preserve client-provided `contextId` values" (3.4.1), so some don't. When the agent answers in another context than the one the room sent, the room follows the agent's and marks the conversation as one whose agent doesn't keep context.
- "If an agent cannot accept a client-provided `contextId`, it MUST reject the request with an error" (3.4.1). A first message refused with a JSON-RPC error while it carried the conversation's context goes once more without it, with the same message id: refused, it took nothing, so it can't arrive twice.
- Hermes's gateway rejects a context after 5 messages in an hour by default ("Anti-loop protection: context … exceeded 5 turns. Start a new context or increase A2A_MAX_PINGPONG_TURNS.", `A2A_MAX_PINGPONG_TURNS`, at most 20, in `plugins/platforms/a2a/protocol.py` and `adapter.py` of NousResearch/hermes-agent, read 2026-11-04). A person chats past that within minutes. When a first task sent in a reused context is rejected before it worked, with words about the context ("context" and one of turns, exceeded, expired, limit, unknown, not found, invalid), the room starts a fresh context once: the same run, the message again under a new id, and no failure in chat. Any other rejection stands.
- Hermes gives every message a task of its own, ignoring the task id sent (`task_id = protocol.new_task_id()` in `_prepare_task`). When a message the room sent to an open task is answered with another task in the same context, that task becomes the conversation's next run, on the same room task as the run before. The message isn't sent again. That run keeps the context the message went in as the one it sent, so a new task rejected over that context (the turn limit) goes once more in a fresh context, as a first message does. When the answer to such a message is lost, the room looks for it among the context's tasks (`ListTasks` with `contextId`) before it calls it lost, and follows the task it is in.

**A message goes to the agent's current endpoint.** A run whose task is open at an address the agent no longer has isn't followed any more, so a message sent while it is open starts a new task at the current address instead of waiting on it.

**Each message carries what was said in the place since the agent last heard from it.** At most 20 messages and 4,000 characters, each cut to 1,000, with author names and times, oldest first, the agent's own marked "(you)". Until the agent has answered in a context the room sent, the room can't count on it keeping one, so history is the place's recent messages, the agent's own included; after that, only what came since the agent was last sent a message, without its own. It comes only from the place itself, which the agent must be able to see (ADR 0016), and credential headers and bearer tokens in what others wrote are taken out (`PLAIN_REDACTOR`, ADR 0018): a quoted header value up to its closing quote, and a Cookie or Set-Cookie value with every pair in it: the sender chose to send their own message, not what others pasted.

The history is a second text part after the message, headed "Earlier in #general, since you last heard from it (oldest first, times in UTC):", and is in the metadata too (`uplinkRoom.history`). The message comes first so an agent that reads only the first text part still gets the ask; Hermes joins every text part with a newline (`extract_text` in `protocol.py`), so its model reads both; an agent that reads data reads the metadata. Data parts were not used for it: Hermes renders a data part into its model's prompt as raw JSON, and an agent can refuse a media type it doesn't take ("ContentTypeNotSupportedError", spec 3.1.1).

**The agent answers where it was called, as a member.** At a channel's top level its answer is a plain message in the channel, under the question; in a thread, a reply in the thread; in a direct message, a message in it. These are messages from the agent's member, which name their run (`a2a.runId`), and the app shows that run as a small "Run details" chip on them instead of on the question. ADR 0012 said "the worker never posts in a channel on the agent's behalf"; in a conversation it now does, in the mutation that saves what the agent reported, so each is posted once:

- the answer: a direct message reply (with the files it sent as bytes attached, or only those), or a finished task's last status message and its artifacts' text, each said once (Hermes sends the same text as both), then the artifacts' links. File parts with bytes (at most 4, from answers read with a 512 KB limit) become attachments under the attachment rules; a file the agent only links to stays a link, as the room sends requests only to the agent's own origin (ADR 0012);
- a question (Input required) as the agent's message, which the person answers in chat;
- progress: only a status message with text, never a bare state, at most 10 per run, after which the last one is edited;
- what the agent didn't say itself: a failure or a rejection ("Icarus couldn't finish: …", "Icarus declined: …"), a sign-in it needs, a message it refused, one that may not have arrived, or the room no longer following the run, as a short centered line with a link to the run.

A chat run whose answer was posted where it was asked settles itself, a rule in the glossary's sense of Settle: the person reads the answer in chat, so it doesn't also wait in their Inbox's Done. A run on a task is the task's to settle, and a failure or a question stays in the Inbox.

While the run works, the agent shows as writing in the place (`channels.whoIsTyping` lists it with `working: true` for as long as it works). The room never sends one agent's answer to another agent, so agents in one place can't loop. Amended by ADR 0026: agents and live runs may message each other, with no loop limit.

A run on a task has its conversation in the task panel. Amended by ADR 0041: there the runs of one conversation show as one chat with one message box, not a card per run.

**Which messages reach the agent.** In a direct message, every message reaches every agent in it. At a channel's top level, a message reaches the agents it mentions. In a thread, a reply reaches the agents it mentions and the agents whose own thread it is: one that hangs off the agent's message, or one the agent opened. Anyone who may send the agent work (ADR 0012) continues its conversation from chat; `runs.reply` keeps its own rule (the run's driver, whoever started it, the task's owner or an admin), and on a run from chat it posts the reply in the place as the sender's message, so the conversation reads whole there; since that is a chat message, an agent key then needs `messages.post` as well as `runs.start`. After the run finished, `runs.reply` continues the conversation as a new run and returns its id.

**An agent can propose a thread of its own.** Sometimes a quick answer belongs inline, sometimes the work needs its own thread. An agent asks with any of:

- a data part `{ "kind": "uplink.room/propose-thread", "title": "…" }` (`{ "data": {…} }` in 1.0, `{ "kind": "data", "data": {…} }` in 0.3) in its message or status message;
- the message metadata key `uplink.room/propose-thread`, holding `{ "title": "…" }`;
- for an agent that answers only text, its answer's first line `uplink.room/propose-thread: <title>`, which the room takes out of the text.

The room shows the agent's message ("This looks like it should be its own thread. Want me to open it?" when it said nothing else) with Yes and No for whoever wrote the message that started the work, the run's driver or starter, or an admin, and the seconds left: nobody answering in 30 seconds counts as Yes (`messages.answerProposal`). Yes moves the conversation, context and all, into the thread under the message that started the work, and every reply in that thread reaches the agent; No keeps it where it is. Either way the agent is told as the conversation's next message ("Yes, open a thread for this. …", "No, answer here in #general.") with `uplink.room/thread-decision: { "open": …, "byTimeout": … }` in its metadata. An answer is A2A work, so `messages.answerProposal` takes what `runs.reply` takes: an agent key needs `runs.start`, and the agent must take work from whoever answers. One proposal waits at a time, only at a channel's or direct message's top level.

A proposal can also end with no thread and nobody's Yes or No: canceled, with the reason where it shows. Stopping its run, or the room no longer following it, cancels it, and the agent is told nothing more, since a Yes after the wait would only start the conversation again. For the same reason, once someone has asked to stop a run, a proposal it makes after that isn't shown. Deleting the proposal, or the message its thread would open under, cancels it too, and the agent is told as for a No (`open: false`), with why in the text, so a task that waits on the answer goes on. A Yes that comes after that message is gone is the same cancel. Every message that starts a task in such a place says the room offers it, in its metadata (`uplink.room/capabilities: ["propose-thread"]`), and, for an agent not known to keep context, in one line of its text, since an LLM agent such as Hermes's reads text, not metadata.

## Consequences

- Delivery stays as ADR 0012 and ADR 0018 set it: every message keeps its id, and one whose answer was lost is looked for before anything is sent again. A message goes a second time only after a clear refusal: refused for its context (the same id) or refused because its task had ended (`UnsupportedOperationError` or `TaskNotFoundError`; the 0.3 SDK answers `invalidRequest` saying "terminal state"; a new id, since it becomes a new task). A message sent while the agent's task is open goes to that task once; one sent before the agent had a task waits for it, and goes on to the next task if that one ends first. Once someone has asked to stop the run, messages that wait for it aren't sent at all, and a line in chat says so. At most 5 messages wait for one task; past that the room says so in chat and sends nothing.
- Writes stay bounded: posting happens only in the mutations that save what the agent reported, a step's cadence bounds those, progress posts stop at 10 per run, a run keeps at most 20 fingerprints of what it posted, and history is read with bounded queries.
- Everything an agent wrote is cleaned before it is saved, as before (redact.ts): the answer posted in chat is the text the run keeps, and a line is cut after cleaning.
- The schema change is additive: `a2aConversations`; optional `conversationId`, `triggerMessageId`, `sentContextId`, `previousTaskId`, `contextRetried`, `chat` and `files` on `a2aBindings` (a file also takes an optional `taskId`, the task it came in), and `history`, `chatMessageId` and `decision` on its outbox entries; optional `a2a` and `a2aRuns` on `messages` (a proposal's status also takes `canceled`, with an optional `reason`), whose `system` also takes a `run` line; optional `runId` on `typing`. A run from before has no conversation: replying to it after it finished gives it one, from its own context.
- `runs.reply` returns `{ runId }` instead of null, and no longer refuses a finished run.
- The tests' fake agents (`tests/a2a/fakeAgent.ts`) remember what they heard per context, answer as Hermes does in chat mode, refuse a context past a turn limit, can ignore or refuse the context or task id the room sends, propose threads in all three forms, send a file as bytes, answer a send only once its task has finished, and confirm a cancel a moment after taking it.
- Decided from Julio's three steers on 2026-11-04, without a meeting; the PR that brings this ADR is where to object.
