# A deleted Clerk account leaves its Pairs, sessions and teams, through Clerk's signed webhook

ADR 0029's D10 says what deleting an account does to a Pair: the person's runs leave, their messages stay under "A deleted account", and a Pair left with fewer than two people ends. Until now nothing in the room learned that an account was deleted: `people` had no deletion path, and the only deletion code was `internal.pairs.forgetPerson`, left for this slice by ADR 0034. Decided on 2026-11-05 while building slice 15 of #139. Julio decided what a deleted person's team messages show, who becomes a team's admin, and what removing a member does to their machines later the same day; all three are recorded below.

## Decisions

- **Clerk's `user.deleted` webhook is the trigger.** Clerk sends it when a person deletes their account, or when someone deletes it in the Clerk Dashboard or Backend API ("Sync Clerk data to your app with webhooks"). The room takes it at `POST /clerk/webhook`, a Convex HTTP action. Every other event type is answered 200 and ignored, after the same checks.
- **Each delivery is checked against Svix's documented scheme, by hand, on Web Crypto.** Clerk sends its webhooks through Svix ("Webhooks overview"). The route needs `svix-id`, `svix-timestamp` and `svix-signature`; refuses a timestamp more than five minutes from the room's clock, either way, as Svix's libraries do ("Why Verify Webhooks"); and accepts the delivery only when one `v1,` signature in the header equals the base64 HMAC-SHA256 of `<svix-id>.<svix-timestamp>.<raw body>`, keyed with the base64 part of the signing secret and compared in constant time ("Verifying Webhooks Manually"). The body is read with `lib/requestBody.ts` under a 1 MiB cap before anything else. Not a library: `svix` 2.9.1 and `@clerk/backend` 3.27.0 (the registry's current versions on 2026-11-05) both verify through `standardwebhooks` 1.1.1, and the scheme is a few lines on Web Crypto, the way the room already checks GitHub's webhook signature (`lib/github/crypto.ts`). A test reproduces Svix's published example signature, so the hand-written check is held to Svix's own vector.
- **The signing secret is `CLERK_WEBHOOK_SIGNING_SECRET`**, Clerk's own name for it. It may hold several secrets separated by commas, as `CLERK_JWT_ISSUER_DOMAIN` lists issuers (ADR 0014), because each Clerk instance's endpoint has its own secret and production accepts both instances during ADR 0014's switch. Without it the route answers 503 `not_configured`, and Svix retries.
- **A delivery is applied once.** Svix sends every attempt at one message with the same `svix-id`, and Clerk's guide says to store it and skip a repeat ("Handle out-of-order and duplicate events"). The room records it in `clerkDeliveries` in the same transaction as the deletion, so a delivery that fails isn't recorded and Svix's retry applies it. Ids are kept 7 days, far past Svix's retries. A later delivery for an account already deleted, or the same message replayed after its id is gone, changes nothing either, because the deletion is already recorded; it only starts the cleanup again if that stopped (below).
- **The webhook's own transaction is small, whatever the person has.** `accounts.deleteFromClerk` records the deletion in `accountDeletions` by Clerk user ID, marks the person deleted and schedules the cleanup, and reads and writes nothing else. A deletion that touched every sign-in, run and team in one transaction could pass Convex's limits (4,096 index ranges, 32,000 documents scanned, 16,000 writes a transaction), roll back, and fail the same way on every retry.
- **The person's row stays, marked deleted and emptied.** `people.deletedAt` is set, the name becomes "A deleted account", and the email and picture are erased. The row is kept by its Clerk user ID, so what points at the person still finds a row, and no Clerk token issued before the deletion signs them in again: an app session token issued before the deletion gets `unauthenticated`, and so does an ID token from `uplink login`. Clerk's guide recommends this kind of soft delete so late events can't undo a deletion.
- **The deletion is recorded by Clerk user ID even for an account the room never saw**, and kept for good. `uplink login` gets Clerk's ID token before it hands it to the room, so a deletion can land in between, before the room has a person for the account. `recordPerson`, which both `people.ensure` and the CLI token exchange go through, refuses a recorded account, so neither makes a person or a 30-day sign-in for it.
- **Nothing acts as the person from the moment the deletion lands**, before the cleanup below has run: a CLI sign-in (`liveCliSignIn`), a run token (`joinedRunForToken`), an agent they're accountable for, a personal machine's bridge token (`bridge.ts`), and a shared browser's ticket they got before the deletion (`browsers.admit`) all check `deletedAt`. An agent is refused wherever agents act or are reached: its key over HTTP, live queries and MCP (`agentActorForKey`), the remote connector (it shows as ended), routine webhooks, A2A runs and answers, and shared browsers (`accountableStands`). A pairing code (other than a cloud machine's, which is the room's own) works only while the member who made it is still in the team with an account, which also covers someone an admin removed.
- **The rest is cleaned up in bounded steps, `accounts.cleanUp`**, each one transaction that takes one batch of the first kind of thing left, in this order:
  - **their CLI sign-ins are revoked**, 500 a step, **and the runs their sessions joined end**, 100 a step, as `people.revokeSignIn` ends them (ADR 0030, ADR 0032): each run leaves its Pairs;
  - **their Pairs** (ADR 0034), with the steps `internal.pairs.forgetPerson` takes on its own: their runs and agents leave, they stop being one of each Pair's people, their messages stay as "A deleted account", and a Pair left with fewer than two people ends (`too_few_people`). 50 Pairs a step, then 200 messages a step;
  - **every team, as `members.remove` takes a person out**: one step takes them out of the team and stops the agents they added, takes them out of calls and shared browsers, and disconnects the personal GitHub accounts they connected; later steps take them and their agents out of direct messages and private channels, 500 seats a step, then unlink their **personal machines** there, one a step, as `machines.unlink` does, forgetting each bridge token, and delete the pairing codes they or their agents made that nobody used. **Team machines they linked stay linked**: they are the team's, and `members.remove` leaves them too (below). The activity log records `member.removed` and `machine.unlinked` with `reason: "account_deleted"` and the person as the one acting. A team's last admin leaves too, since a deletion can't be refused, and the team gets another (below);
  - **every team an admin had already removed them from**: their name there becomes "A deleted account" (below), and their personal machines there are unlinked, one a step, as above. `members.remove` unlinks them now (below), but a member removed before 2026-11-05 may still have one linked, and once the deletion lands its bridge token refuses, so without this step its terminals and runs would show as live in that team for good.

  Leaving the teams is needed for D10 to hold: otherwise an agent they added keeps its key, and could join a Pair with a code and make the deleted person one of its people again. Each step finds its work by what is still there (a live sign-in, a live run, a Pair or team they're still in), and the team in progress is saved on the deletion (`leaving`), as is how far the walk through the teams they had already left got (`formerCursor`, a page of 50 memberships a step, however many times they rejoined), so a step run again goes on where the last one stopped. `members.remove` takes the same steps in one transaction, as before.
- **A deletion whose steps stopped is started again.** Convex doesn't retry a scheduled mutation that failed ("Scheduled Functions", Error handling). A cron every 10 minutes starts again each deletion whose last step ran more than 10 minutes ago and hasn't finished (`accounts.resumeStalled`), and a replay of the delivery from the Clerk Dashboard does so at once.
- **Leaving a team still changes nothing about a person's Pairs** (D10). Only account deletion does.
- **A deleted person's team messages show "A deleted account"** (Julio, 2026-11-05). When the deletion takes them out of a team, their member row there is renamed "A deleted account", so their messages, tasks and activity in the team show that name, as their Pair messages do. Their messages stay. Memberships of teams they had already left are renamed in the same steps. A member row has no picture of its own: the person's picture was erased with their row when the deletion landed. Someone an admin removes keeps their name, as before.
- **A team's only admin who deletes their account hands the team to the person who has been in it longest** (Julio, 2026-11-05). When the deletion takes them out of a team where no other person is an admin, the person who joined it earliest and is still in it becomes an admin (a rejoin makes a new membership, so this counts from when they last joined). Only a person counts, as for "a team needs at least one person who is an admin": not an agent, and not someone whose own account is being deleted. The activity log records `member.role_changed` with `role: "admin"` and `reason: "last_admin_deleted"`, the deleted person as the one acting. A team with no such person left is left without an admin. The step reads the team's admins through `members.by_team_role`, then its members in the order they joined, 1,000 a step, until the first who counts; how far it got is saved on the deletion (`successor`, the membership leaving and a page cursor of `members.by_team`), and the person leaves the team only once the search ends. Each person still in the team that is checked reads their person row, so without the pages a team where more than about 4,000 deleted accounts (or 32,000 agents and removed members, which read nothing more) joined before the first person who counts passed Convex's limits, rolled back, and failed the same way at every resume, holding up the deletion's other teams.
- **Removing a member unlinks their personal machines in that team** (Julio, 2026-11-05). `members.remove` takes the step account deletion takes (`takeBackMachineStep`, now in `members.ts`), in the same transaction as the rest of the removal: each personal machine the person linked in the team is unlinked as `machines.unlink` does, its bridge token forgotten so the bridge reads and reports nothing, and the pairing codes they or their agents made in the team that nobody used are deleted. Team machines they linked stay linked: they are the team's. The activity log records `machine.unlinked` with `reason: "member_removed"`, the admin as the one acting. Until then a removed member's laptop stayed in the team's machine list with its bridge token working.

## Revoking a sign-in in steps

Found while reviewing this slice: `people.revokeSignIn` and `cliSignIns.expire` ended all of a sign-in's joined runs in one transaction, so a sign-in with about 700 of them passed Convex's limits and couldn't be revoked or expire. Both now only mark the sign-in, which is enough for its run tokens to refuse (`joinedRunForToken`), and schedule the steps that end its runs, 100 a step (`cliSignIns.endJoinedRuns`), as account deletion does. The first step is scheduled too, not run in the same transaction, so nothing it meets can roll the mark back: a revoked sign-in stays revoked, and an expired one's write reaches the live queries watching it. A step that fails isn't retried, but each run then still ends when its heartbeat stops (`joined.expire`, two minutes), since a run whose token refuses sends none. The index `joinedSessions.by_sign_in` became `by_sign_in_ended`, so a step reads only runs still live, and `pairRuns.by_session` became `by_session_ended`, so ending a run reads only the Pairs it is still in, not the hundreds a session that pairs all day has left: 100 sessions with 320 such Pairs each had a step scan more than Convex's 32,000 documents.

## Consequences

- A deployment that should hear about deleted accounts needs `CLERK_WEBHOOK_SIGNING_SECRET` and an endpoint in the Clerk Dashboard (Webhooks, Add Endpoint) on each instance it trusts: URL `https://<deployment>.convex.site/clerk/webhook`, subscribed to `user.deleted` only, its Signing Secret copied into the variable. Since 2026-11-05 the development instance has an endpoint for DEV and one for production, and the production instance has one for production; production's variable holds both instances' secrets. Both deployments run this code since 2026-11-06, and a test delivery from each endpoint was answered 200. Until a deployment has both, accounts deleted in Clerk stay in the room as before. Deliveries refused meanwhile can be resent from the Dashboard (Message Attempts, Replay); each attempt carries a fresh timestamp.
- The route doesn't filter by Svix's IP addresses, which Clerk lists as an extra protection; the signature, timestamp and id checks are what it relies on.
- A daily prune keeps `clerkDeliveries` bounded. `accountDeletions` keeps one row per deleted account for good, since a Clerk user ID isn't reused.
- Until the cleanup finishes, a deleted person's rows can still show where they were (a team roster, a channel's members), but nothing acts as them.

## Verified

Backend tests (`tests/accountDeletion.test.ts`) send deliveries to the HTTP route in convex-test: Svix's published example signature in a list of two, a wrong secret, a changed body, a missing or `v2` signature, timestamps 301 seconds old and ahead, a missing secret, a body over 1 MiB, the effects above for a person in two Pairs and a team with an agent, an agent of a deleted person trying to join a Pair before the team step runs, the same `svix-id` sent again with another body, a second delivery for the same account, a team's only admin, and the 7-day prune. Added after the review of PR #153: a deletion that lands between Clerk issuing a first sign-in's ID token and the token exchange; a personal machine's bridge token and an unused pairing code refused before the cleanup runs, the machine unlinked after it, and a team machine still working; a sign-in with 700 joined runs and a person in 2,050 private channels in a room that enforces Convex's transaction limits; a deletion whose steps stopped, resumed by the cron and by a replay; and the remote connector and a routine webhook refusing an agent whose person was deleted while still in the team (`tests/connector.test.ts`, `tests/webhooks.test.ts`). Added with Julio's decisions: a team's only admin deleted while the person who joined next is being deleted too, with an older agent, so the person after them becomes admin, and a team left with nobody; team messages under "A deleted account" in a team the person was in and one they had already left; a personal machine in a team they had already left; 1,400 memberships left behind by rejoins, renamed in steps that fit Convex's limits; the only admin of a team of 2,050 people handing it over within Convex's limits; a browser ticket refused before the cleanup runs (`tests/browsers.test.ts`); and a sign-in with 700 joined runs, and one whose 100 sessions have each left 320 Pairs, revoked and expired in a room that enforces Convex's limits (`tests/cliSignIns.test.ts`). Added with Julio's decision on removal: an admin removing a member, whose laptop leaves the machine list and whose bridge token is refused while the team machine they linked keeps working (`tests/machines.test.ts`), and a deleted person's laptop left linked by a removal before that change, unlinked by the deletion. Added after the review of PR #157: a team where 4,500 deleted accounts joined before the first person who counts, its only admin deleted, handed over in steps in a room that enforces Convex's limits. No delivery from Clerk itself was received: registering an endpoint was out of scope, so the first real one comes after a deployment is set up as above (the endpoint's Testing tab sends an example).
