# A Hermes Agent run in a bridge terminal hears through its profile's gateway and answers with a launcher of its terminal's own

ADR 0026 has Hermes Agent in a bridge terminal hear messages through its `steer` mode, and #139's slice 8 asks for its state too. Research for that ADR read Hermes v0.22.7, where `display.busy_input_mode: steer` governed what the person typed into a busy session and nothing outside the terminal could reach a running `hermes`. Building it (2026-11-05) found that Hermes v0.23.0 works differently. `hermes` no longer runs an agent in the terminal: its classic interface attaches to the profile's gateway, which runs every session of the profile, and any local client of that gateway can attach to a session, see its events, steer it and submit to it ("Within one authenticated gateway, resuming or activating a live session attaches another event subscriber", Hermes `developer-guide/programmatic-integration.md`; `gateway-local-sessions.md`). The same move took the agent's commands out of the terminal: they run in the gateway, with the terminal's PATH (`client_env`) but none of its other variables (`agent/session_client_env.py`).

## Decisions

- **The bridge attaches to the terminal's session as one more gateway client.** It gets in as Hermes's own CLI does (`hermes_cli/gateway_client.py`): `identify` and a one-use `session-ticket` on the gateway's control socket, which only the same OS user reaches, then the gateway's loopback WebSocket with the subprotocol `hermes-gateway-v1` beside the ticket. The JSON-RPC methods it calls (`session.resume`, `session.steer`, `prompt.submit`) and the events it reads are the documented ones; the bootstrap is Hermes's own and isn't documented for other clients. We chose it over a Hermes plugin with a `transform_tool_result` hook, which can add to a turn but can't wake an idle session, needs an entry in the person's `plugins.enabled`, and would run for every session of the profile, and over shell hooks, which can't rewrite a tool result at all (a shell hook answers only `{"context": …}`, and `transform_tool_result` needs a string). The bridge never starts a gateway; the terminal's `hermes` does.
- **The terminal's tty names its session.** Hermes's classic interface records each terminal's session in `$HERMES_HOME/terminal-sessions/tty-<tty>` for its own `hermes -c` (`hermes_cli/terminal_breadcrumbs.py`). The bridge owns the terminal's tty, so it reads that file and follows the session it names, through the provisional id written first, and to a new session after `/new` or `/resume`. Each delivery reads it again first. Nothing is added to the person's command or config.
- **Messages go in with `session.steer` during a turn and `prompt.submit` otherwise.** A steer reaches the agent after the next tool call without stopping one, and a steer the turn ends without using becomes the next turn (checked live). `prompt.submit` on the gateway always queues (`Submission(..., 'queue')` in `gateway/session_controls.py`): it starts a turn on an idle session and waits behind a running one, so the person's `busy_input_mode`, `interrupt` by default, never applies to the room's messages. The claim's id is the submission id, so a submit whose answer was lost is sent again and the gateway answers with the same admission.
- **The run answers with a launcher of its terminal's own.** For each `hermes` terminal the bridge writes an `uplink-bridge` launcher in a private folder of its home that runs the bridge's CLI with the terminal's id, secret and socket, names it by absolute path in each delivery's reply hint, and removes it when the terminal ends. We chose this over ADR 0037's run keys in each delivery, because Hermes's classic interface prints each command it runs on the terminal's screen, which the room shows to everyone who can watch the terminal, and over adding the bridge's variables to the person's `terminal.client_env_passthrough`, which changes their config. The launcher holds the secret the terminal's environment already holds, readable only by the same OS user.
- **Approvals and questions stay in the terminal.** The room shows them as Waiting with a question to answer there. The bridge never tells the gateway it answers questions (`client.capabilities`), so attaching takes nothing away from the person; an approval asked with the bridge attached still reached the terminal.

## Consequences

- A newer Hermes can change the bootstrap or the breadcrumb without notice. Then the bridge doesn't attach, the run reports Unknown and its messages wait in the room, as for any terminal without a delivery path; nothing reaches the wrong session, because the bridge only follows a session the gateway confirms.
- Hermes's classic interface paints only the turns it started. A turn a room message starts in an idle session runs and is kept in the session's history, so the agent and `hermes --resume` know it, but the terminal doesn't show it; the room shows the run's state and its reply.
- Only `hermes` in the classic interface (`display.interface: cli`, Hermes's default) writes a breadcrumb. `hermes --tui`, Desktop and a messaging session report Unknown and hear nothing through the bridge. So does Hermes on Windows, where the bridge leaves this out.
- A message from a direct message or private channel reaches a Hermes run only under ADR 0039, checked where the room routes and hands it over, as for every terminal run.
- The room needed no change: the adapter's name is the room's harness name, `hermes-agent`, and the bridge sends the same `run_state_changed`, `run_hearing` and `run_message_result` and claims with `bridge:claimRunMessages`.

## Verified

On 2026-11-05, Hermes Agent v0.23.0 with `gpt-5.4-mini` in a scratch `HERMES_HOME` ran as a room run of Hermes Agent on a bridge from source against a local Convex deployment. The bridge followed the session and the room showed it hearing mid-task. A message to the idle session went in at the next turn and Hermes answered with the launcher's `reply`, posted as Hermes Agent (Julio Local). A message posted during a 25-second `sleep` went in with `session.steer`; the command finished with exit code 0 and Hermes answered right after it. A message from a direct message with the team run failed as `visible_outside` and never reached the session. After `/new`, the next message went into the new session. Before the adapter existed, a probe client on a scratch gateway submitted into an idle session, steered a 20-second command without stopping it, saw a steer sent during a tool-less answer become the next turn, and watched an approval reach the terminal with the probe attached.
