# People sign in from the command line with Clerk, and the room gives each computer its own token

ADR 0027 has a joined run act as its signed-in person, and people with no team must be able to pair. Until now only agent keys reached the Room API outside the app. Now `uplink login` signs a person in with Clerk in the browser, once per computer, and the room gives that computer a CLI sign-in: a token of its own that the `uplink` tool and `uplink-mcp` use to act as the person, in any of their teams or in none. Decided on 2026-11-05 while building slice 9 of #139, following decision D8 of the v1 build plan (ADR 0029).

## Decisions

- **The flow is OAuth's authorization code with PKCE and a loopback redirect** (RFC 8252, section 7.3), through a public Clerk OAuth application named "Uplink Room command line" that requires PKCE. The command line listens on 127.0.0.1 on a port the system picks, and accepts only the answer whose `state` it sent, from the issuer the room named (Clerk sends `iss`, RFC 9207). `uplink login --device` uses the device authorization grant (RFC 8628) instead, for a computer with no browser. Clerk documents both for command-line tools ("How Clerk implements OAuth", and its post "Adding Clerk auth to your CLI"). The browser flow is the default because RFC 8628 says it doesn't replace browser flows on devices that have one, and because a device code can be phished from afar (RFC 8628, section 5.4). Clerk's approval page for a code says "Only approve this request if you started it on your other device."
- **The room trusts Clerk's OpenID Connect ID token, once.** `POST /api/v1/cli-sign-in` gives the command line Clerk's issuer, the client ID and a nonce that lasts 15 minutes. The command line sends the ID token Clerk returns to `POST /api/v1/cli-sign-in/token`. The HTTP action checks it with Web Crypto: RS256, signed by a key in the issuer's JWKS, `iss` the first instance in `CLERK_JWT_ISSUER_DOMAIN`, `aud` the client ID in `CLERK_CLI_CLIENT_ID`, not expired, and carrying a nonce the room gave out and nobody has used. The room doesn't take Clerk's access token: Clerk documents an ID token's claims (`aud` is the client ID), while the development instance's access tokens are opaque (`oauth_jwt_access_tokens: false`) and checking one needs the instance's secret key. An access token issued to another client, such as a connector that registered itself (slice 13), must never become a full sign-in. The nonce ties each ID token to one sign-in on one deployment.
- **The room's token is random and stored hashed.** It is `urs_` and 48 hex characters (24 random bytes, as agent keys have; theirs start `urk_`). The room keeps its SHA-256 and its first 8 characters, in `cliSignIns`. It works for 30 days from sign-in, until `uplink logout`, or until it is revoked (`people.revokeSignIn`). `people.signIns` lists a person's sign-ins, never their tokens. It isn't a JWT: one indexed read checks it, and a revoked one fails on its next call. It doesn't go through Convex auth either: `auth.config.ts` stays as ADR 0014 left it, the token travels in the same `Authorization: Bearer` header as an agent key, and its prefix tells the two apart.
- **The command line keeps none of Clerk's tokens.** It asks only for `openid profile email`, but Clerk keeps `offline_access` on every OAuth application and so always issues a refresh token, which Clerk says never expires. The command line revokes the refresh token and the access token as soon as the room has the sign-in.
- **The Room API has two levels.** Team functions take a `teamId`, as before. With a CLI sign-in they act as the person's member in that team, as the app does, and `teamId` can be left out when the person is in exactly one team. Account functions (`accountQuery` and `accountMutation` in `lib/room.ts`, `realm: "account"` in `GET /api/v1/functions`) act for the person in no team: `people.me`, `people.signIns` and `people.revokeSignIn`. Agent keys can't call them. The app calls the same functions with its Clerk session.
- **The sign-in is saved in `~/.uplink-room/cli.json`**, mode 0600, which `uplink-mcp` also reads when `UPLINK_AGENT_KEY` isn't set. It belongs to the deployment it was saved for: with `UPLINK_URL` naming another one and no `UPLINK_AGENT_KEY`, the command line and `uplink-mcp` refuse rather than send it there. Signing in again, or saving an agent key over a sign-in, revokes the sign-in it replaces. If the room can't be reached to revoke it, the command line says so and keeps its token in the file (`unrevoked`) until `uplink logout --pending` or `uplink logout` revokes it; the token, not the signInId, because revoking by id needs a sign-in for the same person, which an agent key or someone else's sign-in isn't.
- **Sign-ins, agent keys and Clerk's ID token travel only over HTTPS**, or plain HTTP to 127.0.0.1, ::1 or localhost for a local backend. A bearer token sent in the clear can be read and replayed (RFC 6750, section 5.2), so `uplink login`, `RoomClient` and live watches refuse any other address before sending anything.

## Consequences

- A deployment that takes CLI sign-ins needs `CLERK_CLI_CLIENT_ID`: the client ID of the "Uplink Room command line" application on the first instance its `CLERK_JWT_ISSUER_DOMAIN` lists. Without it, `uplink login` says the deployment isn't set up, and agent keys work as before. Each instance has the application, made the same way: public, PKCE required, redirect URI `http://127.0.0.1/callback`, device authorization grant on, consent screen on (development `F7BSyV0kValWFmgW`; production made on 2026-11-05). DEV and production have `CLERK_CLI_CLIENT_ID` set, and both run this code since 2026-11-06.
- Revoking a sign-in ends its live watches at once, and so does its expiry. Convex caches a query's result by its arguments and reruns it only when a document it read changes, not when time passes (Convex's best practices, "Don't use `Date.now()` in queries"). So at `expiresAt` a scheduled function (`cliSignIns.expire`) sets `expired` on the sign-in's row, which ends any cached result that checked it. It waits in steps of at most 7 days, since convex-test fires a longer timer at once.
- `lastUsedAt` is written at most once an hour, and only by HTTP calls.
- Slice 10's run tokens will belong to a CLI sign-in. Slice 13 can reuse the JWKS check in `lib/clerkTokens.ts` with its own audience and claims.

## Verified

On 2026-11-05, against a local backend running this code and the development Clerk instance, with a `+clerk_test` user that was deleted afterwards: the browser flow (the consent screen named "Uplink Room command line" and asked for identity, profile and email), the device flow, `uplink whoami`, a team made after signing in, a message posted with `uplink messages post`, `uplink-mcp` over stdio with the saved sign-in, a second login revoking the first, and `uplink logout`. Clerk's ID token was RS256 with `kid` set to the instance ID, and held `aud: ["F7BSyV0kValWFmgW"]`, the nonce, `name` and `email`, and no `picture`. Its access token was opaque. Revoking the access token also ended the refresh token, but RFC 7009 leaves that to the server, so the command line revokes both.
