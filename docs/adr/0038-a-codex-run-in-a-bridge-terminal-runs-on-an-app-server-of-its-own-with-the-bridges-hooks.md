# A Codex run in a bridge terminal runs on an app server of its own, with the bridge's hooks

ADR 0026 has Codex in a bridge terminal hear messages through its app server, `turn/steer` during a turn and `codex queue --resume` when idle, and #139's slice 7 adds its state and approvals from Codex's own hooks. Building it (2026-11-05, Codex 0.166.0) showed that interactive `codex` can't have both as it starts by default. It runs every session on one background app server shared by the person's Codex home, and hooks run inside that server, with the server's environment, so a hook can't tell which terminal it serves. Codex reads hooks only from `~/.codex`, a repository's `.codex`, or config overrides, and `codex -c` with hooks makes the terminal UI leave the shared server ("command-line configuration overrides (-c, --enable, --disable, or --search) requires embedded mode"), after which no outside process can reach the session to steer it.

## Decisions

- **Each Codex terminal gets its own app server.** For a terminal it starts with `codex`, the bridge runs `uplink-bridge codex -- codex …`. That wrapper, inside the terminal, starts `codex app-server --listen unix://SOCK` with the bridge's hooks as `-c` values, tells the bridge the socket, runs the terminal UI on it with `codex --remote unix://SOCK` and the person's arguments, and stops the server when the UI exits. A person in a terminal shared from the machine runs `uplink-bridge codex` for the same. The hooks inherit the terminal's `UPLINK_TERMINAL_REF` and secret, the bridge knows the session's server without guessing among the person's others, and the session's thread is the `session_id` its hooks carry. Hooks the person passes with `-c` stay: Codex sets each `-c` value at its key, replacing an earlier one there, so the bridge's values carry the person's matcher groups and `hooks.state` entries with its own. A signal that reaches the wrapper before the terminal UI starts stops the server first. We chose this over a per-terminal `CODEX_HOME`, which would split the person's sign-in, config and saved sessions, and over writing hooks into `~/.codex` or the repository, which would reach every session there.
- **The bridge passes the trust for its own hooks in the same `-c` layer.** Codex runs a non-managed hook only once trusted, by a hash of its definition recorded under `hooks.state` in `config.toml`. The bridge computes that hash as Codex 0.166.0 does and passes it with the hooks, so nothing is written to the person's Codex home and the person isn't asked to review hooks they didn't write. `--dangerously-bypass-hook-trust` would also have run the person's own unreviewed hooks, so it isn't used. The computed hash is only a first guess: before the terminal UI starts, the server's `hooks/list` says whether it trusts each of the bridge's hooks and by which hash, and a Codex that hashes differently is started again with the hashes it reported. That has to happen in this layer, because session flags win over the person's `config.toml` field by field (`hook_states_from_stack`), so a wrong hash here would also beat one the person approved in `/hooks`. When the hooks still aren't trusted, or `hooks/list` can't say, the wrapper says so in the terminal and runs Codex without the room: never with the bridge's hooks silently skipped.
- **Messages go in through that server.** The bridge claims a run's messages as soon as the room says they wait, puts them in with `turn/steer` during a turn and `turn/start` when idle, and tells the room they were delivered only once Codex took them. A steer or start that went out unanswered (a timeout, or a closed connection) may have gone in, so the bridge doesn't try the other: it looks for the message in the thread's newest turns and reports it delivered when it's there, and otherwise unsure, which the room hands over once more at most. A `/side` conversation, an ephemeral fork whose hooks carry its own thread, doesn't take the session's messages: Codex keeps no turn history of it and discards it when the person goes back. `turn/start` replaces `codex queue --resume` here: it answers whether Codex took the message, where `codex queue` "prints a warning and still exits successfully" when it can't resume.
- **Approvals go to the room.** `PermissionRequest` reports the approval with Codex's reason and the command, and the driver's answer becomes Codex's `decision`. An approval nobody answers within the hook's 600 seconds, or a second one asked while the first waits, gets no decision, so Codex asks in the terminal: never an allow the driver didn't give.
- **Failed comes from the server, the rest from hooks.** Codex fires no hook when a turn fails, so the bridge follows the session's thread and reports Failed on `turn/completed` with `status: "failed"`.
- **A command in Codex's sandbox posts through the terminal's hook.** The default `workspace-write` sandbox blocks the bridge's socket, so `uplink-bridge say` and `reply` print a request signed with the terminal's secret, and the `PostToolUse` hook, outside the sandbox, posts it and tells the agent the result. We chose this over opening the sandbox to the socket (Codex's Unix-socket allowlist needs its experimental network proxy and changes the person's sandbox) and over asking the agent to request an escalation for every reply, which would be an approval each time.

## Consequences

- The session isn't on Codex's shared background server, so other Codex clients of that server don't see it while it runs; its saved session is in the person's Codex home as usual.
- A Codex started any other way in a shared terminal, with `--remote`, with `--no-daemon`, or on Windows, reports Unknown and hears nothing, as before.
- The computed trust hash depends on Codex's normalization of a hook (`hook_hash` in openai/codex); a test pins it to hashes Codex 0.166.0 reported. When a Codex hashes differently, each session starts its server twice. A Codex without `hooks/list` runs without the room.
- Any process in the terminal can still act as its run, as ADR 0026 accepted for Claude Code, and so can anything that prints a request the terminal's own processes signed.
- The room needed no new protocol message or feature name. On a bridge from before, a Codex terminal's messages wait in the room, as they did.

## Verified

On 2026-11-05 Codex 0.166.0 (`gpt-6-luna`, low effort, `on-request` approvals, `workspace-write` sandbox, a scratch `CODEX_HOME` with a copy of the sign-in) ran as a room run on a bridge from source against a local Convex deployment. The terminal UI started on its own server without a review prompt. A message posted before the session's first turn started a turn within about two seconds. One posted during a 25-second command went in with `turn/steer` while it ran, and the command finished. The agent answered both with `uplink-bridge reply` through the hook, and the replies were stored under the driver with `asRun` "Codex (Julio Local)". A network command waited in the room as an approval, and Allow from the room ran it. `/quit` stopped the server and ended the terminal. A failing turn's `turn/completed` was checked against a real server separately.

Checked again on 2026-11-05 after PR #156's review, with the same Codex, settings and setup: a message to an idle session went in at the next turn about a second after it was posted; one posted during a 25-second command was steered in a second later and the command still finished; an approval waited in the room and Allow from the room ran the command; a message posted while a `/side` conversation ran a 30-second command went into the session's own thread as a new turn, not into the side conversation; `uplink-bridge codex --ephemeral` stopped at Codex's own usage error ("unexpected argument '--ephemeral' found") and the wrapper stopped its server; a `PreToolUse` hook the person passed with `-c`, with its trust, ran on a tool call beside the bridge's hooks (`hooks/list` listed it at `pre_tool_use:0:0` and the bridge's at `pre_tool_use:1:0`, both trusted); a server given stale hashes for the bridge's hooks listed them as `modified` with `currentHash` equal to the bridge's own, and one started with those hashes listed them as trusted; a SIGHUP while the server started ended the wrapper with exit code 129 and left no server; and a started and a steered message were listed as the user's about half a second after Codex took them.
