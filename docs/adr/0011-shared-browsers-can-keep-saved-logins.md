# Shared browsers can keep their logins as saved logins, for as long as the starter picks

Whoever starts a shared browser picks how long it keeps its logins: Temporary (nothing is kept, as before), or keep them for 1 day, 7 days, 30 days, or until someone forgets them. Kept logins become **saved logins**: a named Hyperbeam profile, such as "staging admin", that belongs to the channel. Hyperbeam stores a session's Chrome profile (cookies, passwords, history and bookmarks) encrypted when the session ends, and loads it into a later session started with it (docs.hyperbeam.com, "Persist Session State" and "Starting a Chromium Session", checked 2026-11-02). The profile id stays in the backend.

A profile's id is the id of the session that created it, and Hyperbeam's embed URL path is a session's id in base64url (the docs' example `Uvloy2c5QZeD1yMF_l1vVA` decodes to its `52f968cb-…` session id). So the profile can't be created by a browser people join: anyone with its embed URL could read the profile id. The backend creates each new profile with a seed session nobody joins (`profile: true`, a random auth bearer stored nowhere, ended at once) and keeps that session's id as the profile id. Every shared browser with saved logins starts with `profile: { load: <id>, save: <id> }`, which loads the profile and saves back to it when the session ends.

We chose this over keeping every browser empty because the team and its agents sign in to the same staging consoles and vendor dashboards every day. A browser that forgets every login makes each session start with a sign-in, often with a code from someone's phone.

Hyperbeam has no call to delete a profile. Its REST API has calls to start, end, list and read sessions, read usage, and the session endpoints (roles, users, bookmarks, permissions), and nothing for profiles; Hyperbeam confirmed on 2026-11-03 that profiles can't be deleted by hand. It deletes profiles nobody has loaded for three months. But a session started with `profile: { save: <id> }` overwrites that profile when it ends (docs.hyperbeam.com, "Start Chromium Session", checked 2026-11-03). So forgetting saved logins, by hand or when their time runs out, stops the room loading them, and once the last browser with them has ended, the room erases them: a short session that loads nothing saves an empty profile over them (#76). The app and the Room API say this in plain words.

## Consequences

- Temporary stays the default. Anyone who drives a browser with saved logins acts as whoever signed in, so keeping logins is a choice the starter makes. When they do, 7 days is the first choice offered.
- Saved logins belong to a channel. Anyone who can start a browser there can start one with them (agents need `browsers.use`). Whoever saved them (for an agent, also the person who added it), or an admin, can rename them, change how long they're kept, or forget them. An agent changing someone else's saved logins as an admin also needs `team.admin`.
- The keep time counts from when it was picked, and picking again restarts it. A scheduled function forgets saved logins at their deadline, and from the deadline on they count as forgotten even if that job hasn't run yet: no browser loads them, and they can't be changed. Forgotten saved logins stay listed in the channel for 30 days, with why and when, so people see what was forgotten.
- Hyperbeam saves a profile when its session ends, so the room never runs two sessions on one profile: saved logins that a starting, live or stopping browser uses can't be loaded until that browser is confirmed gone. Otherwise the later save would overwrite the earlier one. A start with saved logins that fails without an answer may still have made a session, so that browser stays stopping, holding its saved logins, until the room has found the session by its tag and ended it. Hyperbeam's session list and lookups don't show tags, but a start with the tag of a running session returns that session, so the room starts with the tag (a body that is harmless if nothing runs) and ends whatever comes back. It stops looking once no such session can still run: the longest session plus the offline timeout and a minute, counted from when provisioning ended. Every start call has a deadline, and a watchdog scheduled with provisioning recovers a start the same way if the provisioning job ends without reporting (Convex ends an action at 10 minutes).
- Keeping logins for the first time starts two Hyperbeam sessions: the seed for a few seconds, then the browser. The seed is ended and confirmed ended (its `termination_date` is set) before any browser loads its profile. A seed still running would save its empty profile when it ended, which could come after a short-lived browser's save and wipe real logins. If ending it can't be confirmed after three tries, the start fails and no browser uses that profile; the seed's own timeouts end it.
- Forgetting saved logins while a browser runs with them doesn't end that browser. Its session still saves to the profile when it ends; then the room erases the profile, and nothing loads it again.
- Profiles are an account feature Hyperbeam turns on by request. On a key without it, every form of `profile` is refused with `400 err_api_restricted` ("contact founders@hyperbeam.com to get it enabled"), as the dev key was on 2026-11-02. Until it is on, a browser started with saved logins fails and says so; temporary browsers work as before. Hyperbeam enabled profiles on our account on 2026-11-03.
- Ending a browser with saved logins waits 30 seconds before Hyperbeam's DELETE. In the live check on 2026-11-03, sessions ended about 5 seconds after a login came back logged out when their profile was loaded, while sessions ended 15 seconds or more after a login stayed logged in. Our guess is that Chrome writes new cookies to disk every few seconds and the DELETE doesn't wait for it; the timing is what was measured. The browser shows as stopping for those 30 seconds, and its saved logins can't be loaded until it has ended. Nobody can watch or drive it meanwhile: when the stop begins, the backend takes every control role away and disconnects everyone connected, and a control update still in flight then takes its roles away again. The session runs on only to save.
- Hyperbeam ignores `start_url` when a session loads a profile: it opens the profile's restored tabs, or a New Tab for an empty one (seen live on 2026-11-03). So after starting a browser with saved logins, the backend opens the start URL in its active tab. That is the browser's first navigation, and all of a browser's navigations (the start URL, `openUrl`, an opened suggestion) run one at a time under a lease on its row, each until the URL it opened is still the latest, so a URL asked for later always ends as the open page (#77). A navigation that stops renewing the lease loses it after a minute, and the next one opens the latest URL; the lease is checked again right before the call that changes the page, and if a late change lands anyway, the latest URL is opened again. A call that fails is tried twice more, 2 and 4 seconds apart, and then the browser shows why (`navigationError` in `browsers.get`).
- "Until deleted" can still lose its logins: Hyperbeam deletes a profile three months after it was last loaded.
- The profile id is never returned by a query, an agent call or the activity log. The rules for who drives, the wheel and the frame origin from ADR 0006 are unchanged.
- Saving over a profile erases it. In the live check on 2026-11-03, a load-only session (`profile: { load: <id> }`) started after Forget was still logged in to the test site, so dropping the profile id alone left the logins at Hyperbeam. Then a session with `profile: { save: <id> }` and nothing loaded ran for 20 seconds and was ended. The next load-only session opened that session's blank tab and was logged out, 197 seconds after the login, inside the site's 10-minute login cookie.
- So Forget erases saved logins with that session, which costs a few billed seconds. The room starts it only once every browser with the saved logins has ended, so the profile still has one session at a time, and ends it 30 seconds after it started, the same wait a browser gets before Hyperbeam saves. It starts after the last browser's DELETE has returned, so it saves at least 30 seconds after that browser did. Like the seed, nobody joins it: its embed URL and admin token never leave the adapter, and its auth webhook bearer is random and stored nowhere. If the room never ends it, its own timeouts do (2 minutes with nobody connected, 5 minutes at most), and it saves then. A start or end that fails is tried again with backoff (30 seconds, doubling to 10 minutes) for about a day, and Forget never waits for it. The profile id is kept only until the erase is done or given up on; after giving up, Hyperbeam's three-month deletion is what's left.
