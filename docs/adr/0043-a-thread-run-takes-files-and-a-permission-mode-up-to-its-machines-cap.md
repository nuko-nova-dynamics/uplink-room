# A thread run takes files and a permission mode, up to its machine's cap

Julio drives T3 Code thread runs from the app's thread view. On 2026-11-05 he hit three walls. The thread's message box took text only, though the bridge's thread reader already read T3 Code's attachments, and he wanted to send pictures and files to T3 Code and the other harnesses. Every thread the room started was `approval-required`, with no way to pick full access. And the header's control menu drew "studio-mini allows up to Suggest." and the level's line over the Ask for control and Take control buttons.

We checked T3 Code v0.1.8-nightly.20261105.4234 (commit 8b570d2, the installed nightly) for how its own client sends attachments and changes a thread's mode, Codex 0.166.0's app-server schema (`codex app-server generate-json-schema`), Hermes Agent's gateway (`tui_gateway/methods_prompt.py`, commit 2bd378e) and Claude Code 2.1.318's `--help`.

## Decisions

### Files

- **The thread's message box takes files like the channel composer:** a button, paste and drag and drop, through the same upload flow (`messages.attachUrl`, then the bytes, now shared as `useFileUploads`) and the same checks and limits (`checkAttachment`: no SVG, images up to 20 MB, other files up to 50 MB, at most 10). `threads.send` takes `attachments` and may then have no text. The room keeps each file on the message (`threadAttachments`), shows a sent image from its own copy, and names the other files. A teammate's suggestion stays text.
- **The bridge hands T3 Code the files the way T3 Code's own client does.** For each file it calls `attachments.createUploadUrl` (which `orchestration:operate`, the bridge's pairing scope, allows), `POST`s the bytes to the signed path it gets back with a matching Content-Length, and puts the returned ids in `message.dispatch`'s `attachments`, where T3 Code claims the uploads for the thread. PNG, JPEG, GIF and WebP up to 10 MB go as images, so the model sees them; anything else up to 50 MB goes as a `file`, which T3 Code hands the agent by path. It is all or none: a file that fails to download or upload fails the message before anything reaches the thread.
- **A chat message's files reach a run with the message,** to a bridge that names `run_message_files`. The room hands the bridge each message's files with a link only the bridge sees. A T3 Code thread gets them as attachments. A delivery with files waits for the turn to end, since T3 Code restarts a turn it steers with attachments. A terminal run gets copies saved in its workspace, under `.uplink-room/files/<delivery>/`, which the bridge marks git-ignored. The repository decides what is in the workspace, so the bridge follows no link it finds there: a symlinked `.uplink-room`, `files`, delivery folder or `.gitignore` saves nothing, and each file is written as a new file and renamed into place, so a link where it goes is replaced, not written through. The delivery's text names each path, because Claude Code in a terminal has no other way to take a file. Codex also gets the images themselves as `localImage` items in `turn/start` or `turn/steer`. Hermes Agent gets them through `image.attach` before `prompt.submit`, and such a delivery doesn't steer a running turn, because `session.steer` takes text only. A run whose bridge is older still hears only how many files stay in the room.
- **A claim carries no more files than one delivery takes, and is held while they move.** The room stops a claim before the message whose files would pass 40 (`RUN_CLAIM_FILES_MAX`, four messages' worth, or a smaller `maxFiles` the bridge names); the rest wait for the next claim, so no file is left out of a delivery the room counts as delivered. Moving the files can outlast the claim's two minutes, so the bridge holds it meanwhile (`bridge:holdRunMessages`, every 40 seconds, up to 15 minutes after the claim). A claim the room gave back sends nothing: its messages wait again, and the next claim takes them. The bridge names `maxFiles` and holds a claim only for a room that names `run_message_files` in its features: a room from before refuses a claim with `maxFiles` in its argument validator, which would stop every delivery to a bridge updated before its room, and it hands no files anyway.
- **A Claude Code hook never waits on a download.** Claude Code gives `UserPromptSubmit`, `PostToolUse` and `PostToolUseFailure` the bridge's 30-second hook timeout, and one file may take 120 seconds to download, so a hook that waited on its claim's files timed out, the claim went back, and the next tool call downloaded them again. Now, when the room says messages wait during a turn, the bridge claims them at once and saves the files outside any hook, holding the claim meanwhile and until a hook takes it (up to the same 15 minutes). A hook that comes while files still move answers with nothing. Once they are in, the next tool call's hook hands the claim over, or the idle session's waiter does if the turn ended. A claim with no files that a hook asked for itself still goes at once. A claim's messages go together, so a later message never reaches the run before an earlier one whose files still move.
- **Files saved for a terminal run go when the run ends.** The bridge removes the run's delivery folders from `.uplink-room/files/` when its terminal ends or stops being shared, and lists each workspace it saved in (`room-files.json` in its folder). On start it removes delivery folders older than 7 days from those workspaces, for runs whose end it never saw, and forgets a workspace with none left. Removing follows no link, with the same checks as saving: a linked `.uplink-room`, `files` or delivery folder is left alone, and a link inside a delivery folder is removed as a link, never what it points at.
- **A thread message with files reaches T3 Code even if the bridge restarts while they move.** The bridge takes such a message off the room's queue before its files move, so a bridge that stopped meanwhile lost it. The room keeps every thread message `sending` until the bridge answers (`thread_message_result`), and the first time a new bridge process names its features it sends again each message on that machine still `sending` from the last day, unless it is still queued for that bridge. T3 Code takes a message once by its id (`commandId` `uplink-room:message:<id>`), so one that reached it before the restart isn't sent twice. A message to a run stopped meanwhile fails with `run_stopped`, and one with files to a bridge that no longer takes files fails with `files_unsupported`.
- **A file goes only where its message goes (ADR 0039).** The room adds a message's files to a claim only after `handOver` has checked that the run may hear the message, and sends a thread message's files only with that message, to that thread's own bridge. A storage link never reaches the run, T3 Code or a room view. A sent image in a thread from a private place gets no lasting link in the conversation (ADR 0016).
- **The composer says when a run takes no files with a message.** In a direct message with a terminal run, once a file is attached, a line under it says that the run gets copies saved in its workspace, with the paths in the message, or that the files stay in the room for an older bridge. `channels.list` gives each run of a direct message `files`: `with_message`, `saved` or `stay`.

### Permission mode

- **A run has a permission mode: what its agent may do without asking.** The names are T3 Code's runtime modes, `approval-required`, `auto-accept-edits`, `auto` and `full-access`. The app calls them Ask before acting, Edit files without asking, Approve safe steps itself and Full access, each with one line on what it allows. A run that names none is `approval-required`, as every room run was before.
- **Starting a run picks it** (`runs.start` `runtimeMode`). A thread starts in any mode its T3 Code provider lists in `supportedRuntimeModes`; the bridge refuses any other with `mode_unsupported`. A Claude Code terminal starts with `--permission-mode acceptEdits`, `auto` or `bypassPermissions`, and a Codex terminal with `-a on-request -s workspace-write` or `-a never -s danger-full-access`: the flags T3 Code itself passes these harnesses for the same modes (`ClaudeAdapterV2.ts`, `CodexAdapterV2.ts`). Codex's `auto` needs `approvals_reviewer`, which only `-c` sets, and `-c` takes a terminal's Codex off its own app server (ADR 0038), so a Codex terminal doesn't offer it. A terminal in `approval-required` starts with no flags, as the machine sets the harness up. Other terminal harnesses and runs in Rex take no mode.
- **Only the thread's driver changes it on a live thread** (`threads.setMode`), as only the driver sends it messages (ADR 0023); an admin who isn't driving takes control first. The bridge sends `thread.runtime-mode.set`, which T3 Code applies from the agent's next step, and takes the change only from the driver. The room keeps the new mode pending until the bridge reports that T3 Code has it (`thread_mode`), and shows the mode in effect until then, so the header never shows less than the agent may do. A refusal (`input_rejected` naming the mode) drops the pending mode, and the same change can be asked again. A lower mode it takes from anyone, so the machine's cap can lower a thread whoever drives it. The room records who set the mode and when (`run.mode_set` in the audit log) and shows it in the thread's header: a chip with the mode, and its tooltip naming who set it, or that it changed in T3 Code itself. The bridge reports each thread's mode and its provider's modes (`thread_mode`), so a change made in T3 Code shows too, and only after it reported the thread's run: the room has no run yet for a thread first found in T3 Code, and drops a mode for a run it doesn't have. A terminal keeps the mode it started with.
- **Whoever a machine belongs to caps it** (`machines.updateSettings` `mostPermissiveMode`), like its most open access (ADR 0021, ADR 0025): admins for a team machine. Every machine starts at `approval-required`, so nothing runs without asking until the owner allows more. Lowering the cap asks open threads above it to lower at once, to the most permissive mode the thread's provider lists at or under the cap (approval-required when it lists none there), since T3 Code refuses a mode the provider doesn't take. Each shows the lower mode, marked in amber with the mode it had, once T3 Code has it; terminals keep theirs until they end, and the setting says so. Saving the cap again, even unchanged, asks again for any thread still above it. And whenever the bridge reports a thread's mode above its machine's cap, whether it was raised in T3 Code itself or a driver's raise reached T3 Code after the cap rolled it back, the room asks for the cap's mode the same way, unless a lowering is already on its way, so no order of reports leaves a thread above its cap.
- **A thread never stays above its machine's cap for the room.** If T3 Code refuses the lower mode, the room asks for the next lower one the provider lists. When none is left, or the bridge can't set a mode at all (T3 Code unreachable), the room stops the run as `runs.stop` does: it shows Stopped, the bridge stops the thread, and the room sends it no more messages. The header's mode chip stays on the mode T3 Code still had, in amber, saying the room stopped it because T3 Code didn't take a lower mode (it stays after the run stops, where a stopped thread shows no other chip), and the audit log keeps `run.stopped` with reason `mode_cap`. Stopping is safer than leaving the room's messages to drive an agent past what the machine's owner allows; the thread itself stays in T3 Code, for whoever is at the machine.

### The control menu

- **The menu's levels sit in two rows, with the lines under them.** The popover's rule that makes each button a full-width menu row also made the four level buttons rows inside the segmented control's fixed 28 px. They stacked past it, and the machine's limit and the level's line were drawn over the lower ones. In the thread menu the levels are now a two-column grid at their own height, so everything after them is in flow below, at every level. Terminals and Spaces show the same control in their header bar, not in a popover, and their Hand off popovers are plain menu rows, so neither had the overlap.

## Considered options

- **Writing a file into the workspace for a T3 Code thread too.** T3 Code takes attachments the way its own composer sends them, and gives images to the model as images, so a path would lose what the agent can see.
- **Inline `data:` URLs for images.** T3 Code's `assets.persistChatAttachments` takes them, but only for images, and the upload route takes any file with the same claim step.
- **Codex's `auto` through `-c approvals_reviewer=auto_review`.** It would move a terminal's Codex onto an embedded server no outside process can steer, which ADR 0038 rules out.
- **Letting admins change a live thread's mode without driving.** The mode is the driver's choice, like the thread's messages; an admin takes control first, which the room already records.
- **Leaving a thread T3 Code won't lower running, marked over its cap.** The header would say so, but the room would still deliver its messages to an agent working past what the owner allows.
- **Capping modes with the machine's most open access.** Who may watch a thread and what its agent may do without asking are different questions, and the owner may want either open without the other.

## Consequences

- A Claude Code terminal's run sees a file as a path it reads with its own tools, not as an image in its prompt. Codex and Hermes Agent see images as images.
- Files saved for a terminal run leave its workspace when the run ends, or within 7 days if the bridge never saw it end, so an agent can't come back to them later. A bridge from before this change never listed its workspaces, so what it saved stays until removed by hand.
- A run's messages are claimed when the room says they wait during a Claude Code turn, not at the next tool call, so the room checks who may hear them a little earlier.
- An upload T3 Code got for a message that then failed stays in T3 Code's pending uploads until T3 Code removes it, after 15 minutes.
- A bridge from before this change ignores `set_thread_mode` and the new fields, and doesn't name the new features, so the room offers neither files nor modes for its threads and says to update it.
- The cap reaches a terminal only when it starts. Lowering it doesn't touch a running Claude Code or Codex terminal.

## Amended

On 2026-11-06, after review of #167: hooks no longer wait on downloads, saved files are removed, a restarted bridge gets thread messages that were still on their way, and the over-cap chip stays on a stopped thread. Each is in the decisions above.

## Verified

On 2026-11-06 a bridge from source ran against a local Convex deployment and this Mac's T3 Code v0.1.8-nightly.20261105.4234, in a scratch project. With the machine at its default cap, `runs.start` refused a Claude Code thread in `full-access` ("allows at most approval-required"). Once the owner raised the cap, the thread started, and T3 Code listed it with `runtimeMode: full-access`. A 96 × 64 PNG, red on the left and blue on the right, uploaded with `messages.attachUrl` and sent with `threads.send`, reached T3 Code as the message's image: Claude Code (claude-opus-5-5) answered "Red fills the left half of the image and blue fills the right half." `threads.setMode` to `auto-accept-edits` changed T3 Code's thread to it, and the audit log kept both changes with who made them. T3 Code's Claude and Codex providers list no `supportedRuntimeModes`, so they take every mode. The scratch project, its thread, and the bridge's T3 Code session were removed afterwards.
