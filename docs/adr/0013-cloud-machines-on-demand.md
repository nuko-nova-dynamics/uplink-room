# Cloud machines are persistent team machines that start on demand

A cloud machine is an ordinary team machine whose computer the room rents and starts and stops itself. The first provider is Vercel Sandbox (Pro) in `iad1`, Linux only. Each machine is a named, persistent sandbox: stopping it saves its filesystem, and the next boot starts from it (vercel.com/docs/sandbox, "Persistence", checked 2026-11-02). So a cloud machine keeps its disk, its settings and its machine-bound profiles when stopped. It starts when a terminal or run needs it and stops after 15 minutes with no live work. Julio decided this on 2026-11-02 (#10, `research/decision-cloud-machines.md`).

We chose this over a disposable box per run because a team machine already has settings, slots, access, a machine setup and profiles, and people would have to sign in again on every fresh box. Disposable per-run boxes are deferred. Mac and Windows stay on linked machines; Vercel Sandbox has neither.

## How it works

- The room talks to a provider only through `CloudMachineProvider` (`packages/backend/convex/lib/cloudProvider.ts`): create, start, stop, extend, status and delete, each safe to repeat. The Vercel adapter (`lib/vercelSandbox.ts`) uses `@vercel/sandbox` and runs only in Node actions (`cloudMachineActions.ts`), because the SDK needs Node. Tests use a fake provider.
- Making one creates the machine row first, then a sandbox named after it. Its boot step (`lib/cloudBoot.ts`) runs detached on every boot. On the first boot it installs the bridge from `UPLINK_BRIDGE_TARBALL_URL`, sets the machine's own limits wide open so the room's admin-set settings decide, and pairs with a one-time code bound to that machine row. The bridge's token stays on the kept disk, so later boots only start the bridge. The code comes in that boot's environment, never in the script, and the provider's credentials never reach the box.
- Wake-before-start: starting a terminal or thread run, or creating a profile, on a stopped cloud machine starts it. The start waits in the bridge's queue, as it already does for an offline machine, and the bridge's registration keeps starts queued after its saved cursor. Concurrent starts share one wake. A start that arrives while the machine stops waits for the stop, then wakes it again; meanwhile the old bridge reads nothing from its queue. When a stop finishes, only the work that reached that session ends; starts still queued stay queued, and any queued start wakes the machine again. An admin who stops a machine that is already stopping cancels that queued work instead.
- The idle stop runs every minute while the machine runs. Live work means live or starting terminals, shared Spaces, thread runs Working or Waiting, and starts or profile changes still queued for the bridge. Bridge heartbeats don't count, and a bridge quiet for the whole idle time keeps nothing awake.
- Every start, stop and delete bumps a generation, and each provider call carries the one it was made for, so a late result from an older operation changes nothing. A create or start that finds it was overtaken while it talked to the provider undoes what it did: it deletes the box if the machine was deleted meanwhile, or stops it if the machine was stopped. Twenty minutes after a confirmed delete, the room asks the provider again and deletes the box if it came back.
- Convex runs a scheduled action at most once, so the start's watchdog is set in the same mutation that schedules the provider call, before the call. An action that dies after booting the box can't leave the machine starting forever.
- A session lasts an hour at the provider and is extended by an hour while work goes on, so the bill stays bounded if the room ever stops checking. The room moves its deadline only when the provider accepts an extension; a failed one is asked again at the next minute's check.

## The reconciler is the safety net

Each start, stop and delete action may change the provider, and they can race: an action that is overtaken, dies mid-call (Convex runs a scheduled action at most once) or fails while compensating can leave a box that doesn't match the room. After two review rounds of patching such races one at a time, correctness now rests on a reconciler (`lib/cloudReconcile.ts`, `cloudMachineActions.reconcileAll`). The per-action corrections stay as a fast path.

- It runs from a cron every 5 minutes, and 20 seconds after any provider action reports back, so a leak lasts at most one interval. The cron is defined only on a deployment with `VERCEL_TOKEN`, `VERCEL_TEAM_ID` and `VERCEL_PROJECT_ID`, so a deployment without cloud machines schedules nothing (#51). Convex reads cron definitions only on deploy, so a deployment that gets those settings later has the cron from its next deploy.
- It lists the boxes tagged with this room at the provider and compares them with each machine's state and generation. It stops a box that runs for a stopped or failed machine. It deletes a box no machine owns and a deleted machine's box. It deletes the snapshots a delete left behind. It boots a confirmed boot again if its box went down. It marks a running machine stopped when its box is gone. It ends the work a failed machine still shows once its box is confirmed down. It restarts a stop or delete with no progress for 10 minutes. It wakes a stopped machine that has work queued, and fails work queued on a deleted one.
- Each provider call is re-checked against the machine's generation right before it is made.
- **What it never touches:** boxes without this deployment's `room` tag, since dev and prod may share a Vercel project and other projects' sandboxes are not ours; a box booting for the current generation before the provider confirms the boot, which its action and the watchdog own; a running machine's box, which the idle stop owns; a stop or delete still making progress; and any machine that changed state after the listing began, since the listing may be older than the change.
- Snapshots are found by the ids the delete recorded while the box existed. Once a box is deleted, Vercel lists none of its snapshots by name, and its own cleanup of them is asynchronous (seen live: about two minutes).
- Deletes are numbered attempts. Only the current attempt's failure schedules the next, and a guard set with each attempt starts the next one if that attempt never reports back. **Retry now** starts a new attempt, and the attempt it supersedes changes nothing.
- When a bridge registers, outbox rows at or below its saved cursor are acknowledged: it handled them, maybe without acknowledging before it died, and they would otherwise count as live work forever.

## Consequences

- A stopped machine is not a suspended run. Only the disk survives. Terminals and runs that were going when it stopped end, and a later boot doesn't bring them back.
- If the bridge doesn't come back within 10 minutes of making the machine or 5 minutes of a later start, the waiting terminals and runs fail with that reason and the box is stopped. A failed start does the same. Starting again retries.
- When the bridge goes quiet while the room thinks the machine runs, the room asks the provider. If the provider stopped it (such as at Pro's 24-hour session limit), the room marks it stopped and ends what ran there.
- A stop is retried with backoff six times, then shows as failed with "Didn't stop", and admins see it at the top of Machines with its last error, since its box may still bill. It keeps being retried in the background: the reconciler stops a failed machine's running box every 5 minutes, and once it sees the box down the machine settles as stopped, as after any stop, so work or a profile cleanup owed starts it again (#51). We chose this over keeping it `stopping` and retrying forever, as deletes do, because a machine stuck `stopping` would hold Start behind the stop, and the reconciler already retries the stop. A delete never gives up: it retries with backoff up to every 30 minutes until the provider no longer knows the machine, admins see it as still deleting with its last error, and deleting it again retries at once. A stop request or an offline bridge alone doesn't prove the box stopped.
- Each machine keeps exactly one snapshot that never expires, and older ones are deleted as soon as a newer one exists. A stopped machine can't lose its setup to the default 30-day snapshot expiry, and Vercel's 14-day removal of sandboxes that can't resume doesn't apply.
- A profile that expires or is deleted while the machine's box is down (stopped, or failed after a stop) wakes it, so its bridge deletes the profile. When the idle stop saves the disk again, the snapshot that held the profile is deleted. The cleanup is recorded whenever the bridge isn't connected: when the machine is down or starting, or still shown running with a quiet bridge (the provider may have stopped the box before the room noticed). When the room learns a box stopped, it also counts a profile that expired after the bridge was last heard from, or a deletion still queued, since a dead bridge looks online for up to 90 seconds. Any stop with cleanup owed starts the machine again (a stop that ran out of tries retries it with the same backoff as a failed start), and the reconciler wakes a stopped machine with cleanup still owed. A maintenance wake, or a start that owed one, that doesn't reach a bridge is retried, from 10 minutes doubling up to every 6 hours, until one does.
- A create that failed before any sandbox existed recovers on the next start, which makes sure the sandbox exists before booting it. In the app, the run picker offers stopped cloud machines as "Starts when you run", with the same sharing and slot checks.
- Only admins make, stop and delete cloud machines (agents need `machines.manage` and an admin role, ADR 0003). Anyone who may start runs may start one (`runs.start`). Unlinking a cloud machine is refused: deleting it removes the box and its snapshots too.
- The boot step puts the bridge's private install on the PATH of the terminals it starts (`UPLINK_BRIDGE_BIN_DIR`), so Claude Code's hooks find `uplink-bridge`.
- Cloud machines need `VERCEL_TOKEN`, `VERCEL_TEAM_ID`, `VERCEL_PROJECT_ID` and `UPLINK_BRIDGE_TARBALL_URL` in the Convex environment. On prod, the Bridge release workflow sets `UPLINK_BRIDGE_TARBALL_URL` on each version tag (#52, `packages/bridge/README.md`). Without them they say they aren't configured, as shared browsers do (ADR 0006).
