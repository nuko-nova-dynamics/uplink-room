# A Rex tab the room sees runs its program on a pty the bridge owns, inside the tab

Rex (superlogical.com/rex) is a terminal app some of the team works in. The room now shares Rex tabs and starts runs in them. For that the bridge needs a tab's output as it happens, a way to type into it for the room's driver, and a size that doesn't break the view of the person using the same tab in Rex.

Rex documents no live stream of a tab's output that the bridge can use. Its API has `data.connect`, which issues a ticket for a WebSocket to `/api/data` with the subprotocol `rex.data.terminal.v1`, but the framing after the ticket (the HELLO message, REJECT codes, what the stream carries) isn't documented, and `rex block stream`, the CLI's wrapper for it, prints "not implemented" in the installed Rex (0.0.1793741575, API revision 10, checked 2026-11-04). A third-party client (github.com/leizhiyuan/rexpocket) reverse-engineered it; building on that would be guessing. The documented ways to read a tab, `format` and `rex capture`, return the whole screen and scrollback each time: there is no event when output changes, so the bridge would poll, and a tab with 20,000 lines of output already passed Rex's 1 MiB reply limit in a live check. Repainting the room's view from snapshots every second is screen scraping, and it would cost the Rex server a full render per poll.

So a shareable Rex tab runs `uplink-bridge rex-host`, and the program the person wants runs under it, on a pty that `rex-host` opens (node-pty, the same as every bridge terminal). `rex-host` passes everything through: the program's output goes to the tab, and the person's keys and the tab's size go to the program, so the tab works in Rex as any tab does. It also connects to the bridge over the bridge's private local socket. While the bridge shares the tab, `rex-host` sends it the output and takes the room driver's input. Everything else is Rex's documented CLI: listing sessions and tabs (`rex ls`, `rex window ls`), opening a tab (`rex new`, `rex window new`), resizing (`rex block call … resize`), closing (`rex block close`), and the tab's program status (`rex events`, `program_status`). Every call passes `--autostart=false`, and `-S` when `REX_SERVER` is set: with only the variable, the CLI goes on to the computer's own Rex server when the named one is gone (seen in the live check), and the bridge must not act on a server it wasn't set up for.

We chose a pty inside the tab over one inside the bridge (with the tab running a viewer that attaches to it). A tab's program lives as long as the tab, as it does everywhere in Rex: quitting Uplink Room, which stops its bridge, doesn't end the person's tabs, and closing a tab or quitting Rex ends its program as it would without us.

## How it works

- **Finding tabs.** A tab whose `rex-host` is connected can be shared; the bridge reports those in `rex_found`, with their session and tab labels from Rex. Tabs opened in Rex directly can't be (there is no stream), so the bridge reports only how many there are, and none of their names or folders leave the machine. People open a shareable tab with `uplink-bridge rex-open -- COMMAND`, or by running `uplink-bridge rex-host` in a tab, and runs the room starts In Rex are shareable from the start.
- **Sharing.** Only whoever the machine belongs to (an admin, for a team machine) shares a tab: `rex.share` in the room, or `uplink-bridge share-rex TAB` on the machine. It becomes a terminal with the usual access, driver and wheel rules, clamped to the machine's most open access, and uses no slot. Ending the share (`rex.stopSharing`, `stop_terminal`, stopping sharing, unlinking, the bridge closing) never ends the program: `rex-host` only stops sending output.
- **Runs In Rex.** `runs.start` with `via: "rex"` opens a new tab in the "Uplink Room" session on the machine (made when missing), without taking focus, in the run's folder, with Rex's `--interactive` so the program finds what the person's own tabs find on PATH. The harness starts with its first prompt on its command line. It is a room-started terminal: it uses a slot as any does, and stopping it, stopping sharing or the bridge closing ends its program, and its tab closes.
- **Size.** The program always has its tab's size. The driver's resize goes to Rex's `resize`, which applies at once only when no Rex app has the tab open (it then follows the app, its owner); the bridge reports the size Rex gives the tab (`terminal_size`), and the room's view draws at that size. The person at the machine never sees their tab redrawn for someone else's window.
- **Terminal replies: Rex answers.** When a program queries its terminal (device attributes, cursor position), the Rex server answers on the tab's input itself, with or without a Rex app open: a throwaway Rex server with no client attached answered `ESC [ c`, `ESC [ 6 n` and `ESC [ > c` with `ESC [ ? 62 ; 22 c`, `ESC [ 1 ; 1 R` and `ESC [ > 1 ; 0 ; 0 c` (Rex 0.0.1793741575, 2026-11-04; Rex's docs don't say). The room's screen, drawn by xterm.js, answers the same queries when someone has the terminal open, so the program would get two answers, the second landing as stray input. Rex is the one responder for a Rex tab: its answers come from the tab the program really draws on, at the tab's real size, and they're there whether or not anyone watches in the room. The bridge drops only the room screen's automatic replies (the input the room marks `reply`, in the exact shapes `terminalReplies.ts` lists, from #115); anything typed, from Rex or the room, always passes, even a key shaped like a reply (Shift+F3 sends what looks like a cursor position report).
- **Status and approvals.** A shared or started tab's run state is its Rex program status, followed on the tab's own block without any target to configure. The status snapshot (`program_status`) is taken once `rex events` is live (its first line is its own `client_connected`), so a status reported before the stream started is in the snapshot, and one after it comes through the stream. Rex's program-status protocol has no way to send an answer back ("The only bytes a terminal writes back are the feature detection reply"), so a blocked tab is a question that says to answer it in the terminal, with no Allow or Deny.
- **Old bridges and old rooms.** The room offers In Rex only for a bridge whose `tools` list `rex-tabs`, which older bridges never send. A bridge sends `rex_found` and `terminal_size` only after the room's `room_features` lists `rex`, since a room from before them refuses a message it doesn't know, and with it the whole batch.

## Consequences

- A tab opened in Rex directly can't be shared live. To share running work, the person starts it again in a shareable tab. This is the one thing a documented Rex output stream would change: when Rex documents `/api/data` or ships `rex block stream`, the bridge can share any tab, and this decision should be revisited.
- Rex tabs are shared on macOS and Linux only. Rex's public builds are the macOS app and the Linux and FreeBSD server (its installation page, checked 2026-11-04); its Windows server isn't public, so a Windows bridge never reports `rex-tabs`.
- When the bridge restarts, a run it started In Rex has already ended with it. A tab the person opened keeps running and connects again; it is shareable again but unshared.
- A shared tab's room view starts with the tab's last 256 KiB of output, and its program gets one resize so a full-screen program draws its screen again.
- A run In Rex uses the machine setup, never a profile: Rex starts the tab with its own environment, where a profile's logins can't be kept apart from the machine's (#18).
