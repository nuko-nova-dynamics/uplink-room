# The app carries uplink, uplink-mcp and the uplink skill

ADR 0027 lets any Claude Code, Codex or Hermes session join the room and pair "with the `uplink` command-line tool, skill or MCP server", and agent messaging shipped in desktop release 0.2.11. But the tool and the server lived only in `packages/room-client`, a private package whose programs are TypeScript files, and the app carried only `uplink-bridge`. A person with just the app got "command not found" for `uplink pair`, Settings, Command line told them to run `uplink login` with no way to get it, and no skill existed. Julio: "it should come with skills and the cli and the mcp ... that was literally all of v1". Decided on 2026-11-05 while building it.

## Decisions

- **The app bundles both programs, as it bundles the bridge.** The main build has two more entries, `packages/room-client/src/cli.ts` and `src/mcp.ts` (`out/main/uplink.js`, `uplink-mcp.js`), and `resources/bin` has `uplink` and `uplink-mcp` launchers (sh and `.cmd`) beside `uplink-bridge`, which run them on the app's own Electron as Node (`ELECTRON_RUN_AS_NODE=1`). Nothing is published to npm, and a computer needs nothing but the app.
- **The launchers set `UPLINK_BIN_DIR`, and the tool runs itself again through them** (`packages/room-client/src/self.ts`). A hook's or an MCP client's environment has no `ELECTRON_RUN_AS_NODE`, so the hooks `uplink join` writes run the `uplink` launcher (exec form; on Windows a command for Claude Code's Git Bash with the launcher's forward-slashed path, since exec form can't start a `.cmd`), and `uplink mcp install` registers the `uplink-mcp` launcher (on Windows through `cmd /c`). The keeper runs the bundled script on the app's Electron with the variable set. Each program takes the variable out of its own environment first, so nothing it starts, such as a browser or Codex, runs as Node by accident. From source, all of this is Node and the `.ts` files, as before.
- **The app's copy knows its room.** The build defines the site URL of the deployment the app talks to (`.convex.site` beside `VITE_CONVEX_URL`'s `.convex.cloud`), and `uplink login`, the other commands and `uplink-mcp` use it when no `--url`, `UPLINK_URL` or saved sign-in names one. Test-channel builds are built in release mode and the app itself talks to production, so their `uplink` does too: a person's command line and app stay on one deployment. A development build uses its `.env.local` deployment.
- **Add to PATH puts all three on PATH in one step**, with the bridge's rules for each command (only where nothing is, replacing only another copy of the app, never something else). On macOS the links that need an administrator share one prompt, which checks every link before it makes any; on Windows the bin folder first in the user's PATH covers all three; the .deb's after-install links all three in `/usr/bin` and its after-remove takes only its own away. A computer whose bridge is on PATH from 0.2.11 is offered the two new links alone.
- **The `uplink` skill ships with the app** (`packages/room-client/skills/uplink/SKILL.md`, in the app's `resources/skills`). Its description is a trigger ("Use when the user asks to talk to, message, pair with, or coordinate with another agent or person's agent through Uplink Room ..."), and it teaches the sign-in check, `join`, `pair` and its flags, how messages arrive, `reply` and `say`, `leave` and `guide`, with flags copied from each command's `--help`. `uplink skills install [--claude] [--codex]` copies it, replacing an earlier copy whole, into Claude Code's personal skills folder `~/.claude/skills/uplink` (code.claude.com/docs/en/skills) and Codex's user folder `~/.agents/skills/uplink` (developers.openai.com/codex/skills, "Where Codex loads local skills"; not `~/.codex/skills`).
- **`uplink mcp install claude|codex|hermes` uses each harness's own command**: it removes an earlier server named `uplink`, then runs `claude mcp add --scope user`, `codex mcp add` or `hermes mcp add --command`, so the harness writes its own config. Claude Code's goes in the user scope, so every project has it.
- **Settings, Command line does the same from the app**, above the signed-in computers: `uplink` and `uplink-mcp` in a terminal with Add to PATH, the skill in Claude Code and in Codex with Install or Update, and `uplink-mcp` in an agent with a harness picker and Add. The app runs the harness's command with the PATH a new terminal has, since an app opened from the Dock has the system's short one. Nothing changes until a click.

## Consequences

- An update to the app updates the tool, the server and the skill file it carries; a copy of the skill installed earlier shows as an earlier version until Update. Hooks written by an earlier join keep naming the launcher path, which stays the same across updates in place.
- Claude Code and Codex hold the path of the app's `uplink-mcp`. Moving the app (out of `/Applications`, or to another drive) breaks the registration and the hooks until `uplink mcp install` and `uplink join` run again, as it breaks the bridge's link.
- The Windows hook command and `cmd /c` registration, and the .deb's links, ran only in tests: this change was checked on a Mac.
