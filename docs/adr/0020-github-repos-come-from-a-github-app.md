# GitHub repos come from a GitHub App the team installs

Until now a project's repos were free text. Julio asked for a way to add a GitHub organization and personal GitHub accounts, sync their repos, and start and link projects from them (2026-11-04). He decided on a GitHub App, not an OAuth App: a team admin installs the room's App on an organization or on their personal account and picks all repos or some, and the room syncs the repos it was given and keeps them current with webhooks.

We chose an App over an OAuth App because an App's access belongs to the installation, not to a person. The account's own admin picks the repos, the permissions are fine-grained, and the App hears about installs, repo changes, renames and uninstalls. An OAuth App's token is one person's and reaches everything that person can.

Later the same day Julio widened who connects: "the admin of the organization can add a github organization so the team can work on it. Also, the users as well, if they want, can add their own repos with github, and all synced." So organizations stay with team admins who own them on GitHub, and any person in the team can connect their own personal account. Its repos are the team's to pick, as an organization's are, because the person chose to share them by connecting. Agents connect nothing. See "Who manages a connected account" below.

## What the App asks for

- **Metadata: read**. It is the one permission every App has, and it is all that `GET /installation/repositories` needs. The room stores each repo's GitHub id, full name, whether it's private or archived, and its default branch. It reads no code, issues or pull requests.
- **Members: read** (an organization permission), for two calls that check the connecting person owns the organization (below): `GET /user/memberships/orgs/{org}` with their token at the callback, and `GET /orgs/{org}/memberships/{username}` with the installation's token at Confirm. GitHub's [permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps#organization-permissions-for-members) lists both under "Members", the second as read for user and installation access tokens (UAT, IAT), and [Get organization membership for a user](https://docs.github.com/en/rest/orgs/members#get-organization-membership-for-a-user) gives its `state` (`active`, `pending`), `role` (`admin`, `member`, `billing_manager`) and `user.id`. Without the permission the room couldn't tell an owner from someone who reads one repo. The room makes no other call that uses it, and never reads member lists.
- **Events**: `repository`, which needs Metadata: read ("Webhook events and payloads"). Apps receive `installation` and `installation_repositories` without subscribing. GitHub says Apps don't receive `repository.deleted`, and `installation_target` (an account renamed) isn't marked as delivered by default, so the room doesn't rely on either: a full sync of every account runs daily, and it renames and drops repos by GitHub's id.
- **Any account** can install it (`public: true` in the manifest). A private App installs only on the account that owns it, and the team needs it on organizations and on each person's personal account. Installing it does nothing until someone connects that installation to a team through the flow below.
- **No "Request user authorization (OAuth) during installation".** With it, GitHub drops the Setup URL and starts its own authorization without the room's state or PKCE ("Registering a GitHub App", step 13; "Generating a user access token", "when a user installs your app"). The room runs the web application flow itself instead.

## Connecting an account

A connected GitHub account is an installation linked to one team. GitHub warns that anyone can call the Setup URL with a made-up `installation_id` ("About the setup URL"), so the id it carries is only a claim.

1. A person chooses Connect. `github.connect` (people only: an agent's call is refused, whatever its scopes and role) stores a connect row: a random nonce (as a SHA-256 hash), the team, the person, their role then (`starterRole`), a PKCE verifier, and an expiry 30 minutes out. It returns `https://<deployment>.convex.site/github/connect?state=<nonce>.<signature>` and the connect's id. The signature is an HMAC over the nonce, team, person and expiry, with a key derived by HKDF from the App's client secret. Each check recomputes it from the row, compares it in constant time, and checks the expiry in the action. What the person may connect isn't fixed here: each step reads who they are then (`starterNow`). An admin may connect an organization they own and their own personal account; a member, only their own personal account. Someone who has left the team, an agent (a flow an agent started before agents were refused), or an admin who has stopped being one connects nothing, and `/github/connect`, the Setup URL and the callback each answer with a page that says so.
2. `/github/connect` keeps the state in a `__Host-` cookie (HttpOnly, Secure, SameSite=Lax, 30 minutes) and redirects to `github.com/apps/<slug>/installations/new`. GitHub documents `state` for the authorize step only, not for the install page, so the cookie carries the flow across GitHub's pages. The state also goes on the install URL, and the Setup URL accepts it from there if GitHub passes it back.
3. GitHub sends the person to the Setup URL (`/github/setup`) after an install, and after a change of repos ("Redirect on update"). With a live flow, the room records the claimed installation id and redirects to `github.com/login/oauth/authorize` with the client id, the callback's `redirect_uri`, the state and an S256 `code_challenge`. Without one, the page says it can't tell which team the install is for, or, after an update, that the room picks up the change on its own. A `setup_action=request` (an organization member asked an owner to approve) gets a page saying so.
4. The callback (`/github/callback`) checks the state from its query, as GitHub's docs ask ("If the state parameter does not match the state parameter that you sent in the previous step, the request cannot be trusted, and the web application flow should be aborted", "Generating a user access token for a GitHub App"). It trades the code for a user access token with the client secret, the same `redirect_uri` and the PKCE verifier, then asks GitHub who the person is (`GET /user`) and which of the App's installations they can access (`GET /user/installations`, every page up to 1,000). The token is then dropped: the room stores neither it nor its refresh token. The flow keeps the list of installations GitHub returned and the GitHub login and id of whoever signed in.
5. Being able to access an installation isn't the authority to share it. GitHub lists an installation to anyone with read access to one of its repos, and connecting it syncs every repo it gives, private ones included. So, while it still holds the token, the callback decides for each listed installation whether this GitHub user may give the team all of it:
   - **an organization**: only in a flow a team admin started, and only if GitHub says the GitHub user is an active owner (`GET /user/memberships/orgs/{org}` answers `role: admin`, `state: active`). A member, an outside collaborator, a pending invitation, or an organization that wants a SAML session first (403) is refused. At most 25 organizations are checked on one page, the claimed one first. In a flow a team member started, no organization is asked about: each is refused as "Only an admin of <team> can connect an organization".
   - **a personal account**: only if the account is the GitHub user (`GET /user`'s id is the account's id), in a flow anyone in the team started.
   We chose refusal over linking only the repos the person can see (`GET /user/installations/{id}/repositories`): that list would go stale as the installation's repos change, and keeping it current would mean keeping the person's token. An organization's non-owners ask an owner to connect it.
6. The browser part ends at the callback, and it links nothing. Its page says to return to Uplink Room: "GitHub signed you in as julio, and the Uplink Room App is installed on nuko. Julio started this in Uplink Room and confirms it there, in Settings, then GitHub. Nothing is connected to Nuko Nova until then. If you aren't Julio, you can close this tab." When the account the page was opened for is already connected or can't be connected, or nothing GitHub listed can be, the page says so instead and the connect ends there. The page has no form, and its policy allows none (`form-action 'none'`).
7. In the app, Settings, GitHub shows the connect under Finish connecting (`github.connects`, the person's own connects only): first the GitHub user who signed in, then each account GitHub listed, with Connect on those the person may connect and, on the others, why not. `github.confirmConnect` is a Room API mutation, so it runs as the person signed in to the app. It refuses an agent, anyone but the person who started the connect, a connect that expired, was cancelled or already finished, one from before Confirm moved into the app, and one an admin started who is no longer an admin. An organization also needs the person to be an admin now. It then records the choice (`confirming`) and schedules the check below. Cancel (`github.endConnect`, the starter only) ends a connect, so nothing can be connected from it.
8. What the callback learned can be minutes old by then: an owner can be demoted, or the App uninstalled, before the person chooses Connect. So the check (`githubConfirm.check`, an action) asks GitHub again, as the App, since the user token is gone. It reads the installation (`GET /app/installations/{id}`, the App's JWT) and requires the same account. For a personal account, that account must still be the GitHub user (the id kept from the callback's `GET /user`). For an organization, it mints an installation token and asks `GET /orgs/{org}/memberships/{username}` for the login kept from the callback, and requires `state: active`, `role: admin` and the same `user.id`. A suspended installation can't get a token, so it can't be connected until it's unsuspended. Then `github.confirm` checks the connect and its starter again in its transaction: still the Connect this check was for, not expired or cancelled, the starter still a person in the team, still an admin if they started as one, and an admin for an organization. Only then does it link the installation, as connected by the person who started the connect, and start the first sync. The connect is then used and can't be replayed. If GitHub or the room says no, or GitHub doesn't answer, nothing is linked, the account's row in the app says why, and the person can choose Connect again until the connect expires. A check that hasn't reported back after 2 minutes has died; Connect can be chosen again, and the dead check's late report, which carries the time of its Connect, changes nothing.

**Why Confirm is in the app.** The browser knows which GitHub user signed in, never which person in the room is at the keyboard: a Connect link works for whoever opens it. Until Codex's review of PR #131, Confirm was a button on the callback's page, and the connect was linked as connected by whoever started it. So a link Bo started and Ana finished connected Ana's personal account as Bo's: Bo could sync it and change its repos, Ana couldn't, and removing Ana from the team left it connected. An admin's link, forwarded, let an owner of an organization who isn't a team admin finish connecting it. With Confirm in the app, signed in, only the person who started a connect links anything, and the app shows them which GitHub user signed in before they choose.

What stays possible is narrower: the starter can confirm an account someone else signed in for on GitHub, once that person finished the starter's link there. The app names that GitHub user first, its hint says to cancel when it isn't you, and the browser page tells whoever finished the link that only the starter confirms it. For an organization this is intended: an admin who doesn't own one on GitHub sends an owner the link, the owner installs the App and signs in, and the admin confirms in the app. The ownership check uses the owner who signed in, at the callback and again at the check.

The same installation can be connected to more than one team. Each team gets its own row and its own copy of the synced repos, and webhooks update every copy.

## Who manages a connected account

The server decides each of these from the actor (`mayDo` in `github.ts`), for the mutations and for what `github.accounts` offers. The UI only shows what it is told.

- **An organization is the team's.** Admins connect it (as owners on GitHub), sync it, change which repos it gives and disconnect it. A member can do none of these.
- **A personal account is its person's**: the one who connected it (`connectedBy`). They sync it, change which repos it gives and disconnect it. An admin can only disconnect it, to take its repos away from the team, and can't sync it or change its repos.
- **Change which repos** is GitHub's page for the installation, where GitHub lets only the account's owner change it ("Organization owners can change the repository access for an app installed on their organization", "Reviewing and modifying installed GitHub Apps"). So the room hands that link (`settingsUrl`) only to whoever may change the repos: admins for an organization, the person for their own account. `canSync`, `canChangeRepos` and `canDisconnect` on each account say the rest.
- **Agents** connect nothing. An agent's effective role (never above its person's, and with `team.admin` on its key) lets an admin agent sync and disconnect organizations and disconnect personal accounts, as before; it owns no account. Agents' reads (`github.accounts`, `github.repos`, `github.repoStatus`) are unchanged.
- **Leaving the team.** `members.remove` disconnects the personal accounts the person connected (and any their agents connected), as any disconnect does: their repos leave the pickers, projects keep their strings and show them as not connected. Organizations they connected stay, since they're the team's. A connect they started links nothing after they leave, even one whose check with GitHub was running when they were removed. Uninstalling the App on GitHub stays the person's own business, and Settings and the removal dialog say so.
- **Settings, GitHub** groups the accounts: Your account, Organizations, and, for admins, Other people's accounts, each with a line on who may do what. A member doesn't see other people's personal accounts there, though `github.accounts` still lists every account to every member and agent with `room.read`, and the repo pickers offer every account's repos.

## Keeping repos in sync

- **Webhooks** (`/github/webhook`) are checked against `X-Hub-Signature-256`: an HMAC-SHA256 of the raw body with the webhook secret, compared in constant time ("Validating webhook deliveries"). Each delivery is applied once. Its `X-GitHub-Delivery` id is recorded in the same transaction as the change, so a redelivery of an applied delivery changes nothing, while one that failed is applied when GitHub sends it again. Deliveries are kept 7 days.
- `installation`: `deleted` removes the account. `suspend` marks it, and its repos stay listed, marked, until it's unsuspended (then a sync) or uninstalled. `new_permissions_accepted` syncs. If one of these webhooks is lost, the daily sync catches it: it visits suspended accounts too, and a sync asks GitHub for the installation before reading repos.
- `installation_repositories`: adds and removes repos by id, for each team that connected the installation in its own mutation (the first with the delivery, the rest right after), since 100 changes times every team would pass a mutation's limits. Over 100 in one delivery, or a switch to all repos (which lists none), syncs the account instead. Added repos come without a default branch or archived flag, so a sync follows.
- `repository`: `renamed`, `archived`, `unarchived`, `privatized`, `publicized` and `edited` (default branch) update every synced copy by GitHub's id, 50 copies a batch. A transfer reaches only the new owner's installation. Each copy under another account is renamed in its team's projects first, then removed, so projects follow the repo even in a team that never connected the new owner. A team that connected both accounts gets the repo under the new one, and its projects keep their links. `created` and `transferred` add the repo to installations with all repos that lack it, and others sync.
- **Webhooks and syncs both write the synced repos, and either can arrive late.** A sync page can leave GitHub before a rename or a removal and reach the room after its webhook. So a webhook stamps what it changes (`webhookAt`) and leaves a tombstone for what it removes (kept a day), and a sync page carries when the room asked GitHub for it (`fetchedAt`). A page older than a webhook's change leaves that repo alone: it neither brings a removed repo back nor reverts a rename. A tie goes to the webhook. A sync that started before the account's latest webhook (`lastWebhookAt`) doesn't finish as synced; another sync starts and reads GitHub again.
- **The daily sync** visits every connected account, 200 a batch until all are done, and spreads their syncs over five minutes.
- **A sync whose action dies** (a timeout or a crash) reports nothing and stays "syncing". Fifteen minutes after it started, it counts as not finished: Settings says "Sync didn't finish" and enables Sync now, which starts a new generation (`github.accounts` gives `syncStaleAt`), and the daily sync restarts it too. Convex gives an action up to 30 minutes in the default runtime and one step takes seconds, so an old step could in theory still be running. Its pages, finish and failure carry the old generation and change nothing.
- **A sync** (`githubSync.run`, an action) makes a JWT for the App (RS256, `iss` the App ID, `iat` 60 seconds back, `exp` under 10 minutes), trades it for an installation token, reads the installation itself (its account's name and picture, all repos or some, suspended or not), and pages `GET /installation/repositories` 100 at a time, 10 pages per step. Each sync has a generation. Every page carries it, the sync deletes its account's repos it didn't see, and a page or result from an older sync or after a disconnect changes nothing. A 404 for the installation means it was uninstalled while the room missed the webhook, so the account goes as on an uninstall.
- The room signs the JWT with Web Crypto in Convex's default runtime. GitHub's private key download is PKCS #1, which Web Crypto doesn't import, so the room wraps it as PKCS #8, and the registration script stores it as PKCS #8 already.

## Projects and repos

Projects keep their repo strings, so `projects.list`, runs and unfiled-run suggestions work as before. A synced repo's string is `github.com/<owner>/<name>`, and so is a repo typed as a bare `owner/name`: `normalizeRepo` adds GitHub's host, because the bridge matches a run's repo against T3 Code's repository keys, which have it. Only a bare `owner/name` gets it: a remote that names its host with a scheme, `user@` or `host:` keeps that host, so `git@gitbox:payroll.git` is `gitbox/payroll`, not a GitHub repo. When a project lists a string that is a synced repo, the room also keeps a link by GitHub's id (`projectRepoLinks`, with the repo's key): on `projects.create` and `projects.setRepos`, and when a sync or a webhook brings a repo a project already lists. A rename on GitHub finds projects through those links, not through the old string, and swaps the old name for the repo's current one.

Each link keeps the name its project lists, so a rename job brings every link's name up to date, whatever it was. That covers links a disconnect kept: when a reconnect brings the repo back under a new name, its insert starts a rename job for the team. And the job that links a new repo carries the name the repo had when it was found, so a rename that lands before the job reaches a project still renames that project; the rename job had no link to follow yet.

Both of these grow with the team, so they run as scheduled batches that continue until done, on team-scoped indexes: a rename reads 50 links a batch, and linking new repos reads 25 projects a batch for up to 100 repos. A project lists at most 200 repos (`projects.create` and `projects.setRepos` refuse more, and say so), which bounds what each batch reads. Matching ignores case and spelling (`repoKey`), so `Nuko/Billing`, `github.com/nuko/billing` and `https://github.com/nuko/billing.git` are one repo. Unfiled-run suggestions now compare the same way.

A disconnect or an uninstall takes the account's repos out of the pickers, in batches. Projects keep their strings, and the repo picker shows those as not connected. Projects aren't rewritten.

## Consequences

- Every member sees the connected accounts and the names of the synced repos (`github.accounts`, `github.repos`, `github.repoStatus`, all `room.read`). Admins connect and manage organizations; anyone in the team connects and manages their own personal account, which an admin can disconnect (above). Agents reach the same functions through the Room API, so an agent with `room.read` can find a repo to start a run in, but can't connect anything.
- The schema change for members' accounts is additive: an index on `githubAccounts.connectedBy`, used to find a person's accounts when they leave. `githubConnects.agentKeyId` stays for the rows agents started before they were refused.
- Queries are bounded: an account list reads at most 200 rows, a repo search reads at most 200 candidates from the search index (`searchText`, the name's words) and returns 50, a status check takes 100 strings (the picker asks in batches of 100, and a batch that fails leaves its repos without a status), and deletes and sweeps go 500 rows per mutation. A search with a slash, such as `nuko/uplink-ro`, reads the key index from that prefix instead, so a repo is found however many share its owner's words.
- The deployment needs `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_WEBHOOK_SECRET` and `GITHUB_APP_PRIVATE_KEY`. `packages/backend/scripts/github-app.ts` registers the App with GitHub's manifest flow, exchanges the code (`POST /app-manifests/{code}/conversions`) and pipes each value into `npx convex env set` without printing it. Without them, Settings says GitHub isn't set up, as for shared browsers (ADR 0006).
- Installing the App somewhere does nothing for a team on its own: only a connect its starter confirmed in the app links an installation.
- A person's GitHub identity isn't tied to their room identity: the callback checks that a personal account is the GitHub user who signed in, and the app checks that whoever confirms is the person who started the connect. Nothing ties the two together beyond the starter seeing the GitHub login before choosing Connect (above).
- The schema changes for Confirm in the app are additive: on `githubConnects`, `starterRole`, `confirming`, `refusal`, `connectedLogin`, `endedAt`, each listed account's `refusal`, and an index by person (`by_member`). `confirmTokenHash` stays for rows from before. Links and pages from before the change connect nothing: a connect without `starterRole` gets "Connecting now finishes in Uplink Room" at `/github/connect`, the Setup URL and the callback, the app can't confirm it, and `POST /github/confirm`, the old page's button, always answers with that page (410). Such connects expire within 30 minutes of the deploy anyway.
- The first sync against the real App is the live check still to run. Tests cover the flow against a fake GitHub that checks the JWT's signature, PKCE, the redirect URI, the user's installations and their organization roles, and the HTTP routes and webhooks ran on a local Convex backend.
- Codex's first review (PR #116) found the ownership check, the agent recheck, late sync pages, transfers, the batching and the owner/name search. Its second found links a disconnect kept through a rename, a rename that lands before linking, and one delivery applied for every team in one mutation. Its third found the daily sync stopping at 1,000 accounts, no way to restart a stalled sync from Settings, and hand-typed `owner/name` repos that a thread run couldn't find. The last round found Confirm trusting an ownership answer from the callback, explicit non-GitHub remotes read as GitHub repos, and suspended accounts the daily sync never rechecked. Its review of PR #131 found that the browser's Confirm bound the GitHub user but not the person in the room (above). Each has a test with its trigger in `tests/github.test.ts` or `tests/repos.test.ts`.
- Known limit: a deferred `installation_repositories` removal (the per-team mutation that runs right after the delivery) can land after a newer sync page or webhook and remove a repo that brought back, since it applies the delivery as of when it arrived. It takes that narrow race, and the daily sync puts the repo back within a day.
