# A joined run acts with its own token, and hears through hooks its join adds

ADR 0027 lets any Claude Code or Codex session join the room by itself as its signed-in person, and ADR 0029 decided its token (D8) and that a joined run without a team can only pair (D13). Building it (slice 10 of #139) needed choices those left open: what proves the run on each call, what keeps it live and ends it, and how a session with no bridge hears its messages. The #138 delivery tests settled the last one: Claude Code drops a custom channel without its development flag, and a hook added to a settings file mid-session is picked up without a restart. Decided on 2026-11-05 while building slice 10.

## Decisions

- **A joined run is a `runs` row marked `joinedSessionId`, with no machine, terminal or thread.** Its driver is the person's member, so it is named, numbered and mentioned like any run ("Claude Code (Pepe)"), and every rule of slices 1 and 2 applies to it. It reports no state: it shows Unknown while live, so it sits in Working and the roster's running harnesses and never in anyone's Needs you (D13), and Done when it ends (Stopped when someone stops it). Amended by ADR 0044: it starts closed, so only its person and their agents see it, until its person opens it (`uplink join --open`, `uplink open`).
- **Each join gets a run token, `urj_` and 48 hex characters, stored only as its SHA-256** in `joinedSessions` with the CLI sign-in it was made with and the harness's session id (Claude Code's `session_id`, Codex's thread id). The person's sign-in is used once, by `joined.start`, an account function. After that the session's hooks and commands use only the run token, which reaches only the run functions (`realm: "run"`, `joined.*`): take its waiting messages, post as the run, send its heartbeat, leave. Every other function refuses it, and run functions refuse sign-ins and agent keys. The token stops working when the run ends, when its sign-in is revoked or expires (which also ends the run), or when the person leaves the team (the run then ends when its heartbeat stops). The same session joining again in the same team keeps its run with a new token; in another team its old run ends.
- **Liveness is stored, never computed from the clock in a query.** Convex reruns a query only when a document it read changes (docs.convex.dev, best practices, "Don't use `Date.now()` in queries"), so the run is live until `endedAt` is written: by `joined.leave` (`uplink leave`, or Claude Code's `SessionEnd` hook), by `runs.stop`, by the sign-in's end, or by `joined.expire`, which runs at the last heartbeat plus two minutes and waits again while heartbeats come.
- **A keeper process holds the session's liveness.** `uplink join` starts `uplink joined-keeper` detached. It sends `joined.heartbeat` every 30 seconds, keeps a live watch on `joined.waiting` and writes the count to a local file, and ends the run when the harness process it found among `uplink join`'s parents exits. It finds that process in the system's process list on every platform: `ps` on macOS and Linux, one snapshot of `Get-CimInstance Win32_Process` on Windows. When it finds none, the keeper ends the run 12 hours after the join, and the join says so. The hooks read the count, so a tool call with nothing waiting costs no call to the room.
- **Only the session acts as itself.** A harness variable (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`) or a hook's `session_id` only names a session, and any program of the same person can set one. So `uplink inbox`, `say`, `reply`, `leave`, the hooks and `uplink-mcp --channel` act as a session only from a process whose parents, read from the process list, include the harness process its join recorded. The bridge (#145) checks a per-terminal secret in the terminal's environment instead, since its local socket can't tell which process connected.
- **Claude Code hears through hooks the join adds to the project's `.claude/settings.local.json` by default**, the person's own file for one project, where Claude Code reads it (code.claude.com/docs/en/settings): at the repository root in a git repository, the main checkout's for a worktree, and in the session's primary working directory (the folder Claude Code started in, read from its process) outside git, on Windows, when the root is the home folder, or when the root isn't the person's. A file the join makes is added to the repository's `info/exclude`, since only a file Claude Code makes is kept out of git for it. `PostToolUse`, `PostToolUseFailure` and `UserPromptSubmit` return waiting messages as `additionalContext` during a turn. `Stop`, `StopFailure` (which Claude Code fires instead of `Stop` when a turn ends in an API error) and `SessionStart` run a waiter with `asyncRewake` and a 7-day timeout, as the bridge's waiter does (#144): only the newest waiter waits, and it exits 2 with the messages when one comes while the session is idle, which wakes it. A hook with `agent_id`, from a subagent, does nothing. A session started with `--setting-sources` that leaves out `local` gets the hooks in `.claude/settings.json` in its primary working directory instead, where Claude Code reads the shared file, and the join says so. Each hook runs `uplink` in exec form and finds the run token by the hook's `session_id`, so no credential is written into settings. A hook group stays in a file while any joined session records it there: joining again takes out the earlier join's groups the new one doesn't keep, and `uplink leave` takes out its own, except those another joined session uses. Joins and leaves of one file take turns under a lock beside it, and each write replaces the file whole.
- **A Claude Code channel is opt-in.** `uplink-mcp --channel` declares `claude/channel` and pushes the joined run's messages as `notifications/claude/channel`. `uplink join` uses it instead of the delivery hooks when that server announced itself for the session and the session's `--dangerously-load-development-channels` names it (`server:<the name Claude Code's MCP config gives a server running uplink-mcp --channel>`), or when given `--channel`. Only the `SessionEnd` hook is added then.
- **Codex hears through its app server**, as #138 test 2 did: the keeper steers a running turn with `turn/steer` and queues for an idle session with `codex queue --resume`, over the control socket in the person's Codex home. Without that socket (Codex started with `--no-daemon`) nothing delivers, and the session reads `uplink inbox`.
- **Any other agent joins with `--harness <name>` and reads its own inbox**: its join instructions tell it to run `uplink inbox` after each step, and the keeper still ends its run with its process.
- **`runs.hearing` says which**, with its meaning unchanged: `mid_task` for Claude Code hooks and Codex, `between_turns` for a channel, `none` for a session that reads its inbox itself.
- **A message is delivered once the session has it.** `joined.take` claims the messages it hands out, and `joined.ack` delivers them once they are in front of the session: a hook's output written, a waiter's wake text written, `uplink inbox` printed, a channel notification sent, Codex's steer or queue done. `joined.release` puts back what couldn't be. A claim nobody answers within two minutes waits again once, then fails as `unsure`, with the same `runInbox` fields as the bridge's claims (#144). Codex and channel delivery go on until nothing waits, and retry a failure after a pause that doubles from 1 to 30 seconds.
- **A joined run posts as its driver with `asRun`** (D2), through `messages.post`'s checks (`postMessage`), as `bridge:runSay` does for a run in a bridge terminal: `uplink say --in <place>` or `uplink reply <messageId>` (D5).

## Consequences

- Until pairs exist (slice 11), `joined.start` without a team is refused with a message saying so. `joinedSessions.teamId` and `runId` are optional, so a teamless join needs no new token.
- While a session of a project is joined, every Claude Code session in that project runs the hooks; a session that hasn't joined gets nothing from them.
- Any process the session's harness started can still act as the session, such as a command the agent runs or a program that command starts, and a join that found no harness process is taken by its session id alone. On Windows a process whose parent exited keeps that parent's id, which Windows may give a new process.
- Codex's app server outlives the TUI that started it, so a Codex run ends with the `codex` process `uplink join` found, which may be the app server.
- In Claude Code's auto mode, the permission check can block `uplink reply` and `uplink say` as writes to an outside system; the person allows them with a permission rule.
- A process that dies after it wrote a message for the session but before `joined.ack` gets that message once more, two minutes later.

## Verified

On 2026-11-05, against a local backend running this code, the development Clerk instance and a `+clerk_test` user deleted afterwards, Claude Code 2.1.318 on Haiku 5.5 in a scratch folder ran `uplink join` itself. With `--setting-sources project` the hooks went in `.claude/settings.json`; the `Stop` hook the join added fired at the end of that same turn, and a message posted while the session was idle woke it about half a second later (`next_turn`). A message from its driver posted during a 25-second foreground build reached it as `PostToolUse` `additionalContext` after the build, inside the same turn (`mid_task`). The run stayed live past the two-minute timeout on the keeper's heartbeat, the session answered with `uplink reply` and `uplink say` (stored under its person with `asRun`), and `uplink leave` ended the run, deleted the settings file it had made, and stopped the keeper and the waiter. A second session with `--setting-sources project,local` got its hooks in `.claude/settings.local.json`, was woken the same way, and quitting Claude Code ended its run (`session_ended`) and took the hooks out. The Codex path and the channel ran only in tests.
