# Decision for #10: persistent team machines, started on demand

Prepared for Julio, 2026-11-02. **Decided by Julio on 2026-11-02 as recommended: persistent team machines on Vercel Sandbox Pro in `iad1`, Linux, started on demand.** Built in ADR 0013.

## Decide in a minute

**Start with Vercel Sandbox Pro in `iad1` for Linux, keeping each box a team machine with its existing settings and machine-bound profiles.** Start it when a terminal needs it; stop it after 15 minutes with no live work. Preserve its disk and room identity, but restart the bridge on each boot. A stopped machine is not a suspended run.

Why: explicit US East placement, filesystem persistence, and no $150/month sandbox plan fee. At 2 vCPUs/4 GB and 10% average CPU use, estimated compute is **$0.1104/hour** before credits, storage and transfer. This is an estimate from the current rate card, not a measured workload. Keep native macOS/Windows work on existing linked machines initially; neither is available from Vercel Sandbox. [Sandbox product](https://vercel.com/sandbox), [pricing](https://vercel.com/docs/sandbox/pricing).

**Question for Julio:** start with Vercel `iad1` Linux boxes that remain team machines and keep their settings and profiles when stopped, with disposable boxes deferred?

| Product choice | Gain | Trade-off | Code consequence |
| --- | --- | --- | --- |
| **Persistent team machine, on demand** | Keeps today's slots, access, machine setup and profiles; no repeated sign-in | Disk and credentials outlive a run; expiry must work while offline | Add provider lifecycle and wake-before-start; keep current machine/profile rules |
| Disposable team machine per run | Fresh filesystem for each run; deletion bounds retained state | Repeated setup/sign-in; output must be exported; one run's end destroys its profiles | New allocation/deletion policy, profile expiry capped to box lifetime, artifact export, token revocation and cleanup reconciliation |
| Both immediately | Covers development machines and isolated batch work | Two lifecycle policies, retention UIs and failure paths before either is verified | Both implementations plus an explicit choice at run start |

The recommendation follows #3's “cloud box is a team machine” and ADRs 0001–0003. Disposable machines could still belong to the team, but deleting their profiles at run end changes the retention promise and needs a separate policy. This document proposes choices; it changes no ADR or glossary.

### macOS and Windows are separate purchasing decisions

Daytona's [macOS docs](https://www.daytona.com/docs/macos-sandboxes) quote **$60.08 per 24-hour M4 Pro reservation**, with up to two VMs on a dedicated Mac. Stopping a VM cannot end that paid period early. The region is `macos-1`, not a verified US East city. Persistent disk recovery at reservation end creates a new VM identity; that must not silently clone an existing bridge token. Its published base macOS core surcharge is not the reservation's total. Do not estimate a short Mac job by multiplying the Linux hourly rate.

For Windows, Daytona's v2 dedicated page says coming soon; that takes precedence over assuming the pricing page proves availability. Orgo currently advertises Windows and Mac, discussed below. The bridge already supports Node 24+ on those OSes, but a Windows machine needs ConPTY and OS-specific adapters; tmux/herdr do not become Windows-compatible by renting a box.

## Cost of the recommended first machine

Calculated from [Vercel's `iad1` rate card](https://vercel.com/docs/sandbox/pricing), read 2026-11-02:

`hourly compute = 2 × CPU utilization × $0.128 + 4 × $0.0212`

At 10% CPU: **$0.1104/hour**. At continuous full use of both vCPUs: **$0.3408/hour**. For 100 active machine-hours/month that is **$11.04–$34.08**, plus storage and traffic. CPU utilization is a scenario parameter, not a benchmark.

Example storage assumption: one retained 10 GB snapshot for a full month adds **$0.80**. The resulting gross usage is **$11.84–$34.88** before traffic and tiny creation charges. With a new $20 Pro account and its entire $20 credit unused elsewhere, total platform-plus-usage is approximately **$20–$34.88/month**. Existing account credits may already be spent; verify the account rather than count the credit twice. Extra Vercel deploying seats cost $20/month each; Uplink Room membership does not itself imply each person needs a Vercel seat. [Pro fees](https://vercel.com/docs/plans/pro-plan), read 2026-11-02.

Keep one latest snapshot, explicitly retained for the machine's intended life; Vercel's default snapshot expiry is 30 days since last use. If no resumable snapshot remains, it can remove the sandbox after 14 days of inactivity. A persistent team machine must not quietly lose its setup under provider defaults. [Retention](https://vercel.com/docs/sandbox/concepts/persistent-sandboxes), read 2026-11-02.

## Code changes and operating rules

Inspected [Room API factory](../packages/backend/convex/lib/room.ts), [HTTP](../packages/backend/convex/http.ts), [schema](../packages/backend/convex/schema.ts), [machines](../packages/backend/convex/machines.ts), [runs](../packages/backend/convex/runs.ts) and [bridge README](../packages/bridge/README.md) on 2026-11-02. There is no provider lifecycle implementation today. Machine online/offline describes the bridge, not whether a provider is charging.

For **every full-machine provider**, add a provider adapter with create/get/start/stop/delete and reconciliation, plus provider resource ID, region, image revision, intended lifecycle and operation generation. Expose provision/wake/stop through the same Room API factory so MCP, HTTP, CLI and the desktop app share authorization and audit. Use Convex actions or an external worker for provider calls, not network side effects inside a mutation. Keep provider credentials service-side and separate from the machine's bridge token. Only admins change provisioning settings for team machines; ordinary starts operate within those settings.

For **Vercel**, use a unique provider name derived from the room machine ID and `Sandbox.getOrCreate`; set `region: iad1`, persistence and snapshot policy explicitly. Build an image with Node 24+, the bridge tarball, `python3`, `make`, `g++` and the required harnesses. Linux installs compile node-pty. Pair once as a team machine; persist its private bridge directory and profiles, not a pre-paired golden image. An `onResume` hook restarts the bridge. Its outbound Convex subscription needs network access, not an exposed inbound bridge port. These are proposed installation steps; no box was created.

For **Daytona**, substitute its version-specific persistent create/start/stop operations and region selector. For **E2B**, use template create/connect/pause/kill and explicitly set timeout to pause, since the documented default is kill; reconcile a refused pause because billing may continue. For **Modal**, mount persistent data and recreate from the intended image/snapshot with a fresh process. For **Morph**, use pause/resume for retained machines, not destructive stop. **Orgo** needs confirmed stop/suspend billing and region semantics. Browser-only candidates require a separate browser integration rather than a provider adapter pretending they run the bridge.

Recommended lifecycle rules:

1. Reserve a wake/start operation once per machine; concurrent terminal starts share it. Wait for both provider readiness and bridge registration before opening a terminal. Record ambiguous results and reconcile before retrying, so a network timeout cannot buy a second box.
2. Idle means **no live or starting terminals, no active thread runs including Waiting, no viewer/desktop lease, and no pending start**. Bridge heartbeats or polling do not count as useful work. After 15 minutes, recheck under the same operation generation before graceful bridge shutdown and provider stop. A new start cancels the stop or waits for it and wakes again.
3. Do not pause active work to save money. Warn before a provider session cap, then let work finish or stop it explicitly. Provider timeout/failure ends or invalidates the affected runs; starting the same disk later does not revive a completed/stopped run. The current bridge registration already invalidates terminals from a previous process.
4. Keep access limits, slots, driver checks and supported profile harnesses exactly as documented. Currently only Claude Code and OpenCode can start profile terminals. Persistent disks do not expand that support.
5. Profile expiry uses wall-clock time while stopped. Schedule a maintenance wake when a profile expires: keep terminal starts blocked, delete the profile, save the cleaned disk and remove earlier credential-bearing snapshots, then stop again. Budget that cleanup runtime. Also purge overdue profiles before accepting terminals after an outage. Resuming an old snapshot must not restore an expired profile. Preserve only the intended machine's identity, never clone its paired token into another machine.
6. Stop is reversible and retains setup; delete destroys the machine's retained data and revokes its bridge identity. Cleanup must include provider snapshots/volumes and verify the provider reached the requested state. Neither offline nor a successful stop request alone proves billing stopped.

If Julio chooses **per-run boxes** instead, add an allocation binding from run to machine, one-run occupancy, explicit deletion at run end, maximum lifetime, expiring credentials and output export before deletion. Profile lifetime becomes the lesser of its selected expiry and box lifetime. Keep the run/transcript after deleting the machine. Never copy a person's existing profile to a replacement box; the glossary deliberately makes profiles machine-bound.

## Experiment before implementation is called complete

On one real `iad1` sandbox: build/install bridge, pair, observe registration, open a real terminal through the Room API, type/read output, stop after idleness, read back stopped provider state, wake the same machine and verify settings plus an unexpired supported profile. Repeat with an expired profile, two simultaneous starts, a start racing idle stop, an interrupted provider call and a bridge restart. Measure wake time and actual CPU/storage usage. Confirm all retained credential copies obey expiry. Until that passes, provider compatibility and the workload cost remain estimates. This research created no cloud resources or subscriptions.
