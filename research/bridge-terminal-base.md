# The bridge's terminal base: herdr, sshx, T3 Code, or our own node-pty

Research for [#14](https://github.com/nuko-nova-dynamics/uplink-room/issues/14), experiment 5. Checked on 2026-11-02 against the bridge at `527f9e9fd25ddbbd94b5d4fee1293eb7fdd6722f`, then updated the same day with #34's root cause (PR #41) and #43, and on 2026-11-03 with experiment 1's results from sthopc20 and sthopc01 (#43, #61, PR #54). Every claim below names the file, release, issue or doc page it comes from. Anything not reproduced here is marked **hypothesis**, with the experiment that would settle it.

## Recommendation

**Keep the bridge's own node-pty base, in TypeScript on Node.** None of the three replaces it without giving up something the bridge already enforces. Take specific pieces from them instead:

- **herdr: keep it as an adapter, not a base.** It is a full terminal multiplexer with its own server, socket and access rules (the same OS account controls everything). Its public API gives text snapshots and events, not a raw output stream. Building on it would add a second daemon per machine and still leave slots, drivers and profiles to the bridge. Its docs now say native Windows support is generally available, so the bridge README's "herdr doesn't run natively on Windows" is out of date; re-test the adapter there (experiment 4).
- **sshx: don't use it.** Its server, not the sharing machine, decides who may type, and anyone with the write link can type at once. Self-hosting is "not supported at the moment". Its Windows client can't start PowerShell. The last release was v0.4.1 in February 2025. Its end-to-end encryption also means the room couldn't store output for late viewers and agents.
- **T3 Code: borrow ideas and small pieces of MIT code, not the module.** T3's terminal server also runs on node-pty, so moving to it fixes nothing on Windows. Its terminal manager is written in Effect against T3's private packages. One thing is worth porting: its replay clean-up (removing terminal queries and alternate-screen state before replaying history). Its node-pty patch isn't: when the helper fails it still kills the shell's old pid, only sooner, which is the kill PR #41 removes.
- **Language: TypeScript.** Rust would only pay off if we adopted herdr's or sshx's code, and this recommends neither. The bridge already ships inside the Electron app on its Node runtime.

**node-pty's Windows `kill()` has two separate problems, and both affect T3 Code too.** In node-pty 1.1.0, `kill()` starts a helper to list the console's processes, then closes the console on the next line. The helper often loses that race and fails with `AttachConsole failed`. Two things follow:

1. **Killing a recycled pid (#34, fixed by PR #41).** With no answer from the helper, node-pty falls back 5 seconds later to killing the shell's old pid. Windows had often given that pid to another process by then. In CI it was sometimes room-client's vitest, which died with exit code 1 and no output: 4 failures in 1,210 room-client runs, each traced to this fallback, and 0 in 1,240 with the patch. PR #41 (merged as 9e564d6) patches node-pty 1.1.0 so the helper reports an empty list, as 1.2.0-beta.18's helper does, and the fallback kills nothing. On a person's machine the same fallback could kill an unrelated program 5 seconds after a terminal closed.
2. **A process the shell started can survive (#43).** A reporter measured a surviving pipeline stage in 5 of 5 kills ([microsoft/node-pty#952](https://github.com/microsoft/node-pty/issues/952)). We didn't reproduce that one: on Windows 11 builds 26100 and 22000 the helper lost the race in all 20 measured stops, yet closing the console ended every process attached to it. What does survive is a process with no console, such as one started detached: it outlived node-pty's `kill()` in 5 of 5 stops. PR #54 kills the shell's process tree with `taskkill /PID <pid> /T /F` while the shell is still alive, then calls node-pty's `kill()` (experiment 1, below).

The bridge README called `AttachConsole failed` "noise, not a failure". It was the visible sign of both problems.

## Evidence

### What the bridge does today

From the baseline commit:

- `packages/bridge/src/terminal.ts`: `nodePtyHost.spawn` calls `pty.spawn` from node-pty, after fixing the execute bit on the macOS `spawn-helper`.
- `packages/bridge/src/platform.ts`: `terminalShell` runs `/bin/sh -c` on macOS and Linux; on Windows it picks `UPLINK_BRIDGE_SHELL`, then `pwsh`, then Windows PowerShell, then cmd, and passes PowerShell the command as `-EncodedCommand`.
- `packages/bridge/src/bridge.ts`: output is batched per terminal and flushed after 30 ms or at 16,384 bytes (`onData` handler). `resize_terminal` is refused with `not_driver` unless it comes from the driver, then clamped. `input` reaches the pty only from the driver. `end`, `stopSharing` and `close` all call `terminal.process.kill()` with no tree kill.
- `packages/backend/convex/lib/bridgeMessages.ts`: `OUTPUT_CHUNKS_KEPT = 2000`; older chunks are deleted as the seq passes each hundred. `packages/backend/convex/lib/terminals.ts`: `OUTPUT_CHUNK_BYTES = 32 * 1024`, `OUTPUT_PAGE_BYTES = 4 * 1024 * 1024`.
- `packages/bridge/src/convexLink.ts` sends each message as a `bridge:send` mutation. convex 1.49.0's `dist/esm/browser/sync/request_manager.js` `restart()` resends every mutation that was unsent or in flight when the socket dropped, and fails in-flight actions.
- `packages/bridge/README.md` said "tmux and herdr don't run natively on Windows" and that `AttachConsole failed` on Windows "is noise, not a failure". Both were wrong; this PR corrects them from the sources below.

### node-pty and the Windows kill

Read from the npm tarballs of `node-pty@1.1.0` (the bridge's pin) and `node-pty@1.2.0-beta.18`:

- `lib/windowsPtyAgent.js`, `kill()`: on the default ConPTY path it calls `_getConsoleProcessList()`, which forks `conpty_console_list_agent`, then calls `this._ptyNative.kill(...)` on the next statement. `_getConsoleProcessList` resolves with the helper's list, or after 5,000 ms with `[this._innerPid]` (the shell's pid) alone. 1.2.0-beta.18's `kill()` and timeout are the same.
- `src/win/conpty_console_list.cc` throws `AttachConsole failed` when it can't attach to the shell's console. In 1.1.0, `lib/conpty_console_list_agent.js` doesn't catch it, so the helper exits without sending its list and the 5-second fallback runs. In 1.2.0-beta.18 the helper catches it and sends an empty list, so the fallback runs only if the helper can't reply at all.
- `lib/unixTerminal.js`: `kill(signal)` is `process.kill(this.pid, signal || 'SIGHUP')`, the shell's pid only.
- 1.1.0 prebuilds: `darwin-arm64`, `darwin-x64`, `win32-arm64`, `win32-x64`. 1.2.0-beta.18 adds `linux-arm64` and `linux-x64` and bundles `third_party/conpty/1.25.260303002`, used only with the experimental `useConptyDll` option.

Open upstream issues, read on 2026-11-02. The measurements are the reporters', not reproduced here:

- [#952](https://github.com/microsoft/node-pty/issues/952) (2026-08-16): the helper "frequently loses that race", so "the leftover-process sweep runs five seconds late against a pid that was already killed". On node-pty 1.1.0, Node 24.13.1, Windows 11: 5 of 12 kills printed the stack trace, and a pipeline stage survived in 5 of 5 kills. No replies.
- [#1007](https://github.com/microsoft/node-pty/issues/1007) (2026-10-30): with two processes spawning and killing ptys at once, 8 of 8 kills crashed the helper, on 1.1.0 and 1.2.0-beta.18. The reporter also saw a pty's exit event never arrive under that contention.
- [#965](https://github.com/microsoft/node-pty/issues/965) (2026-09-08): a shell that exits on its own never gets `ClosePseudoConsole`, leaving one `conhost.exe --headless` per pty for the life of the host process. Confirmed in comments on 1.1.0 and on the official 1.2.0-beta.15.

In this repo, from #34's "Root cause analysis" artifact and PR #41 (read on 2026-11-02; PR #41 merged the same day):

- The bridge tests, running beside room-client's under `pnpm -r test`, triggered the 5-second fallback. With node-pty logging every pid it killed, [run 41546654480](https://github.com/nuko-nova-dynamics/uplink-room/actions/runs/41546654480) had 4 failures in 1,210 room-client runs, and in all four the fallback had killed a live room-client process (three times vitest's main process, once a worker). Across both unpatched runs there were 1,820 fallback kills.
- `patches/node-pty@1.1.0.patch` in PR #41 makes the helper catch the error and send an empty list, and makes the 5-second timeout resolve an empty list instead of the shell's pid. [Run 41547961527](https://github.com/nuko-nova-dynamics/uplink-room/actions/runs/41547961527) with the patch: 0 failures in 1,240 room-client runs and 60 bridge runs, and 0 fallback kills.

That settles the stale-pid problem. Experiment 1 then settled #43 and found #61; see its results below. A long-running bridge does collect `conhost.exe` processes (#965): each terminal whose program exited on its own left one, 3 of 3 on both hosts. PR #21 already ruled out one related suspicion: lost output on quick exits was the tests' short profile lifetime, not ConPTY (220 node-pty runs on windows-latest, 0 lost).

`taskkill /T` "Ends the specified process and any child processes started by it", and `/F` "Specifies that processes be forcefully ended" ([Microsoft Learn, taskkill](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill)). It walks parent and child links, so it has to run while the shell is still alive, before node-pty's `kill()`.

### herdr

Checked: the GitHub repo through the API (`herdrdev/herdr`, master at `ee5bfb5`), its README, [herdr.dev/docs/windows-beta](https://herdr.dev/docs/windows-beta/), [herdr.dev/docs/socket-api](https://herdr.dev/docs/socket-api/), and the installed `herdr 0.9.5` with `hc --help` and `hc attach --help`.

- License Apache-2.0. Releases v0.9.3 (2026-09-29), v0.9.4 (2026-10-13) and v0.9.5 (2026-10-14), with preview builds between.
- The Windows page opens with "Native Windows support is generally available." It lists local persistent sessions, ConPTY panes and `herdr --remote` as supported, and "Direct terminal attach (`herdr terminal attach`)" as unsupported. Whether `hc attach`, which the bridge's adapter discovers its target from, is that same attach wasn't checked on Windows (experiment 4).
- The socket API can "list, inspect, split, swap, focus, resize, rename, read, close, and send input to panes" and "subscribe to events and wait for output or state changes". `pane.read` returns `visible`, `recent` or `recent-unwrapped` text. The page says the screen stream used by herdr's own UI belongs to a "numbered binary protocol" for "same-install and internal operations"; it isn't offered as a public API.
- Event history "is not durable"; a subscriber that falls behind must re-read the current state.
- The socket is `~/.config/herdr/herdr.sock` (or one per named session). The page doesn't state its file mode; on Windows "ordinary local processes belonging to that account" can control panes and "other accounts remain excluded".
- `hc attach` has `--observe` ("Watch only: never type or resize") and `--history` ("Scrollback lines to show first").
- The README says herdr "keeps terminals running in a background server when you close the client or lose your SSH connection", and that after a server or machine restart "the original processes do not survive".

That last point is the one thing herdr offers that the bridge doesn't: terminals that outlive the process sharing them. The bridge already gets it by sharing `hc attach TARGET`, so work run inside herdr survives a bridge restart even though the shared view ends.

### sshx

Checked: `ekzhang/sshx` through the API (main at `3604e8e`), its README, `LICENSE`, `crates/sshx/src/terminal.rs`, `crates/sshx/src/terminal/windows.rs`, `crates/sshx/Cargo.toml`, `crates/sshx/src/controller.rs`, `crates/sshx-server/src/session.rs` and `crates/sshx-core/proto/sshx.proto`.

- License MIT, the issue's open question. Releases v0.4.0 and v0.4.1 on 2025-02-11 and 2025-02-12, with no assets attached; binaries come from `sshx.io/get`. The last two commits (2026-09-20 and 2026-09-21) fix a Redis version, rustfmt and clippy.
- README, Deployment: "Self-hosted deployments are not supported at the moment." The author hosts the servers on Fly.io with Redis Cloud.
- `windows.rs`: the default shell is Git Bash or cmd, and its comment reads "I can't get `powershell.exe` to work with ConPTY, since it returns error 8009001d." It uses the `conpty` crate 0.7.0.
- `session.rs`: `SHELL_STORED_BYTES` is 2 MiB per shell, and `check_write_permission` runs on the server and only asks whether the user `can_write`. `controller.rs` puts the encryption key in the URL fragment ("hidden from the server") and, with `--enable-readers`, a separate write password.

### T3 Code's terminal code

Checked: `pingdotgg/t3code` at `71646e031a6dc9db1309b3b9dff597f872cf2fd3` (2026-11-02): `apps/server/src/terminal/Manager.ts`, `NodePtyAdapter.ts`, `OutputProtocol.ts`, `nodePtyConsoleList.test.ts`, `patches/node-pty@1.2.0-beta.15.patch`, `apps/server/package.json` and `packages/contracts/package.json`.

- License MIT. The server depends on `node-pty` `^1.2.0-beta.15`. `@t3tools/contracts` is `"private": true`.
- The patch makes the console-list helper settle on `close` or `error` instead of waiting 5 seconds, forks it with `windowsHide: true`, and keeps Node's watch mode out of its IPC channel. When the helper fails it still returns the shell's pid, so T3 can kill a recycled pid too, with a shorter window than 5 seconds. Its test cites the regression "#18519 Windows terminal kill waited on timeouts".
- `Manager.ts`: `DEFAULT_HISTORY_LINE_LIMIT = 5_000`, `DEFAULT_HISTORY_BYTE_LIMIT = 8 * 1024 * 1024`, history saved per thread. "Attached viewers share one PTY sized to the smallest of them, so a narrow client still sees the whole TUI." `neutralizeInheritedHistory` and the query-stripping functions clean history before replay. Kill sends SIGTERM, waits `DEFAULT_PROCESS_KILL_GRACE_MS = 1_000`, then SIGKILL; `NodePtyAdapter.ts` drops the signal on Windows.
- `OutputProtocol.ts`: `MAX_PENDING_CHUNKS = 8`, `MAX_PENDING_BYTES = 64 * 1024` per attached stream.
- `Manager.ts` imports Effect, `@t3tools/shared`, `@t3tools/provider-core` and server modules such as provider drivers and telemetry, so lifting it means porting it.

Experiment 1 in `research/notes.md` (#12) reached the same verdict for T3's thread view: reuse selected MIT code behind the bridge rather than embedding T3.

## Open questions and experiments

1. **Do Windows terminals the bridge stops leave processes behind, and does a tree kill fix it?** (#43) **Done on 2026-11-03**, by hand on the team's Windows runners, since hosted runners were unavailable: sthopc20 (build 26100) and sthopc01 (build 22000), pwsh running `node child.cjs | more`, survivors counted 6 s and 15 s after each stop. node-pty's `kill()` alone: 0 survivors in 20 stops (10 per host), although its helper returned an empty list every time. `taskkill /T` first: 0 survivors, but 4 of 20 stops left a `conhost.exe` (#965: the shell is gone before node-pty can close its console). `taskkill /T` after `kill()`: the shell was already gone every time (exit 128), so it can't come second. A detached child (no console) survived `kill()` alone in 5 of 5 stops and was ended by `taskkill /T` first in 5 of 5; that is the bridge test now. #34's stress run on sthopc20 (47 room-client runs during 2 bridge runs) had 0 failures and 0 node-pty kills. The runs also found #61: node-pty holds `kill()` until a terminal's first output, and on build 22000 under a service account ConPTY sends none for a silent program.
2. **Does a long-running bridge on Windows collect `conhost.exe`?** (#965) **Answered on 2026-11-03** (#66): yes, one per terminal, on main after #54. Through the bridge's own `nodePtyHost`, every stop (the tree kill ends the shell before node-pty's `kill()`) and every program that exited on its own left its `conhost.exe` running 8 s after the exit: 20 of 20 stops and 10 of 10 exits on sthopc20 (build 26100, `CORP\jdiaz`), and the same on sthopc01 (build 22000, NETWORK SERVICE, Node 24.22.2). node-pty#965 is still open, its fixes (#990, #991) unmerged, and 1.2.0-beta.18's exit watcher still erases the baton without closing the console, so the bridge now ends a terminal's console host itself a second after node-pty reports the exit, through the holder: the only `conhost.exe --headless` whose parent is the bridge and that started inside that terminal's `pty.spawn` (all 150 measured started 0 to 1034 ms into it), and only while no program is still attached to its console. Ending a console host doesn't end the programs attached to it, and a first version without that last check stranded one in 2 of 6 bridge-suite runs on sthopc01. With the fix, 0 of 20 stops and 0 of 10 exits left one, on each host (on sthopc20, measured before the attached check was added). PR #82's review then made the check fail closed: it looks at every process that could be attached and keeps the console host when one can't be read or exits during the check, through a second helper that never delays a stop. It also showed two more leaks, on both builds: a program attached to a stopped terminal's console whose parent had already exited (so the tree kill can't reach it) kept running, 10 of 10 on each host, and is now ended after a stop; and a bridge that crashed with a terminal open left its console host after exiting in 4 of 5 crashes on build 22000 (0 of 5 on 26100), which the next bridge now ends from a record each bridge keeps. Codex's second round found that matching a console host by spawn window can confuse two terminals started within it; the bridge now binds each terminal to its exact console host while the shell is alive. The bridge README says how.
3. **Does replay from a trimmed window render TUIs correctly?** (hypothesis) Run Claude Code in a shared terminal until the room has deleted early chunks, then open the terminal in a new viewer. If the screen is wrong until the next redraw, port T3's history clean-up (strip query sequences, leave the alternate screen) into the viewer's replay, with MIT attribution.
4. **Does the herdr adapter work on Windows now?** Install herdr stable on a windows-latest runner, run `hc run --bg`, share `hc attach TARGET` through the bridge and watch `hc events --json` report Working and Done. If it passes, load the herdr adapter on Windows and fix the README; if `hc attach` is the unsupported direct attach, use a configured target instead.
5. **Should the pty follow the driver's size or the smallest viewer's?** Today viewers narrower than the driver see wrapped output. Open the same terminal in the desktop app at two widths and compare. T3 chose the smallest viewer; the room chose the driver. This is a product decision more than a test.
6. **How much memory does a bridge use while its link is down?** (hypothesis) The Convex client keeps unsent mutations in memory and the bridge doesn't cap them. Block the Convex host, run a command printing 1 MiB a second for ten minutes, and record the bridge's resident memory. If it grows without bound, drop or summarise output past a cap while offline.
7. **When does node-pty 1.2.0 become stable?** Its Linux prebuilds would remove the compiler requirement from the standalone install. Until then, run the bridge's CI matrix once on 1.2.0-beta.18 to learn whether anything breaks, without shipping a beta.

No experiment is proposed for sshx: nothing in it fits the room's model without the hosted server it says not to self-host.
