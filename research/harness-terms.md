# Harness subscriptions, teammates and CLI proxies

This is research, not legal advice.

Research for [#11](https://github.com/nuko-nova-dynamics/uplink-room/issues/11), experiment 3. **Read on 2026-11-02.** Every external source below was opened on that date. Dates attached to sources are their stated effective or update dates, not the date of this report. Private order forms and negotiated agreements were not available.

## Scope and reading of the results

The [glossary](../GLOSSARY.md) defines **machine setup** as a machine's existing logins or CLI proxy, settings and skills. A **profile** holds one person's separate setup on that machine. Here, shared use means a teammate starts or drives requests against someone else's subscription. It includes an already logged-in terminal; revealing a password is not necessary to make an account available to someone else.

**Allowed** means the cited source expressly supports the described arrangement, subject to its conditions. **Not allowed** means an express restriction covers it. **Unclear** means the sources do not settle it, or conflict. These are research conclusions, not provider approvals of Uplink Room. Sharing code or an output, watching a run, suggesting something to its account holder, and independently driving that account are different actions. None of the sources grants a general multiplayer exception for passing the wheel.

A network proxy carrying one authorized user's requests is also different from a service that turns subscription OAuth credentials into a model API, pools accounts, or serves other people. The table concerns the latter subscription use; it does not claim all networking proxies are prohibited.

## Sources and qualifications

All links in this section are primary sources, read **2026-11-02**. Quotations are exact; a passage identified as an excerpt is not presented as a complete sentence. The providers' usage policies still govern the content and conduct of every run. Their existence is not an exception to account or plan restrictions.

### Anthropic

- **[A1] [Consumer Terms of Service](https://www.anthropic.com/legal/consumer-terms), effective 2025-10-08, §§2–3.** In addition to the sentence in the table, these terms restrict credential sharing, resale, and automated access unless an API key or explicit permission applies. The express native Claude Code permission must be read alongside the account restriction.
- **[A2] [Purchase and manage seats on Team plans](https://support.claude.com/en/articles/12004354-purchase-and-manage-seats-on-team-plans), live help.** The quoted named-person rule appears in its seat-use guidance. Reassignment is for team changes, not rotating several people through one seat. [Roles and permissions](https://support.claude.com/en/articles/9267276-roles-and-permissions) permits a Primary Owner service account; that administrative role does not grant a shared coding seat.
- **[A3] [Claude Code legal and compliance](https://code.claude.com/docs/en/legal-and-compliance), live docs, “Can customers offer Claude Code in their products?”:** “Customers may not pay for, resell, or intermediate Claude usage on their end users’ behalf.” The surrounding conditions require the published binary, preserve its authentication choices, and require each end user's own credentials and direct provider billing. The authentication section separately limits subscription OAuth to native Anthropic application use and prohibits routing third-party users through personal-plan credentials. This is a material distinction between controlling the real CLI and using its token as another harness's backend.
- **[A4] [Commercial Terms](https://www.anthropic.com/legal/commercial-terms), effective 2025-06-17, §A.1**, grants use of the services to power customer products for end users. [Service Specific Terms](https://www.anthropic.com/legal/service-specific-terms), effective 2026-08-31, §A, governs Claude for Work and administered users. An API product under that grant is distinct from intermediating the Claude Code binary under A3. Do not assume Uplink Room may rebill Claude Code usage merely because an API contract exists.
- **[A5] [Usage Policy, effective 2025-09-15](https://www.anthropic.com/legal/archive/22742366-2ef0-4c7a-a833-6523f10d3944).** The official version history identifies this as the predecessor to the posted November policy. Its scope includes authorized reseller/passthrough users; that scope does not authorize an otherwise prohibited reseller. No shared-subscription exception was found. **Date qualification:** the [live policy](https://www.anthropic.com/legal/aup) displays **2026-11-12**. Anthropic's [October 8 announcement](https://www.anthropic.com/news/2026-usage-policy-update) says: “The updated policy takes effect on November 12.” The archive labels the earlier text replaced, despite that future effective date. Keep both dates visible and recheck at launch; do not silently treat the November text as already effective today.

### OpenAI

- **[O1] [Terms of Use](https://openai.com/policies/terms-of-use/), effective 2026-01-01, “Registration and access” and “Using our Services.”** These prohibit sharing credentials or making the account available to others and circumventing limits. The [Codex plan help](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan) connects ChatGPT sign-in to the applicable individual or business terms. A work email is not a sharing exception. Regional terms or an actual organization agreement may govern instead.
- **[O2] [OpenAI Account Sharing Policy](https://help.openai.com/en/articles/10471989-openai-account-sharing-policy), live help.** The table quotes the own-account instruction; the same page expressly distinguishes multiple devices used by one person.
- **[O3] [OpenAI Services Agreement](https://openai.com/policies/services-agreement/), effective 2026-01-01, §§2.2 and 3.1.** The table quotes the shared-login prohibition. Section 2.2 expressly permits API integration into customer applications for end users; §3.1 restricts resale/leasing of account access. Use an application entitlement, not the resale of a human account.
- **[O4] [Authentication](https://learn.chatgpt.com/docs/auth), live docs, “Authenticate with a custom model provider.”** Exact sentence: “This is useful when you access OpenAI models through an LLM proxy server.” The surrounding instructions support OpenAI authentication through a proxy and distinguish gateway OAuth and API authentication. This is evidence against a blanket ban on proxies, not permission for a shared credential pool. API usage is separately billed; API access does not spend included ChatGPT plan credits.
- **[O5] [Service Terms](https://openai.com/policies/service-terms/), updated 2026-10-16, §4**, covers Codex/code generation without adding a sharing exception. [Usage Policies, effective 2025-10-29](https://openai.com/policies/usage-policies/revisions/2025-10-29/) prohibit safeguard circumvention. **Date qualification:** the [live page](https://openai.com/policies/usage-policies/) instead displays an effective date of **2026-11-20**, after this report. The linked previous version is the verified earlier text; neither supplies authorization to share subscriptions.

### xAI / SpaceXSI

- **[X1] [Consumer Terms](https://x.ai/legal/terms-of-service), updated 2026-10-27, §2.** The table's excerpt is the first clause of the account-sharing sentence; the rest makes the account holder responsible for activity. [Grok Build overview](https://docs.x.ai/build/overview) documents browser sign-in, API-key use, headless scripting and ACP. The [Grok FAQ](https://docs.x.ai/grok/faq) describes one subscriber's weekly allowance spanning Grok products, including Build. Neither makes that subscriber several people.
- **[X2] [Enterprise Terms](https://x.ai/legal/terms-of-service-enterprise), updated 2026-10-27, §§1.1–1.2.** The table quotes the credential clause. Employees, agents, contractors and consultants may be Permitted Users; API integrations may be offered as Bundled Services under the stated conditions. The [license/user-management docs](https://docs.x.ai/grok/management) describe invitations and assigning licenses to users. Shared billing or a central team is supported; a generic shared human login is not explicitly resolved by the narrower unauthorized-person wording.
- **[X3] [Acceptable Use Policy](https://x.ai/legal/acceptable-use-policy), effective 2026-08-14.** It restricts service resale, bots, and rate-limit/protection circumvention. Read its general bot language together with the explicit native headless/ACP features, rather than declaring the official CLI itself prohibited. No CLIProxyAPI subscription-pooling exception was found. [Enterprise deployments](https://docs.x.ai/build/enterprise) supports corporate identity providers and token brokers, not a general grant to redistribute personal subscriptions.

### OpenCode / Anomaly

- **[P1] [Terms of Use](https://opencode.ai/legal/terms-of-service), effective 2026-08-15.** The terms distinguish hosted/inference services from local open-source software, which is governed by its repository license. Hosted use is limited to the customer's internal use, with no third-party-benefit grant; the terms restrict bulk accounts and using multiple accounts to circumvent limits or billing. Exact sentence: “Except as expressly set forth herein, no rights to the Services or Third Party Models are granted to you.” No express shared-human-login permission was found. Additional checkout terms are incorporated but were not inspected through a purchase.
- **[P2] [Go plan documentation](https://opencode.ai/v2/docs/console/go/), live docs.** The table quotes the single-member rule. Go Teams gives each member their own allowance; service accounts are excluded from that plan. The same page's client requirements explicitly discuss proxies forwarding native session headers. This supports the described integration pattern, not identity concealment or combining several people's individual subscriptions.
- **[P3] [Console members](https://opencode.ai/v2/docs/console/members/), live docs.** The table quotes its short single-member sentence. The invitee signs in using the invited email; the documented team arrangement is membership, not one shared login.
- **[P4] [Provider documentation](https://opencode.ai/docs/providers/), live docs**, supports custom base URLs/proxies and documents ChatGPT subscription authentication. That proves OpenCode functionality, not OpenAI's authorization of every proxy. Its Anthropic section says personal-plan plugins are prohibited and directs users to API keys. Provider terms govern those entitlements. [Local software license](https://github.com/anomalyco/opencode/blob/dev/LICENSE): MIT. A local-model setup can avoid subscription sharing, but each model's license remains applicable.

### Cursor / Anysphere

- **[C1] [Terms of Service](https://cursor.com/terms-of-service), updated 2026-09-03, §§1.5 and 3.** Use-restriction excerpt: “rent, lease, lend, or sell the Service”. Section 3 requires account/password confidentiality and responsibility for account activity. It does not contain the explicit anyone-else account prohibition found in Anthropic/OpenAI/xAI terms. An organization's MSA can govern instead.
- **[C2] [Acceptable Use Policy](https://cursor.com/acceptable-use-policy), updated 2026-08-11.** The table quotes its complete sentence addressing others' use under an account. It also restricts resale, rate-limit circumvention and manipulating team/user assignment to avoid fees. The responsibility sentence is not an express paid-seat license.
- **[C3] [Official staff answer, post 5](https://forum.cursor.com/t/can-multiple-people-use-one-cursor-account/158868/5), 2026-04-23.** Kevin Neilson (`kevinn`), whose forum record identifies him as staff, wrote: “Account sharing is against the Cursor terms of service, you can read more here:”. This is first-party support guidance, not a contract amendment, and predates C1/C2. Its conflict with the current AUP is why the table says unclear rather than inferring permission or a new categorical ban.
- **[C4] [Team pricing](https://cursor.com/docs/account/teams/pricing), live docs.** “Seats don't share weekly pools with each other, and usage doesn't transfer between team members.” The same page supports centralized administration and shared prepaid overage billing. [CLI docs](https://cursor.com/docs/cli/overview) document the actual harness, not a separate sharing entitlement.

### Google Antigravity

- **[G1] [Antigravity Additional Terms](https://antigravity.google/terms), live text with no visible effective date.** The table quotes §6. The opening enterprise provision instead points covered enterprise/Workspace access to the administrator's accepted or signed terms. Consumer use incorporates [Google Terms](https://policies.google.com/terms), effective 2026-07-30. Do not transfer the consumer exception analysis to an unknown enterprise order form.
- **[G2] [Antigravity FAQ](https://antigravity.google/docs/faq), live docs, headless-mode question.** “Wrapping agy inside third-party coding agents or applications, or automating account rotation, is not supported under consumer plans.” The preceding sentence distinguishes direct scripting/CI use. The neighboring third-party-login answer recommends Gemini Enterprise or a Google AI Studio API key for third-party coding agents. Accordingly, running the official binary inside Uplink Room is not automatically an approved workaround for the OAuth restriction.
- **[G3] [Avoid sharing an account among users](https://knowledge.workspace.google.com/admin/users/avoid-sharing-an-account-among-users), updated 2026-10-26.** The table quotes Google's one-person account guidance. This help page is not a specific consumer Antigravity remote-terminal clause; that exact teammate scenario remains unclear. [Cloud AUP](https://cloud.google.com/terms/aup), modified 2026-10-12, expressly restricts granting several individuals access to an individual Workspace/Cloud Identity End User Account, except through supplied delegation features. That rule's stated scope is not every Cloud service.
- **[G4] [Plans](https://antigravity.google/docs/plans) and [Enterprise](https://antigravity.google/docs/enterprise/), live docs**, distinguish individual Google AI entitlements from team access under enterprise terms. [Google One Additional Terms](https://one.google.com/terms-of-service), modified 2026-10-01, §6, supports specified family benefits. That is not a general coworker-sharing grant and does not override G1/G2. [Google Cloud Terms](https://cloud.google.com/terms) permits certain customer-application integrations subject to its product distinctions and the actual agreement, not arbitrary consumer token resale.
- **[G5] [Generative AI Prohibited Use Policy](https://policies.google.com/terms/generative-ai/use-policy), modified 2024-12-17**, applies where the Google product refers to it and restricts circumventing protections. Cloud use is also subject to the applicable Cloud AUP. Neither is an affirmative grant to share a human subscription.

### CLIProxyAPI

- **[R1] [Project README](https://github.com/router-for-me/CLIProxyAPI), live default branch.** The table quotes its multiple-account load-balancing feature. The README also advertises subscription OAuth support for Codex, Claude Code and Grok Build. These are the proxy author's capability claims, not statements from those model providers. No provider endorsement or blanket shared-subscription license was established.
- **[R2] [Project license](https://github.com/router-for-me/CLIProxyAPI/blob/main/LICENSE): MIT.** That permits use and redistribution of this software subject to its notice conditions. It does not license the upstream accounts. This distinction also applies to another proxy with the same architecture. An API-key upstream is not interchangeable with a subscription OAuth pool just because both expose compatible HTTP endpoints.

## Options for a person to decide

| Option | What it addresses | Limitation |
| --- | --- | --- |
| Warn when a run uses someone else's machine setup | Makes the driver, account holder and expected charge visible before a run or passing the wheel | Disclosure does not authorize prohibited sharing. For expressly prohibited cases, require a different entitlement rather than offering “continue anyway.” |
| Add per-person usage limits and attribution | Controls spending and contention on an authorized team API or team entitlement | A local cap cannot turn a personal subscription into a shared license. Do not rotate accounts to evade provider limits. |
| Use each person's profile or assigned provider seat | Keeps each teammate's requests tied to their own entitlement | [#18's local findings](profile-logins.md) support Claude Code and OpenCode only with caveats and further authenticated tests. Codex, Grok Build and Cursor currently offer only the machine setup for complete profiles; Antigravity separation is unverified. A profile is not an OS security boundary or provider approval. |
| Use an organization's API and, if desired, Uplink Room billing | Supports a deliberately shared application under a contract granting end-user use | Requires provider/product review, usage enforcement and separate API costs. Claude Code's A3 conditions prevent assuming Uplink Room can intermediate its usage; an API product with a different harness is a separate arrangement. |

**Recommendation:** begin with each person's own authorized login or named team seat, including when a personal machine happens to host the run. Record the driver, entitlement holder, provider, and whether the run uses a subscription or an API. Check that identity again when passing the wheel. If a complete profile is unavailable, send the teammate to their own machine or an authorized team API rather than silently using the machine setup. Keep warnings and caps as supporting controls, not substitutes for permission.

Do not enable consumer Antigravity through the proposed application wrapper based on T3 Code's FAQ claim. Resolve G1/G2 with Google or use its documented enterprise/API route first. Obtain current written clarification for Cursor's shared-login case and any sole-user subscription proxy whose permission is unclear. No provider has been contacted by this research.

The T3 Code FAQ quoted in [research notes](notes.md#t3-code), including “A separate work account is fine”, is a statement by T3 Code, not an amendment to these providers' terms. A separate work account for one person, separate users within a paid team, and one login shared by several people must remain distinct in the product decision. **Experiment 3's source review is complete; the product choice and provider-specific clarifications remain for a person.**
