# Uplink Room bridge

The bridge shares real terminals and enforces the machine's local limits. It runs on macOS, Linux and Windows with Node 24 or newer. Its entry point is `src/bin.ts`; `pnpm --filter @uplink-room/bridge build` bundles it into one file, `dist/uplink-bridge.mjs`, with node-pty as its only dependency.

```sh
uplink-bridge pair CODE --url https://your-deployment.convex.cloud
uplink-bridge limits --most-open-access suggest --slots 2 --longest-profile-ms 604800000
uplink-bridge run
# From another terminal:
uplink-bridge share -- node build.mjs
uplink-bridge rex-open -- claude          # a Rex tab the room can share (see Rex tabs)
# Inside a shared terminal, as its run (see Messages to runs):
uplink-bridge reply MESSAGE_ID "done, releasing the model"
uplink-bridge say --in "#payments" "build is green"
uplink-bridge say --in "#payments" --file out/render.png "the render"   # send files with it (ADR 0047)
uplink-bridge codex                       # Codex that reports its state and hears messages (see Codex in a terminal)
uplink-bridge share-rex TAB
uplink-bridge stop-sharing
uplink-bridge unlink
```

## Install

There are two ways to get the bridge onto a machine, and a cloud machine gets it by itself.

**With the desktop app (a person's own computer).** The app carries the same bridge, bundled, and runs it on its own Electron binary as Node, so nothing else needs installing. Once the computer is paired, the app starts the bridge when it opens and stops it when it quits. Setup's link step, or Settings → Machines → Link a machine → This computer → Link this computer, pairs it in one step.

To type `uplink-bridge` in a terminal too, choose **Add to PATH**, in Setup's link step, Settings → Setup or Settings → Command line (`apps/desktop/src/main/bridgeCli.ts`). The same step puts the app's `uplink` and `uplink-mcp` (the Room API's command-line tool and MCP server, ADR 0042) on PATH beside it, each read and linked by the rules below; on macOS the links that need an administrator share one prompt, and on Windows the one PATH entry covers all three. The app shows what a new terminal runs for `uplink-bridge` now: this app's bridge, nothing, another copy of the app (a link to one that moved or was deleted), or another install, such as a bridge from npm. It changes nothing until the person clicks.

| OS | Launcher | Add to PATH |
| --- | --- | --- |
| macOS | `/Applications/Uplink Room.app/Contents/Resources/bin/uplink-bridge` | Links `/usr/local/bin/uplink-bridge` to it, as VS Code's "Install 'code' command in PATH" does, making the folder if it's missing. The link is made only where nothing is (`ln -s`, no `-f`), so a file that appears meanwhile stays. A link to another copy of Uplink Room is replaced only through **Use this app's**, and only while it still reads what the app saw. Anything else there (a bridge from npm, a file that isn't executable, a link to something else) is reported and left alone. When the folder isn't writable, macOS asks for an administrator's password with its own prompt (`do shell script … with administrator privileges`, Apple's TN2065), never a terminal `sudo`. On this repo's Apple Silicon Mac (macOS 27.2) `/usr/local/bin` exists, belongs to root, and comes first in `/etc/paths`. |
| Windows | `%LOCALAPPDATA%\Programs\Uplink Room\resources\bin\uplink-bridge.cmd` | Puts that folder first in the user's PATH (`HKCU\Environment`), no administrator needed. The value is read and written as stored, `%VARS%` unexpanded, as Scoop does, and keeps its registry type: a REG_SZ PATH stays REG_SZ, so `C:\%TOOLS%\bin` stays a folder with that name, and an expandable one is expanded before it's split, so a variable holding several folders is searched as several; other copies of the app's folder leave it; and a PATH another program changed meanwhile is refused, not overwritten. It then broadcasts `WM_SETTINGCHANGE` with `Environment`, as Microsoft's Environment Variables page says, so terminals opened afterwards see it. |
| Linux (.deb) | `/opt/Uplink Room/resources/bin/uplink-bridge` | The package does it: its after-install links `/usr/bin/uplink-bridge` (and `uplink`, `uplink-mcp`) to the launchers where nothing is, replaces only a link to another copy of Uplink Room, and leaves anything else (a bridge installed with npm, a link to something unknown) as it is; its after-remove takes only its own link away (`apps/desktop/build/linux`). The app doesn't run as root, so when the link is missing it shows the `sudo ln -s … /usr/local/bin/uplink-bridge` to run. |

"What a new terminal runs" comes from the person's login shell (`$SHELL -l -i`, as Terminal starts it), so a bridge earlier on PATH, such as one npm put in Homebrew's bin, is reported rather than hidden. An empty or relative folder on PATH before the app's link means the plain command depends on the folder the terminal is in, so the app keeps showing the full path then. On Windows the system PATH comes before the user's, and only an administrator can change it; a folder there that isn't named in full (`tools`, `.\tools`) is searched from the folder PowerShell is in, so it counts like a relative one. Cleaning the user's PATH removes only a literal entry that is exactly another copy's launcher folder whose launcher is gone; an entry with a `%VAR%` always stays. Link a machine's terminal command for this computer names the launcher by its full path unless a new terminal already runs this app's bridge as `uplink-bridge`.

The AppImage carries the bridge too, but its path changes on every launch, so it can't go on PATH. Use the .deb, or install the bridge as below.

**On another machine (headless team boxes, CI machines, a teammate's computer without the app).** Link a machine → Another machine shows these steps for macOS, Linux and Windows, with the commands filled in. They install the release cloud machines run, which `machines.bridgeRelease` gives any team member: the tarball's URL and sha256 from `UPLINK_BRIDGE_TARBALL_URL` (see Releasing for cloud machines). The URL goes into commands people paste into a shell, so the query answers only the shape the release script uploads (https, the public Blob store's host, `/bridge/uplink-room-bridge-<version>-<sha>.tgz`), and the app checks it again before it builds a command; each command quotes it for its own shell (PowerShell also ends a quoted string at the curly quotes ‘ ’ ‚ ‛).

1. Install Node 24 or newer. On Linux also install `python3`, `make` and `g++`, since node-pty ships prebuilt binaries for macOS and Windows only and npm compiles it there (`sudo apt-get install -y python3 make g++` on Debian and Ubuntu).
2. Download the tarball, check it, install it into `~/.uplink-room/npm`, a folder of your own, as on a cloud machine:

   ```sh
   curl -fsSLo uplink-bridge.tgz '<url>' && echo '<sha256>  uplink-bridge.tgz' | sha256sum -c - && npm install -g --prefix "$HOME/.uplink-room/npm" --allow-scripts=node-pty ./uplink-bridge.tgz && rm uplink-bridge.tgz
   ```

   Node from a system package (nodejs.org's macOS installer, apt, NodeSource) keeps npm's global folder root's, where a plain `npm install -g` fails with EACCES; the prefix needs no sudo, and `sudo npm` isn't the answer. macOS checks with `shasum -a 256 -c`. npm doesn't check a `#sha256=` fragment on a tarball URL, so `npm install -g '<url>#sha256=…'` would install whatever the URL serves. The check is in the command, against the hash the room recorded, as on a cloud machine. `--allow-scripts=node-pty` lets npm run node-pty's install script, which a global install skips unless allowed in npm 12.

   On Windows, in PowerShell, the same steps use `Invoke-WebRequest`, `Get-FileHash` and `npm.cmd install -g`, since Windows PowerShell's default execution policy refuses npm's `npm.ps1`. npm's global folder there, `%APPDATA%\npm`, is already the person's, and Node's installer puts it on PATH.
3. macOS and Linux: put that folder's `bin` on PATH for new terminals, in zsh's or bash's startup file, then open a new terminal:

   ```sh
   printf '\n%s\n' 'export PATH="$HOME/.uplink-room/npm/bin:$PATH"' >> ~/.zprofile   # macOS (zsh)
   printf '\n%s\n' 'export PATH="$HOME/.uplink-room/npm/bin:$PATH"' >> ~/.bashrc     # Linux (bash)
   ```

   The line goes after a newline of its own, so a startup file whose last line has none doesn't swallow it.
4. Pair it with `uplink-bridge pair CODE --url https://<deployment>.convex.cloud` (`uplink-bridge.cmd` on Windows, for the same reason as `npm.cmd`), then start it with `uplink-bridge run` and keep it running. On Linux, `uplink-bridge service install` keeps it running instead (below).

CODE is a machine code (`ABCD-EFGH`, valid for 10 minutes) from Link a machine → Another machine, or from `uplink machines createPairingCode name=<machine>`. A Pair code (`RIVER-4821-MAPLE-0937`) joins a Pair with `uplink pair`, not a machine; `bridge:pair` says so when it gets one.

Or install the desktop app there and use Link this computer.

### A Linux server with no display

The bridge needs no display: it shares terminals, and the parts that need a desktop (Cua Spaces, T3 Code, Rex) turn on only when that tool is installed. What a server lacks is someone keeping `uplink-bridge run` open, since it ends with the SSH session. `uplink-bridge service install` runs it as a systemd user service instead:

```sh
uplink-bridge pair CODE --url https://<deployment>.convex.cloud
uplink-bridge service install    # starts now, at boot, and again whenever it exits
uplink-bridge service status     # systemctl --user status; logs: journalctl --user -u uplink-bridge -f
uplink-bridge service uninstall  # stops and removes the service; the machine stays paired
```

It writes `~/.config/systemd/user/uplink-bridge.service` (under `XDG_CONFIG_HOME` if set) with the Node and bridge script that ran the command, the shell's `PATH` (so terminals find `claude`, `codex` and the rest; install again after changing it), and `UPLINK_BRIDGE_HOME` if set. It runs as you, not root, so terminals have your home and sign-ins. systemd stops a user's services at logout unless the user lingers, so `install` runs `loginctl enable-linger` and prints `sudo loginctl enable-linger <user>` when that's refused; `--no-linger` skips it. Run it in your own SSH login, not under `sudo su`, where `systemctl --user` has no session to talk to. It refuses while a bridge started by hand runs, and `pair` refuses while the service runs (`systemctl --user stop uplink-bridge` first). On macOS and Windows the desktop app keeps the bridge running, so the command is Linux only.

Checked on 2026-11-12 on Ubuntu (systemd user manager, this repo's Linux box) with a scratch `UPLINK_BRIDGE_HOME` and a pairing to an unreachable URL: install wrote and started the unit, the bridge ran under systemd and kept retrying the room, installing again restarted it, `pair` refused while it ran, and uninstall stopped it and removed the file.

npm installs node-pty from the registry, without the repo's patch (`patches/node-pty@1.1.0.patch`); on Windows the bridge applies the same fix to it at runtime (see Tests). From a checkout you can also build the tarball yourself (`pnpm install`, `pnpm --filter @uplink-room/bridge build`, then `pnpm pack` in `packages/bridge`) or skip it and run `node packages/bridge/src/bin.ts run`.

A single executable (Node SEA) isn't offered: SEA can't embed native addons, so node-pty's `.node` files (and on Windows its conpty helpers) would still have to sit beside the executable, and the desktop app already provides a runtime.

**On a cloud machine (#10, ADR 0013).** The room installs and runs the bridge itself. A cloud machine's boot step (`packages/backend/convex/lib/cloudBoot.ts`) runs on every boot: on the first, it downloads the tarball at `UPLINK_BRIDGE_TARBALL_URL`, installs it into `~/.uplink-room/npm` only if its sha256 matches the room's, sets the machine's own limits wide open so the room's settings decide, and pairs with a one-time code for the machine the room made. Later boots only run `uplink-bridge run`, since the pairing stays on the kept disk. Its log is `~/.uplink-room/boot.log` on the machine. A new tarball URL reinstalls the bridge on the next boot.

## Error reports

Bundled builds (`dist/uplink-bridge.mjs` and the app's copy) report crashes, unhandled rejections, a lost room link and programming errors to Sentry (`uplink-room-bridge`). A command that fails with a plain `Error` the person can fix, such as a missing pairing, isn't reported, and running from source never reports. `UPLINK_NO_TELEMETRY=1` or `DO_NOT_TRACK=1` turns it off. What a report may hold is in `src/telemetry/scrub.ts` and `docs/error-reports.md`.

## Releasing for cloud machines

Cloud machines get a new bridge only when `UPLINK_BRIDGE_TARBALL_URL` changes, so every release publishes the tarball under a new URL (#52). To release:

1. Merge to main, and deploy the backend to prod first if the bridge needs a backend change.
2. Tag the commit with a version and push the tag: `git tag v0.1.1 && git push origin v0.1.1`.
3. The **Bridge release** workflow (`.github/workflows/bridge-release.yml`) runs `scripts/release.ts`. It builds and packs the bridge, uploads the tarball with `@vercel/blob` (public access, the store's read-write token; the Vercel CLI wants a Vercel login even with the token) to the public Vercel Blob store `uplink-bridge-releases` (project `uplink-room`, team Miami Web AI) at `bridge/uplink-room-bridge-<version>-<sha>.tgz`, downloads it again and checks its sha256, and sets `UPLINK_BRIDGE_TARBALL_URL` on Convex prod to `<url>#sha256=<hex>`, then reads it back. A cloud machine installs the tarball only when its bytes match that hash, so write access to the Blob store alone can't change what machines run. The script refuses to point prod at an older version than the one it has; `--rollback` does that on purpose.
4. Each cloud machine installs the new bridge on its next boot. A running one keeps its current bridge until it stops (after 15 minutes with no live work) and starts again.

The version comes from this package's `package.json` and the sha from the commit, so a tag on a commit already published (or a rerun) finds the same tarball, checks its sha256 and sets the same URL; the pack is byte-for-byte reproducible. The workflow can also be run from the Actions tab, on main only.

It needs two repository secrets: `BLOB_READ_WRITE_TOKEN`, the store's read-write token (`vercel env pull` in a folder linked to the `uplink-room` project), and `CONVEX_DEPLOY_KEY`, a deploy key for prod (`npx convex deployment token create <name> --deployment fleet-jaguar-632`). To run it by hand, set both in the environment and run `node packages/bridge/scripts/release.ts` from the repo root; `--skip-convex` uploads and checks the tarball without changing the deployment, and a different `CONVEX_DEPLOY_KEY` points another deployment at it.

| | macOS and Linux | Windows |
| --- | --- | --- |
| Terminal | node-pty on a Unix pty. A harness's command runs in `/bin/sh -c`, and a shell run's one-shot `command` in `$SHELL -l -i -c` (see Protocol integration). With no command the terminal starts `$SHELL` through `/bin/sh -c` as an interactive, non-login shell: it reads the person's interactive startup files (`.zshrc`, `.bashrc`), where version managers usually live, but not the login ones (`.zprofile`, `.bash_profile`), which a one-shot `command` also reads. | node-pty on ConPTY. So both adapters are left out on Windows for now, and their terminals report Unknown. Tools installed as `.cmd` shims (how npm installs CLIs such as `t3`) run through cmd.exe. |

Claude Code runs its hooks through Git Bash on Windows; the hooks call `uplink-bridge`, which npm's global install and the app's launcher folder both provide. A terminal started by the bridge gets the launcher folder at the front of its PATH (`UPLINK_BRIDGE_BIN_DIR`), so hooks find the bridge that started them.

`share` starts a terminal in the running bridge and prints its local reference. It does not attach the calling terminal's keyboard or screen. The terminal appears in the room. Stopping sharing ends room-started terminals; personally started terminals keep running, unshared, until they exit or the bridge closes. While sharing is stopped, the bridge answers each `start_terminal` with `terminal_start_failed` (`sharing_stopped`).

Sharing stopped from the room (`stop_sharing`) comes back when the room sends `resume_sharing` (`machines.resumeSharing`). Sharing stopped on the machine with `stop-sharing` stays stopped whatever the room sends; restart `run` to share again. A restarted bridge is sharing, and the room clears its stopped flag when the bridge registers.

Config is `bridge.json` in the bridge's folder (see Operating systems). Pairing saves the room's token and ids there, plus who the machine belongs to (`belongsTo`: a member id, or `null` for a team machine) and who linked it (`linkedBy`). A machine paired before these were saved has no `belongsTo`, so every room-started terminal on it uses a slot, including its own person's; pair it again to fix that. Every command that writes `bridge.json` (a running bridge's saves of its inbox cursor, the limits or an unlink, and `pair`, `t3-pair`, `limits` and `unlink`) takes one lock first, `bridge.json.lock` beside it, then re-reads the file, changes only its own fields and writes it back. The lock is a file created only if it doesn't exist (`open` with `wx`), holding the holder's pid; a lock whose process has exited, or that is older than 30 seconds, is stale and the next writer removes it. A writer that can't get the lock in 10 seconds fails and names the pid holding it. A running bridge's saves that touch the pairing are skipped once the file holds another token. `pair` refuses while a bridge answers on this folder's local socket (stop `run`, or quit the desktop app, first), because that bridge holds the old pairing's profiles and threads; the desktop app stops its bridge, and waits for it to exit, before it pairs. `t3-pair` works while `run` is going, and the new T3 Code session is used after `run` restarts. A running bridge also pairs with T3 Code by itself (the same steps as `t3-pair`, with the local `t3` CLI found on PATH or in `~/.t3/bin`) when it starts with no session, when T3 Code refuses its session, and 8 days before the session ends, so `t3-pair` is only needed when that fails, as when T3 Code isn't open.

Profiles, the inbox cursor and `threads.json` belong to one pairing; the T3 Code session (`t3`) and the limits belong to the machine and stay. Every pairing is a new machine in the room, perhaps in another team, so `pair` and `unlink` delete the profiles and `threads.json` and reset the cursor. The bridge also checks at start: `threads.json` names the machine and team it was saved for, and a file saved for another pairing, or by an earlier bridge that didn't record one, is deleted unread. The profiles folder holds `.pairing.json` the same way, and its profiles are deleted when it names another pairing; a folder without one, from an earlier bridge, is kept for the current pairing. `room-files.json` there lists the workspaces where the bridge saved files for runs, so a bridge that starts again removes the ones older than 7 days (ADR 0043). `UPLINK_BRIDGE_HOME` overrides that folder. On macOS and Linux the private socket is `bridge.sock` there; hooks inherit its location through `UPLINK_BRIDGE_SOCKET`. When that path would pass the Unix socket length limit (about 104 bytes on macOS), the bridge uses `uplink-bridge-<hash>.sock` in the temp folder instead. Defaults are Suggest, two slots, and seven days for a profile.

## Protocol integration

`Bridge` accepts a `RoomLink`, local limits, a profiles directory, and optional terminal host, clock, adapters, error handler and token removal callback. Its inbound callback returns a promise so `ConvexLink` can finish each command before acknowledging it. Convex inbox snapshots are ordered, processed serially, and deduplicated by sequence. The CLI saves the handled sequence before acknowledging it. Crash recovery cannot make arbitrary terminal input transactional with saving that sequence.

A terminal's `localRef` is its bridge reference. For a room-started terminal it equals the requested `terminalId`. For a personally started terminal it is a generated reference, and `terminal_started` omits `terminalId`. Its output and run-state messages use that reference, which the room resolves. The room then sends `terminal_linked` with the terminal's room id and `driver_changed` naming whoever linked the machine; after that the bridge accepts controls addressed to either id. The bridge counts a personally started terminal as started by `linkedBy` from pairing, so it starts with that person driving.

The bridge decides locally what it doesn't take from the room:

- **Slots.** A room-started terminal uses a slot unless its `startedBy` is the member the machine belongs to. The room's `usesSlot` is ignored. On a team machine every room-started terminal uses one. Terminals shared from the machine never do. An agent's terminal uses a slot even on its person's machine, because the bridge can't verify who an agent belongs to; the room counts it the same way.
- **Who may start (ADR 0025).** While the machine's own most open access is Watch or Suggest, a personal machine's bridge starts a room's terminal (In Rex too) or thread only for the member it belongs to, or for an agent whose `accountable` person is that member; anyone else's gets `terminal_start_failed` or `thread_start_failed` with `owner_only`. The room refuses the same starts first, by its own setting, which can be lower than the machine's. A team machine, and a pairing that never saved `belongsTo`, start them for anyone.
- **The driver below Drive.** At Watch or Suggest, after the local clamp, `driver_changed` is accepted only back to whoever started the terminal, to the member the machine belongs to (the room hands teammates' terminals to them when it's lowered below Drive, ADR 0025), or to no driver. Any other driver change is refused with `input_rejected` (`driver_change_rejected`) and the driver stays. At Drive and Open the room's driver change is applied. Whatever the level, only the current driver's input reaches the terminal.
- **A shell's command.** A `start_terminal` with harness `shell` and a `command` (from `runs.start`'s `command`) runs that command in the person's own shell as a login and interactive one, `$SHELL -l -i -c <command>`, on macOS and Linux, so it gets the PATH and version managers their startup files set up, as typing it into their terminal would. A bridge the desktop app starts has a GUI app's short PATH, where `/bin/sh -c` wouldn't find tools such as npm. It also runs with `NO_COLOR=1` and without `FORCE_COLOR`, as does any terminal whose `start_terminal` sets `noColor` (the room sets it for a shell an agent opens), because whoever started it, almost always an agent, reads its output as text, and a test runner's colored inline diff merges the two values once its escape codes are removed. A harness's own command (`claude`, `codex`) still starts with `/bin/sh -c` and the machine's colors, and Windows uses the machine's shell either way. A leading `~` in `cwd` is this machine's home.
- **Resizing.** `resize_terminal { terminalId, cols, rows, from }` resizes the pty (node-pty `resize`). A terminal has one size for everyone, so, as with `input`, only the current driver's request counts; any other `from` gets `input_rejected` (`not_driver`) and the size stays. The room clamps to 20–500 columns and 5–200 rows, and the bridge clamps again, so a size outside that range is never applied. A terminal starts at 120×30 until its driver sends one.
- **Approvals.** See prompt ids under Adapters.

A bridge sends `register_machine` once, when it starts. The room ends every terminal the previous bridge process could have had on that machine, marks their unfinished runs Failed and frees their slots, because a new bridge process has no terminals. Those are the live terminals and the starting ones whose `start_terminal` the previous process already handled: acknowledged, or at or below the saved inbox cursor that `register_machine` carries as `afterSeq`. A starting terminal whose `start_terminal` comes after that cursor is kept, because the new process reads that message and starts it. When the local limits change while it runs, the bridge sends `limits_changed` instead, which keeps live terminals. Closing the bridge (SIGINT, SIGTERM or a lost link) reports `terminal_ended` for each shared terminal before the link closes, waiting up to 2 seconds. If the room gets `terminal_started` for a terminal it has already ended, it answers with `stop_terminal`.

`terminal_ended` carries a `reason`:

| `reason` | Sent when | The room marks the run |
| --- | --- | --- |
| `exited` | The terminal's process exited. `exitCode` is set; a process killed by signal N reports 128 + N, as a shell does (node-pty itself gives 0 and the signal). | Done for exit code 0, Failed otherwise |
| `stopped` | The room's `stop_terminal`, a stop of sharing (from the room or the machine), or an expired profile ended it. | Stopped |
| `bridge_stopped` | The bridge closed. No `exitCode`. | Stopped |

A message without `reason`, from an older bridge, is treated as `exited`.

For a terminal the room asked for, the room ignores the access in `terminal_started` and keeps its own, since the report can be older than a change made in the room while the terminal started. The bridge reports its own clamp to the machine's limit separately with `terminal_access`, which lowers the room's level. A terminal shared from the machine itself takes the access it reports, capped at the machine's setting.

`start_thread`, `stop_thread` and answers to thread approvals go to the T3 Code adapter; see [T3 Code](#t3-code) below.

The Convex link calls `bridge:pair`, `bridge:send`, `bridge:inbox`, and `bridge:ack`. It also sends `bridge:heartbeat` every 30 seconds, so an idle bridge stays online; a missed heartbeat is ignored unless the room rejects the token. Against a local Convex deployment on 2026-11-02, at commit 3047388: pairing (which saves who the machine belongs to), registering, a room-started terminal using no slot for its owner, driver input and output, a resize read back with `stty size`, and a graceful bridge stop leaving the run Stopped. A terminal shared from the machine and the heartbeat were verified earlier the same day, before the review fixes. Output batches flush after 30 milliseconds or when they reach 16 KiB; a single incoming PTY chunk may exceed that threshold.

| herdr | `hc events --json --terminal TARGET`, initial snapshot and JSON-RPC change events | Installed CLI and a real temporary terminal reported Waiting and Done through the bridge | Automatic target discovery covers `hc attach TARGET`. Other starts need an explicitly configured adapter target. |
| tmux | `tmux -C attach -t TARGET`, `refresh-client -B` subscriptions | A private tmux socket reported Waiting and Done through the bridge | No built-in agent waiting state. The tool must set the explicit options below. Use an explicit `-t` target. |
| Rex | `rex events -s TARGET --json --autostart=false`, block program-status snapshot | Installed CLI and a temporary Rex terminal reported Waiting and Done through the bridge; Rex tabs checked live on 2026-11-04 (see [Rex tabs](#rex-tabs)) | A Rex tab the bridge shares or opens is followed on its own block, with no target to set. For a shared terminal that runs `rex`, it needs an explicit target and block, or inherited `REX_SESSION` and `REX_BLOCK`; a tab that `rex run` or `rex split` opens isn't followed, but one opened with `uplink-bridge rex-open` can be shared. The tool must emit program-status reports. Rex can't take an answer back, so a blocked report is a question answered by typing in the terminal. |
| T3 Code | Paired: T3's client protocol over its WebSocket (`orchestration.subscribeShell`, `getThreadProjection`, `launchThread`, `dispatchCommand`). Not paired: `t3 thread list --project PATH --json` | See [T3 Code](#t3-code) | Set `UPLINK_T3_PROJECT` to a registered project's path or id, or launch the bridge there. Not paired, it can't see requests (Waiting reports Unknown) and can't launch, stop or answer. |

The program-status mapping for herdr and Rex is `working` → Working, `blocked` → Waiting, `done` → Done, `error` → Failed. Missing reports and `idle` map to Unknown. A blocked report carries its own text. From herdr, `kind=permission` becomes an approval. From Rex every blocked report is a question, its text followed by "Answer it in the terminal.", with no Allow or Deny: Rex's [program-status protocol](https://www.superlogical.com/rex/docs/build/program-status) has no way to send an answer back ("The only bytes a terminal writes back are the feature detection reply"), and no Rex CLI command answers one, so none is guessed. A known process exit also reports Done or Failed.

For tmux, set these options on the attached target:

```sh
tmux set-option -t TARGET @uplink_state waiting
tmux set-option -t TARGET @uplink_prompt 'Approve build?'
tmux set-option -t TARGET @uplink_prompt_kind approval
# Later:
tmux set-option -t TARGET @uplink_state done
```

Other supported values of `@uplink_state` are `working`, `failed`, and `unknown`. The bridge subscribes to target-level options. It does not infer which pane needs approval.

For Claude Code, add command hooks to the chosen machine setup or profile settings, for example:

```json
{
  "hooks": {
    "PermissionRequest": [{ "hooks": [{ "type": "command", "command": "uplink-bridge hook PermissionRequest", "timeout": 600 }] }],
    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "uplink-bridge hook UserPromptSubmit" }] }],
    "Stop": [{ "hooks": [{ "type": "command", "command": "uplink-bridge hook Stop" }] }]
  }
}
```

`PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `StopFailure`, and idle-prompt `Notification` events are also understood. An unanswered approval is denied if the socket closes, sharing stops or the terminal ends. Only the current driver can answer it through the room, at any access level: access limits teammates, never the driver.

### Messages to runs

A message someone sends a live run in the room (ADR 0026) reaches a Claude Code session in a terminal the bridge started: during a turn after its next tool call, and at once when it is idle. The messages stay in the room until a hook of the session takes them, so the bridge holds none and loses none if it stops.

- The room sends `run_messages_waiting` (a terminal, no text) only to a bridge that named `run_messages` in `bridge_features`.
- At the session's next hook that delivers messages, the bridge claims them with `bridge:claimRunMessages`. The room labels each one for the run's driver at that moment, and hands over only what that driver may read: a message from a private channel or direct message whose run has passed to someone outside it fails with `driver_changed`, and one from a sender the driver has since stopped the run hearing fails with `not_heard`. It hands over the oldest that fit in one delivery and says whether more wait.
- The hook's CLI writes the messages for Claude Code, and only then tells the bridge (`ack` on the local socket), which answers `run_message_result` `delivered` with `how` (`mid_task` or `next_turn`). A hook that got them and doesn't say so within 30 seconds makes the claim `unsure`; one that never got them (its socket closed while the room answered) makes it `released`. The room hands an unsure message over once more, then fails it as `unsure`, and counts a claim with no answer at all after 2 minutes as unsure.
- `run_hearing` goes once a terminal's hooks reach the bridge. Both bridge messages go only to a room that names `run_messages` (see Protocol versions).

An older bridge gets nothing, and the message waits in the run's inbox in the room, which says to update the bridge.

**Hooks.** When the bridge starts a terminal whose command starts `claude` (a room run of Claude Code, or `uplink-bridge share -- claude …`), it writes `claude-hooks.json` in its own folder and adds `--settings <that file>` after the program word. The file holds only `hooks`, so it overrides none of the person's settings, and hooks from `--settings` merge with theirs instead of replacing them ([hooks](https://code.claude.com/docs/en/hooks): "Hook entries merge across settings levels"; [CLI reference](https://code.claude.com/docs/en/cli-reference): `--settings`). Nothing is written to `~/.claude`. Claude Code has no environment variable that adds a settings file, so the command line is the narrowest place. The room still shows the command it asked for.

| Event | Hook | What it does |
| --- | --- | --- |
| `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure` | `uplink-bridge hook EVENT` | Reports Working, and returns the run's waiting messages as `hookSpecificOutput.additionalContext` (`next_turn` for a prompt, `mid_task` after a tool call). A subagent's tool call runs these hooks too, with `agent_id` in its input: it reports Working and takes no messages, which wait for the main session's next hook |
| `Stop` | `uplink-bridge hook Stop` | Reports Done |
| `StopFailure` | `uplink-bridge hook StopFailure` | Reports Failed: the turn ended in an API error (rate limit, billing, a missing model) and the session waits for its next prompt. The run stays live, and its messages still reach it |
| `Stop`, `StopFailure`, `SessionStart` | `uplink-bridge inbox --wait`, with `asyncRewake: true` and `timeout: 604800` | Waits while the session is idle; when a message arrives, exits 2 with it on stderr, and Claude Code wakes the session with it. Claude Code ignores a `StopFailure` hook's output, but a waiter started from it still wakes the session (checked with 2.1.318) |

On macOS and Linux each hook runs in exec form (`command` and `args`) with the exact words that started this bridge, so it reaches this bridge even when another `uplink-bridge` is first on PATH. On Windows exec form can't start the app's `.cmd` launcher, so the hooks run `uplink-bridge` from PATH in Claude Code's hook shell, as above. There is no `PermissionRequest` hook: approvals stay in the terminal unless the person's own settings send them to the bridge. A hook that can't reach the bridge answers `{}` and exits 0, and the waiter exits 0, so a lost bridge never puts an error in front of the session; an approval is still denied.

**The waiter.** Claude Code enforces a hook's `timeout` on an `asyncRewake` hook, 600 seconds by default, and once a waiter ends nothing starts another until a turn ends (#138, test 6). Claude Code 2.1.318 doesn't cap the value: it passes `timeout * 1000` to a JavaScript timer, whose limit is 2^31 − 1 ms (about 24.8 days). So the waiter's timeout is 7 days, and the bridge doesn't type a wake line into the terminal, the fallback #139 kept for a capped timeout. A `SessionStart` waiter covers a session that hasn't finished a turn yet, such as `claude` started with no prompt. Only one waiter waits per terminal: a newer one (each turn's `Stop` starts one) ends the one before with exit 0. A `Stop` waiter marks the session idle; a `SessionStart` one doesn't, because Claude Code also fires `SessionStart` when it compacts during a turn (`source: "compact"`), and a message then waits for the next tool call. The waiter reads which hook started it from the input Claude Code writes on its stdin. A session idle for more than 7 days hears its messages at its next prompt.

**What the run reads.** Messages are written as facts, as the hooks page advises for `additionalContext`: each says its id, where it was posted, who sent it (a person, an agent, or another run and its driver), who is accountable for it, and whether that person is this run's driver, then its text quoted line by line, so text can't pose as a label. The text is split on every line break a reader might honour (CR, LF, CRLF, NEL, VT, FF, U+2028 and U+2029), and other control characters, in the text and in names and places, are shown as escapes such as `\u001b`. Whether to act on a message is the run's decision (ADR 0026). One delivery stays under 9,000 characters, below the 10,000 at which Claude Code saves context to a file and shows a preview; what doesn't fit goes with the next hook. The room and the bridge write and measure it with the same function (`formatRunMessages` in `@uplink-room/protocol/runMessages`). A terminal that ends, or stops being shared, ends its waiter.

**Answering.** Inside a terminal the bridge shares, `uplink-bridge reply <messageId> "text"` answers a message in its place and thread, and `uplink-bridge say --in "#place" "text"` posts in a channel named by `#name` or by its id. A place is required (ADR 0029 D5), so a run never posts in a team channel by surprise; the text can also come on stdin. The bridge knows the terminal by `UPLINK_TERMINAL_REF` and its secret (below), and calls `bridge:runSay` with its own token, so the agent holds no key. The room finds the terminal's live run and posts as its driver, with the run's name in `asRun` (D2), through the same checks as `messages.post`, so the run can't post where its driver can't (ADR 0016); the activity log records `run.said`. The command prints where the message went, or the room's reason for refusing it. The bridge calls `bridge:runSay` only once the room names `run_say`; a room from before is reported too old. Once it does, every delivered message ends with a line saying the run can answer this way. As with the hooks, anything running in the terminal can call these and post as its run.

**Sending files.** `--file PATH`, once for each file up to 10, sends files and images with the message, which may then have no text (ADR 0047). The command reads each file and names it to the bridge by its path, size and SHA-256 (`runFiles.ts`). The bridge reads it again, refuses it if its bytes changed, and uploads it to a URL from `bridge:runAttachUrl`, an upload of the run's driver, then names the uploads in `bridge:runSay`'s `attachments`. The room keeps them through `messages.post`'s checks: images (PNG, JPEG, GIF, WebP) up to 20 MB, PDFs and other files up to 50 MB, no SVG. A file that can't be read or uploaded fails the message before anything is posted. The bridge sends files only to a room that names `run_say_files`; a room from before is reported too old to take files. In Codex's sandbox the signed request names the files the same way, and the hook uploads them. A run that gets the message gets the files the way it gets any message's files (ADR 0043).

**Which terminal is calling.** When the bridge spawns a terminal, it puts a random 32-byte secret in its environment (`UPLINK_TERMINAL_SECRET`), beside `UPLINK_TERMINAL_REF`. Every local request that acts as a terminal (`hook`, including approvals, `inbox --wait`, its acknowledgement, `say` and `reply`) must give both; without the secret a hook answers `{}`, an approval is denied, the waiter ends, and `say` and `reply` are refused. So a process in another terminal, or anything else on the machine, can't act as a run by naming its terminal id, which the room shows. The bridge can't learn which process connected instead: Node exposes no peer pid or credentials for a Unix socket or a Windows named pipe (nodejs.org/api/net.html, Node 26), so every platform gets the same check. What's left: a process running as the same OS user can read another process's environment (`ps eww` on macOS, `/proc/PID/environ` on Linux, the process's memory on Windows) and so the secret. On macOS and Linux the socket itself is owner-only (0600), which keeps other users out; the Windows named pipe has the system's default permissions. A Rex tab gets neither variable.

Checked live on 2026-11-05 with Claude Code 2.1.318 in a terminal shared with `uplink-bridge share -- claude --setting-sources project --strict-mcp-config --model claude-haiku-5-5 --allowedTools Bash`, a bridge from source with its own `UPLINK_BRIDGE_HOME`, and a local Convex deployment, messages posted with `messages.post`: one to a session that had run no turn woke it through the `SessionStart` waiter about a second later; one posted during a 25-second foreground command arrived as `PostToolUse` context next to that command's result, and the model did what the driver's message asked; one to an idle session woke it through the `Stop` waiter; and a `Stop` waiter armed for 647 seconds, past the 600-second default, still woke the session a second after the post. `runs.inbox` showed each as delivered, `mid_task` or `next_turn`.

**T3 Code threads (ADR 0037).** A run in a T3 Code thread the bridge reports hears messages too, once the bridge has named `thread_run_messages` and the room has too.

- The room sends `run_messages_waiting` with the thread as its source. The bridge claims the messages with `bridge:claimRunMessages` and `threadRef`, one claim at a time per thread, and sends them into the thread with `message.dispatch` (command id `uplink-room:run-message:<claim>`, message id `uplink-room:run:<claim>`, so a claim sent again goes once).
- How a message goes in depends on what T3 Code says the thread's provider does with a steer, read from the thread's projection (its provider session's `capabilities.turns`) just before each delivery. It joins the turn in progress (`steer_active`, `mid_task`) only when the provider steers active turns and steering doesn't stop running tools (`supportsActiveSteering` without `activeSteeringInterruptsTools`), which T3 Code itself requires before it steers a notification into a turn. Otherwise it waits for the turn to end (`queue_after_active`, `next_turn`), and a thread between turns starts one with it (`start_immediately`, `next_turn`). No harness name is checked. With T3 Code v0.1.8-nightly.20261105.4234 that means Codex steers, while Claude Code (its steering stops the running tool) and Grok (it can only interrupt and restart) hear between turns (#138, test 7). The bridge sends `run_hearing` for each thread from the same flags, reading one thread's projection per provider instance.
- The room hears `delivered` once T3 Code took the messages, `released` when T3 Code refused them, and `unsure` when the request timed out or the socket closed while it was out. After a failure the bridge waits 30 seconds before it claims for that thread again, doubling up to 5 minutes.
- **Answering.** T3 Code gives a thread's agent T3 Code's own environment, not a bridge terminal's PATH, socket and secret, and nothing in T3 Code's API tells the bridge which thread ran a command. So each delivery ends with a new run key and the exact commands: this bridge's own words, `reply` or `say`, `--socket` with this bridge's socket, and `--key urt_…`. The key posts only as that thread's run (`bridge:runSay` with `threadRef`), works while the thread's turn runs and for an hour after it ends, never past 12 hours after it was made, and lives only in the bridge's memory, so a restart ends every key and the next delivery brings a new one. When T3 Code put `T3CODE_THREAD_ID` in the command's environment (Claude Code and Codex threads; Grok threads have none), it must name the key's thread. The bridge hides every run key (`urt_[hidden]`) in everything it sends the room, `say` and `reply` included, and in what T3 Code sends it before it reads or cuts any of it, so no trim leaves a key's secret without its prefix; the secret of a key it holds is hidden wherever it shows (`[hidden]`). A thread keeps its newest 8 keys, a closed thread's keys stop at once, and stopping a run cancels deliveries on their way into its thread. A message from a direct message or private channel reaches a thread run only under ADR 0039.
- What is left: a key is in the thread's own conversation and in T3 Code's database, so another program running as the same user could read and use it until it expires. It separates threads from each other against mistakes and casual misuse, not against a hostile program of the same user, which could act as anything that user runs.

A message to each during a 60-second foreground command: Codex got it inside the same run (`steer_active`, `mid_task`), the command ran its full 60 seconds, and Codex answered before its next step; Claude Code and Grok each got it as a queued run, finished both steps without interruption, then answered (`next_turn`). ### Codex in a terminal

A Codex run in a bridge terminal reports its state, sends its approvals to the room, and hears messages (ADR 0038). Since 0.157.0 interactive `codex` uses a background app server that every client of the person's Codex home shares, and its hooks run inside that server with the server's environment, not the terminal's. Hooks passed to `codex` with `-c` take it off that server instead ("command-line configuration overrides (-c, --enable, --disable, or --search) requires embedded mode", Codex 0.166.0's startup warning), and then nothing outside the terminal can reach the session. So each terminal gets an app server of its own:

- **Starting it.** When the bridge starts a terminal whose command starts `codex` (a room run of Codex, or `uplink-bridge share -- codex …`), it runs it as `uplink-bridge codex -- codex …`. That wrapper, inside the terminal, starts `codex app-server --listen unix://SOCK` with the bridge's hooks as `-c` values, waits for its socket, tells the bridge where it is (`codex-server` on the local socket), and runs the terminal UI on it with `codex --remote unix://SOCK …` and the person's own arguments. The person's `-c`, `--enable` and `--disable` go to the server too, and hooks they pass with `-c` keep running: Codex sets each `-c` value at its key, replacing an earlier one there, so the bridge's values carry the person's matcher groups for each event first, at their own places, then the bridge's, and keep the person's `hooks.state` entries beside its own. The socket is in a folder only this user can open (`$TMPDIR/uplink-codex-UID`). When the terminal UI exits, the wrapper stops the server and its MCP servers (its process group) and tells the bridge; if the wrapper itself is killed, the bridge ends a server still registered when the terminal's process exits. A hangup, kill or Ctrl+C that reaches the wrapper before the terminal UI starts (while it waits for the server's socket, checks its hooks or registers it) stops the server first, then ends the wrapper with that signal's exit code. In a terminal shared from the machine, run `uplink-bridge codex [ARGS]` instead of `codex [ARGS]` to get the same (`uplink-bridge codex -- PROGRAM ARGS` names another Codex program). Commands that open no session (`codex exec`, `codex login`), or that pick their own server (`--remote`, `--no-daemon`), run unchanged, as does `codex` on Windows, where it reports Unknown and hears nothing.
- **Nothing in the person's Codex home.** The server uses the same `CODEX_HOME`, sign-in, config and saved sessions as any `codex`. The hooks come from the `-c` layer, which Codex lists as `source: "sessionFlags"`. Codex runs a hook only once it's trusted, and records trust in `config.toml` as a hash of the hook's definition under `hooks.state."<key>".trusted_hash`; the bridge passes that trust in the same `-c` layer for its own hooks only (`codexHooks.ts`, the hash as Codex 0.166.0 computes it), so the person isn't asked to review them and nothing is written. Their own hooks keep their own review: the bridge doesn't use `--dangerously-bypass-hook-trust`. Before the terminal UI starts, the wrapper asks the server with `hooks/list` whether it trusts each of the bridge's hooks (`trustStatus`) and by which hash (`currentHash`). A Codex that hashes hooks differently gets started again with the hashes it reported; this matters because the `-c` layer wins over `config.toml` field by field, so a wrong hash there would also beat one the person approved in `/hooks`. When the hooks still aren't trusted, are turned off, aren't listed, or `hooks/list` fails, the wrapper stops the server, says in the terminal which Codex and why, and runs `codex` without the room.
- **State.** `UserPromptSubmit`, `PreToolUse` and `PostToolUse` report Working; `Stop`, and `Interrupt` when the person stops a turn, report Done; `PermissionRequest` reports Waiting with the approval. Codex fires no hook when a turn fails (0.166.0: only `SessionStart` and `UserPromptSubmit` fired for a turn that failed with "model not allowed"), so Failed comes from the server's `turn/completed` with `status: "failed"`, which the bridge hears by following the session's thread on its own connection (`thread/resume`).
- **Approvals.** `PermissionRequest` goes to the room as an approval with Codex's reason (`tool_input.description`) as its text and the command as its action, and the driver's answer comes back as Codex's `decision`, `allow` or `deny`, as for Claude Code. One waits at a time: another that Codex asks for meanwhile, from a command running beside the first, gets no decision, and Codex asks for it in the terminal. The hook waits up to 600 seconds, Codex's default; an approval that ends unanswered (that timeout, or the terminal ending) also goes back to Codex's own prompt, never to a decision, and the room shows it as a question to answer in the terminal. A hook that can't reach the bridge answers `{}`, so Codex asks in the terminal.
- **Which thread.** Every hook's input carries `session_id`, the session's thread; a subagent's hooks carry its parent's. Before the first hook (a session that has had no turn yet) the bridge uses the one root thread the server has loaded, which is this terminal's, since nothing else uses that server. A `/side` conversation's hooks carry its own thread, an ephemeral fork Codex discards when the person goes back and keeps no turn history of, so messages keep going to the session's thread then.
- **Messages.** When the room says messages wait, the bridge claims them at once and puts them in through the server: with `turn/steer` and the turn's id as `expectedTurnId` during a turn (`mid_task`), which adds to it without stopping a running command, or with `turn/start` when the session is idle (`next_turn`). It reads the thread's runtime status first (`thread/read`), because Codex lists no turns for a thread before its first message ("not materialized yet"). A steer refused because the turn just ended starts a turn instead, and a turn that just started takes a steer. The room hears `delivered` once Codex took the message; a claim Codex refused is `released` and tried again, after a pause that doubles from 1 to 30 seconds, as is a claim the room couldn't answer. A steer or start that went out with no answer (it timed out, or the connection closed) may have gone in, so the bridge doesn't try the other one: it looks in the thread's newest turns (`thread/turns/list`) for up to 3 seconds, since Codex 0.166.0 lists a started or steered message about half a second after it takes it, and reports `delivered` when the message is there as the user's, and otherwise `unsure`, which the room hands over once more at most, then fails. The text is the same as Claude Code's (`formatRunMessages`).
- **Answering from inside Codex's sandbox.** Codex runs the agent's commands in a sandbox that, in its default `workspace-write` mode, blocks network access and with it the bridge's socket (checked with 0.166.0: a sandboxed `nc -U` to a socket in /tmp failed). So `uplink-bridge say` and `reply`, when the socket refuses them with a permission error in a Codex terminal (`UPLINK_CODEX_RELAY`, which the wrapper sets for the server), print the request signed with the terminal's secret instead (`codexRelay.ts`). The terminal's `PostToolUse` hook, which Codex runs outside the sandbox with the terminal's environment, finds it in the command's output, posts it with `bridge:runSay`, and tells the agent where it went, or why not, as `additionalContext`. A request without the terminal's signature, such as text in a file the agent reads, posts nothing, and each request posts once.

The room needed no change and no new feature name: the bridge sends the same `run_state_changed`, `run_hearing` and `run_message_result`, and claims with the same `bridge:claimRunMessages`. On a bridge from before, a Codex terminal reports Unknown and its messages wait in the room, as today.

Checked live on 2026-11-05 with Codex 0.166.0 (`gpt-6-luna`, low effort, `approval_policy = "on-request"`, `sandbox_mode = "workspace-write"`) in a scratch `CODEX_HOME` with a copy of the sign-in, started as a room run of Codex on a bridge from source against a local Convex deployment: the terminal UI started on its own server with no review prompt; a message to the session before its first turn started a turn within about two seconds of the post (`next_turn`); one posted during a 25-second `sleep` went in with `turn/steer` while it ran and the command still finished; the agent answered both with `uplink-bridge reply`, which the sandbox kept from the socket and the `PostToolUse` hook posted, stored under the driver with `asRun` "Codex (Julio Local)"; a network command the agent asked to run outside the sandbox waited in the room as an approval with Codex's reason and the command, and Allow from the room ran it; the run went Unknown, Working, Waiting, Done; and `/quit` stopped the server and ended the terminal. A failing turn's `turn/completed` with `status: "failed"` was checked against a real server separately. ### Hermes Agent in a terminal

A Hermes Agent run in a bridge terminal reports its state and hears messages (ADR 0040). From v0.23.0, `hermes` runs no agent in the terminal: its classic interface attaches to the profile's gateway, which runs every session of the profile and lets any of its local clients attach to a session, see its events, steer it and submit to it (Hermes's `developer-guide/programmatic-integration.md`, `gateway-local-sessions.md`). The bridge becomes one more such client:

- **Which session.** Hermes's classic interface records the session each terminal runs in a breadcrumb, `$HERMES_HOME/terminal-sessions/tty-…`, named after the terminal's tty (`/dev/ttys004` → `tty-dev-ttys004`). The bridge owns that tty, so it reads that file every second and follows the session it names: first a provisional id the gateway doesn't know yet, then the session a few seconds later, and a new one after `/new` or `/resume`. Each delivery reads it again first, so a message never goes to the session `/new` left. The home is `HERMES_HOME` in the terminal's environment, else the profile the command names (`-p`, `--profile`), else the sticky `active_profile`, else `~/.hermes`. The bridge never starts a gateway: the terminal's `hermes` does.
- **Getting in.** As Hermes's own client does (`hermes_cli/gateway_client.py`): `identify` and a one-use `session-ticket` on the gateway's control socket (`gateway.sock` in the home, or where `gateway.sock.path` points), which only this OS user owns, then the gateway's loopback WebSocket (`/api/ws`) with the subprotocol `hermes-gateway-v1` beside the ticket, and JSON-RPC there. `session.resume` subscribes the connection to the session's events.
- **State.** `message.start`, `tool.start` and a settled approval or question report Working; `approval.request` and `clarify.request` report Waiting with a question to answer in the terminal (the bridge doesn't say it answers the gateway's questions, so they stay with the person); `message.complete` reports Done, or Failed for `outcome: "failed"`, or Unknown for a turn lost in a gateway crash.
- **Messages.** When the room says messages wait, the bridge claims them at once: during a turn with `session.steer` and the turn's `execution_generation` (`mid_task`), which Hermes hands the agent after the next tool call as an out-of-band user message, without stopping one; a steer the turn ends without using becomes the session's next turn. When idle, or when the steer is refused because the turn just ended, with `prompt.submit` (`next_turn`), whose `submission_id` is the claim's id. Every `prompt.submit` on the gateway queues: it starts a turn on an idle session and waits behind a running one, never stopping it, whatever the person's `busy_input_mode`. A refused submit is `released` and tried again after a pause; one whose answer was lost is sent again with the same `submission_id`, which the gateway answers with the same admission, and is `unsure` only when that fails too.
- **Answering.** Hermes runs the agent's commands in the gateway, with the terminal's PATH but not its `UPLINK_TERMINAL_*` variables. So for each such terminal the bridge writes a launcher, `uplink-bridge` in a private folder of its own (`hermes/` in the bridge's home), that runs this bridge's CLI with the terminal's id, secret and socket, and each delivery ends with the launcher's path in the reply hint. The bridge removes it when the terminal ends.

Checked live on 2026-11-05 with Hermes Agent v0.23.0 and `gpt-5.4-mini` in a scratch `HERMES_HOME`, started as a room run of Hermes Agent on a bridge from source against a local Convex deployment: the bridge followed the session and the room showed it hearing mid-task; a message to the idle session went in at the next turn and Hermes answered with the launcher's `reply`, posted as Hermes Agent (Julio Local); one posted during a 25-second `sleep` went in with `session.steer`, the command finished with exit code 0, and Hermes answered right after it; a message from a direct message with this team run failed as `visible_outside` and never reached the session; after `/new` the next message went into the new session. Before that, a probe client on a scratch gateway checked that an approval still reached the terminal with another client attached.

Every approval the bridge reports carries a fresh `prompt.promptId`, from any adapter. `answer_prompt` must name it: the bridge applies an answer only from the driver and only when its `promptId` matches the approval pending now. Otherwise it sends `input_rejected` with `not_driver`, `stale_prompt` (an answer to an earlier approval) or `no_pending_approval` (none is pending, as for adapters with no answer path). The room sends every answer as the run's driver, whoever answered in the room; it records the real answerer itself.

## Protocol versions

A room refuses a bridge message it doesn't know, and a refused send stops sharing. So since ADR 0021 `bridge.send` answers `{ features }`, the bridge messages the room takes beyond the first protocol (`ROOM_FEATURES` in `@uplink-room/protocol`), and the bridge sends `bridge_features`, `thread_access` and `t3_status` only once the room has named them; a room from before answers null and gets none. The other way, a bridge ignores a room message it doesn't know, so the bridge says what it handles (`bridge_features`, `BRIDGE_FEATURES`) right after `register_machine`, and the room asks for those only where the machine's bridge named them: it refuses to pass a thread's wheel through a bridge that hasn't named `thread_driver`, which would keep the first driver and refuse everyone else's answers, and it says a run's messages wait only to a bridge that named `run_messages`, saying so for those still waiting when one does. A bridge that registers clears what the last one named.

## T3 Code

**Threads are private by default.** Pairing, or choosing the repo room launches go to, shares none of T3 Code's threads, now or later. The room gets a thread only when it was launched from Uplink Room, or when someone on this machine picked it: in the app, under Settings, Machines, this computer's T3 Code threads; or with the CLI:

```sh
uplink-bridge t3-threads                 # this machine's threads, shared or private, with their ids
uplink-bridge t3-share <thread id>...    # share these too
uplink-bridge t3-unshare <thread id>...  # stop sharing these
```

The list is read from T3 Code on the machine and shown only there; the room never gets the titles of threads nobody shared. The choice is saved in `t3-threads.json` in the bridge's folder, for this pairing and this T3 Code environment: pairing again forgets it, and a choice made for another T3 Code environment shares nothing until someone here picks again. A change takes effect at once, without a restart. Stopping sharing a thread doesn't touch its work in T3 Code: the room stops hearing it (its run goes Unknown unless it finished, and takes no more messages), and can no longer open, message, answer or stop it. What the room already has of it stays in the room. A thread launched from Uplink Room is always shared; end it from the room or in T3 Code. `UPLINK_T3_PROJECT` picks the repo (T3 Code's project) room launches go to; it shares none of that repo's threads.

Pair the bridge with the machine's T3 Code server once:

```sh
uplink-bridge t3-pair                                   # mints a pairing token with the local t3 CLI
uplink-bridge t3-pair --url http://127.0.0.1:3773 --token TOKEN   # or use one from `t3 auth pairing create`
```

This is T3's documented pairing: a one-time token (`t3 auth pairing create --scope orchestration:read --scope orchestration:operate --ttl 5m`) exchanged at `POST /oauth/token` for a bearer session with only those two scopes. `--base-dir` passes T3's data folder to the `t3` call. The URL, the token and when the session ends (`expiresAt`, from the exchange's `expires_in`) go in `bridge.json` under `t3`, in the bridge's private folder; the token is never sent to the room. Restart `uplink-bridge run` to use a new pairing, except after T3 Code refused the old one (below), when a running bridge picks it up within 30 seconds.

**The pairing ends after 30 days.** T3 Code gives a bearer session 30 days by default (`SessionStore.ts`) and no refresh, so the bridge saves the end and tells the room (`t3_status`, ADR 0021): the room shows "T3 Code pairing ends in N days" in its last week, and "T3 Code needs pairing again" once T3 refuses the session, whether it expired (`reason: expired`) or was revoked (`refused`). A refused session isn't retried every 5 seconds: the bridge reads `bridge.json` again every 30 seconds and connects as soon as a new pairing is saved there, and tries the old one again every 5 minutes. Its threads read Unknown meanwhile. `t3_status` also says `connected`, with T3 Code's `environmentId`, or `unreachable` when T3 Code doesn't answer. A room from before ADR 0021 is sent none of this (see Protocol versions).

**To cut the bridge off, revoke it in T3 Code's Settings → Sharing & access.** That closes its open socket at once (checked live on 2026-11-04, `research/t3code-capabilities.md`). `t3 auth session list` and `t3 auth session revoke` on the host only refuse new connections: the CLI runs T3's auth service in its own process (`apps/server/src/cli/auth.ts`, `runWithEnvironmentAuth`), so it writes the revocation and announces it only to itself, and the running server's watch on an open socket (`SessionStore.ts`, `awaitInvalidation`) never hears it. A connected bridge keeps working until it next reconnects, for example when T3 Code restarts, and then gets "needs pairing again".

Once paired, the adapter gets a WebSocket ticket (`POST /api/auth/websocket-ticket/rpc`), opens `/ws?wsTicket=…&orchestrationProtocol=2` and subscribes to the shell, so T3 pushes every thread change; it reconnects after 5 seconds if the socket drops, and reports its unfinished threads Unknown meanwhile. A thread the room has as Done, Failed or Stopped isn't reported Unknown: that would bring settled work back to the Inbox, so it keeps its state until T3 Code next reports a change to it. The room also ignores an Unknown report for a Done or Failed run, as it does for a Stopped one the bridge reported. T3's typed client packages (`@t3tools/contracts`, `@t3tools/client-runtime`) are private and unpublished, so `src/adapters/t3client.ts` writes Effect RPC's JSON frames itself; every frame and payload there was checked against T3 Code at commit `47f2c8d29e981c7723467efe137ee19e91df924e` (v0.1.7-nightly.20261102.4080) and the effect 4.0.5 it pins. T3 refuses a socket whose `orchestrationProtocol` differs from its own, so a T3 update that changes the protocol stops the adapter until it's updated.

- **Waiting.** A thread with a pending request a person answers (an approval of a command, file read, file change, MCP elicitation or permission, a question, a secret request or a request to link another machine) reports Waiting, even while T3's run status says `running`, which T3's list does during a question (issue #13). T3 names a secret or link card's request by the card's turn item id, not a runtime request (`ProjectionStore.ts`, `secretRequestAsPendingInput`), so the bridge finds the card among the turn items and reports a `question` to answer in T3 Code, with no buttons: a secret never goes through the room. The bridge reads the request's text from the thread's projection: a question's text and choices become a `question` prompt; an approval's reason becomes the prompt text and its `prompt` (for a command, the command) the `action`. An approval T3 can't answer live (`responseCapability` other than `live`) is reported as a question to answer in T3 Code, without buttons. Waiting clears when T3 drops the request. Tool calls and sign-in refreshes aren't a person's to answer, so they don't make a thread Waiting.
- **Answers.** Each T3 request gets its own `promptId`, kept across reconnects. `answer_prompt` for a thread applies only from the thread's driver and only when its `promptId` names the request pending now, as for terminal approvals; otherwise `input_rejected` (`not_driver`, `stale_prompt`, `no_pending_approval`) names the thread in `terminalId`. Allow sends `runtime-request.respond` with `accept`, deny with `decline`; never `acceptForSession` or `acceptAlways`. An answer the approval doesn't offer is refused. When T3 refuses the answer or doesn't take it (it's restarting, or the request timed out), the bridge asks T3 whether the request is still pending: if so, or if T3 can't say, the approval stays answerable and the room gets `answer_failed`, so a retry with the same `promptId` reaches T3; only a request T3 no longer lists as pending gets `stale_prompt`. A question is answered with `answer_question` (ADR 0023), below.
- **Access and drivers (ADR 0021).** A launched thread is driven by whoever started it, a thread found in T3 by whoever linked the machine, until the room passes its wheel with `thread_driver_changed`. As for terminals, below Drive (after the local clamp) the wheel only goes back to whoever started the thread, or to the member the machine belongs to (ADR 0025); anyone else gets `input_rejected` (`driver_change_rejected`), naming the thread in `terminalId`. A thread's access comes with `start_thread` (Watch when absent) and `change_thread_access`, clamped to the machine's most open access; a clamp is reported with `thread_access`, and lowering the machine's limit lowers its threads too. Both apply while sharing is stopped, since the thread goes on in T3 Code. Drivers, starters and access are kept in `threads.json` in the bridge's folder, so a restart doesn't lose them; a thread saved by a bridge from before ADR 0021 has no starter there and takes it from `thread_driver_changed` (`starterId`). A limit lowered in `bridge.json` while the bridge was stopped lowers the machine's threads in the room when the bridge registers. So is which threads the room launched: a thread launched in a project other than the watched one is still reported after the bridge restarts or sharing resumes. The file is kept only for the pairing that saved it (see the config section above), so a machine paired with another team doesn't report the first team's threads or refuse the new team's drivers.
- **`start_thread`.** The bridge picks the registered T3 project containing `cwd`, or else the one whose repository is `repo`, or else the project the adapter watches (`UPLINK_T3_PROJECT`, a registered project's id or a path inside it, as for reporting); the first enabled, installed and ready T3 provider instance whose driver runs the Room harness (`claude-code` → `claudeAgent`, `codex` → `codex`, `grok-build` → `grok`, `opencode` → `opencode`, `cursor` → `cursor`, or an instance id named directly; `shell` and `hermes-agent` have no T3 driver, and the room refuses a thread run of them before it reaches the bridge); and the project's default model for that instance, else the instance's default model. It launches with approvals required (`runtimeMode: approval-required`), in the project folder, with the prompt as the first message. The thread id (`uplink-room-RUNID`) and command id come from the run, so a `start_thread` the room delivers again reuses T3's launch. A `start_thread` or `stop_thread` that arrives before the adapter has connected to T3 and received its first shell snapshot, as one queued while the bridge was offline does right after it starts, waits for both, for up to 15 seconds (the room's messages are handled in order, so later ones wait too), and only then fails with `t3_unavailable`. The bridge sends `thread_bound` before the launch, so the room moves the run onto that thread before any report names it. A failure sends `thread_start_failed` with one of `sharing_stopped`, `t3_not_paired`, `t3_unavailable`, `t3_auth`, `project_not_registered`, `harness_disabled`, `mode_unsupported`, `launch_failed`, and T3's message.
- **Thread view (ADR 0022).** `watch_thread` makes the adapter subscribe to the thread (`orchestration.subscribeThread` with `acceptBoundedSnapshot`) on its socket until `unwatch_thread`, which sends Effect RPC's `Interrupt` for that stream. It turns T3's turn items into the room's `ThreadItem` (`src/adapters/t3thread.ts`): messages, reasoning, tool calls (command, search, web, tool, subagent) with their input and the end of their output, file changes with their diff, plans, approvals and questions with how they ended (from the thread's runtime requests), secret and link cards, checkpoints with their turn (`appRunOrdinal`) and files, and notices. Text is cut to `THREAD_ITEM_LIMITS`. Items of a rolled-back run, and a cancelled queued message, are left out, and their removal is sent (500 ids to a message), as T3's own timeline does. The snapshot's newest 150 items go first as one `thread_items` with `reset` (at most 2 MB); changes then gather for 250 ms and go in batches of at most 50 items. A watched thread is subscribed again after a lost connection, and when sharing resumes. `thread_history` answers with the 50 items before an item the room keeps: first from what the bridge holds, then from T3's history route (`GET /api/orchestration/threads/<id>/history`), whose cursor names that item (`threadHistoryPaging.ts`), and if T3 refuses that, from one read of the whole thread. `thread_diff_request` reads one turn's diff with `orchestration.getTurnDiff` (turn N is `fromTurnCount` N−1 to N), cut to 600 KB. Both run outside the command queue, so a slow read never holds up a terminal's input; one that ends after sharing stopped answers `sharing_stopped` with nothing it read, and no `thread_items` leave while sharing is stopped. Attachments go by name, kind and size only: T3's links to the files are credentials. Verified live with `node scripts/t3-live-check.ts <out> view` (an approval allowed, a plan, three tools, a file written: the room's items arrived in T3's order, turn 1's diff came back, and the history route took the cursor); `test/recordings/t3-thread-stream.json` is that run's stream, replayed in the tests.
- **Messages and questions (ADR 0023).** `send_thread_message` from the thread's driver dispatches `message.dispatch` with `createdBy: "user"` and `creationSource: "web"` (the command's schema requires both; T3 records every socket message as the user's anyway), a `commandId` and `messageId` from the room's message id so a redelivered message is sent once, and `dispatchMode` `start_immediately` for an idle thread or `queue_after_active` for one at work. No `deliveryIntent`, so nothing is steered: steering a running turn wasn't verified (research experiment 2). The room hears `thread_message_result` (`sent`, `queued`, or `failed` with `not_driver`, `sharing_stopped`, `t3_unavailable` or T3's message). `interrupt_thread` from the driver sends `run.interrupt` for the active run. A question T3 can take an answer for now (`responseCapability` `live`, every question with an id) is reported with its `questions` and a `promptId`; `answer_question` from the driver, naming that prompt, sends `runtime-request.respond` with `answers` (each question's id to an option's label, several labels, or the person's own words), refused like an approval's answer (`not_driver`, `stale_prompt`, `no_pending_question`, `invalid_answer`, `answer_failed`). A room that doesn't name `thread_questions` gets the question as text, as before. Verified live with `node scripts/t3-live-check.ts <out> messages`: a teammate's message refused, a message to an idle thread starting a turn, one sent while busy queued and run after the turn, a turn stopped, and a question the scripted agent asked with ACP's form elicitation answered from the room, the agent getting `{"action":"accept","content":{"rounding":"Half up"}}`.
- **`stop_thread`.** Sends `thread.stop` when T3 advertises it (`threadStop`), else interrupts the active run (`run.interrupt`). A stop T3 refuses or can't receive (it's restarting, or the socket is down) is answered with `input_rejected` (`stop_failed`), naming the thread in `terminalId`, which the room records; the bridge and its terminals keep running, and the thread is left to T3 Code. An answer that fails the same way gets `answer_failed`.
- **States.** `queued`, `preparing`, `starting`, `running` and `waiting` without a person's request → Working; `completed` → Done; `failed` → Failed; `interrupted` and `cancelled` → Stopped (the room records that the bridge reported it, so a thread continued in T3 Code is Working again at its next report; a run stopped from the room stays stopped, and Unknown, from a lost connection, doesn't bring a Stopped run back); `rolled_back` and idle → Unknown. Subagents, side chats and archived threads aren't reported as new threads.
- **Deleted and archived threads.** T3 sends the same `thread.removed` (on the active list) for a deleted thread and for an archived one, so the bridge reads the thread with `getThreadProjection`, which T3 answers for both because it keeps the row: `deletedAt` set means deleted, `archivedAt` set means archived. A deleted thread the room has Working or Waiting is reported Stopped, an archived one Done, each with no prompt, so a Waiting run leaves Needs you and its Allow and Deny buttons go with it instead of staying until they fail with `no_pending_approval`. Deleting ends the work; archiving only puts a thread away, which the Room calls settling, so it's Done, not Stopped. Nothing is reported for a thread the bridge never reported, or one the room already has as Done, Failed or Stopped, so settled work stays settled and doesn't come back to the Inbox. If T3 can't be read, or the thread has neither date, the room gets Unknown. A thread restored in T3 Code is reported again from its next update. A thread deleted or archived while the bridge was disconnected isn't reported: if it was unfinished it was already reported Unknown when the connection dropped (a finished one kept its state), and after the bridge reconnects it never sees that thread again.

Verified live on 2026-11-02 against an isolated T3 server (`t3 serve --base-dir` on a temporary folder, its own port and a temporary `HOME`, so no logins and nothing in Julio's T3 Code): `t3-pair` minting and exchanging a token for exactly the two scopes; the socket ticket and protocol gate; `server.getConfig`; the shell snapshot and pushed updates with acks; `launchThread` accepting the adapter's payload with its own thread id; the bridge reporting that thread Working then Failed (the provider wasn't signed in); `thread.stop`; T3 refusing `runtime-request.respond` for an unknown request; and `start_thread` refused with `harness_disabled` when no provider was ready. Not verified live then: Waiting with a real question or approval, and an approval answered, because they need a signed-in provider to ask; they're covered against the fake T3 server in the tests.

Verified live on 2026-11-04 against T3 Code v0.1.8-nightly.20261104.4179 with `node scripts/t3-live-check.ts <out> access`, which starts the same kind of isolated server with a minimal environment, adds the scripted ACP agent in `test/tools/scriptedAcp.mjs` as its only provider (no model, login or network; `codex`, `claude` and `gh` are failing stubs on its PATH, so title generation can't reach the local Codex CLI), and runs the real bridge and adapter against it: `t3_status` connected with T3's `environmentId` and the session's end; a `start_thread` at Open on a machine that allows Drive clamped to Drive and reported with `thread_access`; Waiting with the agent's approval, the wheel passed with `thread_driver_changed`, the first driver's answer refused (`not_driver`) and the new driver's reaching T3 Code (Working, Waiting, Working, Done); a revoke in Settings (`POST /api/auth/clients/revoke`) reported as `needs_pairing` (`refused`) 1.1 seconds later, with no retries while nothing new was saved; a new pairing used 0.2 seconds after it was saved; and a CLI revoke (`t3 auth session revoke`) leaving the open socket working (a thread launched over it 15 seconds later reported Working) while a new socket got HTTP 401, until T3 Code restarted and the bridge reported `needs_pairing`.

CLI flags were checked against installed help. Event shapes were checked against live herdr output, the local tmux manual, and Rex's installed API schema and official docs. Claude hook JSON follows the [official hooks reference](https://code.claude.com/docs/en/hooks). Convex subscription handling follows the [ConvexClient reference](https://docs.convex.dev/api/classes/browser.ConvexClient). Rex event wrapping follows its [events reference](https://www.superlogical.com/rex/docs/reference/events).

## Profiles

Each profile gets a private directory, saved expiry, and separate harness folders. All variable mappings live in `src/profiles.ts`: `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GROK_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME`, and `T3CODE_HOME`. A profile terminal also gets `OPENCODE_DISABLE_EXTERNAL_SKILLS=true` and `OPENCODE_DISABLE_CLAUDE_CODE=true`, so OpenCode doesn't load the machine's `~/.claude` and `~/.agents` skills or Claude Code's prompt. Existing machine credentials are not copied into profiles, and a profile terminal doesn't inherit the machine's sign-ins: `MACHINE_AUTH_VARIABLES` in the same file lists the variables removed from its environment (Claude Code's API keys, tokens and provider selection, such as `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN`; OpenCode's own login, config and database overrides; and every provider key OpenCode reads, from models.dev). Names match in any case. Machine-setup terminals keep them. A shell's startup files can still set them again inside the terminal.

A terminal starts in a profile only when its `start_terminal` names a harness that keeps the profile's logins apart from the machine setup, per [research/profile-logins.md](../../research/profile-logins.md) (#18): `claude-code` and `opencode`. Any other harness, or none, gets `terminal_start_failed` with `profile_not_supported`. Codex, Grok Build, Cursor, Hermes Agent and plain shells use the machine setup only, as would Antigravity, which the room doesn't offer as a harness yet. The room refuses the same runs first (`HARNESSES` in `packages/backend/convex/lib/harnesses.ts`); this is the bridge's own check. It limits what the room can ask for, not what a shell in the terminal can do. Separation with two real accounts, token refresh and authenticated MCP servers is still unverified.

Creating a profile is safe to replay: a `create_profile` delivered again after a restart finds the profile, and the bridge resends `profile_created` with its saved expiry. `delete_profile` is handled even while sharing is stopped, and expiry runs on its own timer whatever the sharing state. Creating, deleting and expiring profiles run in their own queue, apart from room commands, and never wait for the room: an expired profile's folder is deleted on time and `profile_expired` is sent afterwards, so a stalled link can't keep logins on disk past their deadline. The expiry timer is set as soon as the saved profiles load, before `register_machine` is sent, and again when a profile is made, before `profile_created` is sent, so a room that never acknowledges either still sees no login outlive its deadline (`profile_expired` always follows `register_machine`). A profile terminal's start runs on the same queue from its expiry check until it is registered: a profile that expired, was deleted, or is being deleted gets `terminal_start_failed` with `profile_expired`. Expiry and deletion end every terminal started in the profile, including ones already stopped whose kill hasn't finished, and delete the folder only once all of them have exited. A terminal still running after 3 seconds is killed outright (on Windows without the tree kill, elsewhere with SIGKILL). If one is still running 5 seconds after that, the folder stays, no terminal starts in the profile, and the deletion runs again when the last of them exits; every 30 seconds until then, those still running are killed again.

## Spaces

A Space is a Cua desktop on this machine (spec #6, ADR 0009). The bridge shares one only when the room asks on behalf of whoever the machine belongs to, and enforces the terminals' rules on it: the machine's most open access, one driver, and below Drive the wheel only back to whoever shared it. Code: `src/spaces/`.

- **Finding Spaces.** With Cua's CLI on the machine (`UPLINK_CUA`, else `cua` on PATH, else `~/.local/bin/cua`, where Cua's installer puts it), the bridge runs `cua spaces ls --json --no-size` when it starts, every 30 seconds and before each share, and sends `spaces_found` when the list changes. A local Space's power state comes from `cua sb ls --local --json --no-size` in the same pass, because `spaces ls` leaves a stopped local container's power state empty (`cua` 0.10.0, seen in the live check on issue #6). Only `local:` and `direct:` Spaces are listed; `relay:` ones are other computers. A shared Space that Cua stops listing ends (`space_ended`, `gone`). Without `cua`, the bridge shares no Spaces and answers `share_space` with `space_share_failed` (`spaces_unavailable`).
- **Reaching one.** Its token comes from Cua's own credential store, `$CUA_HOME/spaces-credentials.json` (0600, this user's; `~/.cua` by default), and its address from the same store (a Space added by address) or `cua sb info <id> --json` (`endpoints.env`, a local Space). Every call to `cua-spacesd` is `cua spacesd call <url> <Service/Method> <proto3 JSON>` with the token in `CUA_ENV_TOKEN`, never in the arguments.
- **Space views.** For `open_space_view` the bridge mints a Cua viewer ticket (`SystemService/CreateViewerTicket`, 5 minutes to attach) named for the viewer: `SESSION_POLICY_ALLOW_ACTIVATION` with the clipboard only when the viewer is the driver the bridge knows, `SESSION_POLICY_VIEW_ONLY` otherwise, whatever the room asked. `cua-spacesd` then refuses a viewer's input itself. The view is served at `/v/<random key>/viewer/` on the Space gateway, and `space_view_ready` carries that path and the ticket. A minute before the ticket expires the bridge mints a fresh one and gives it to the same route (`space_view_renewed`), for as long as the view stays open, so a viewer whose video socket drops after five minutes can attach again; the route's path and open sockets aren't touched.
- **The Space gateway.** An HTTP server that pipes `/v/<key>/...` (the viewer page, its gRPC-Web calls and its `/media` WebSocket) to the Space's `cua-spacesd`; any other path is 404. It adds no credential. It listens on port 3219 (another if that's taken) on loopback and the machine's Tailscale addresses (100.64.0.0/10); `UPLINK_SPACE_GATEWAY_HOSTS` (comma-separated) and `UPLINK_SPACE_GATEWAY_PORT` change that. Closing a view forgets its key and destroys its sockets at once: when the wheel moves, every interactive view but the new driver's is cut, since Cua can't revoke one ticket and an attached video socket outlives it.
- **Space actions.** `space_action` runs only from the driver the bridge knows (else `not_driver`), with the Space's own token: a screenshot (`ComputerService/Screenshot`, JPEG, quality 70 at most 1280 px, smaller if it would pass 700,000 base64 characters), a click, move or scroll (`ComputerService/Pointer`, in the pixels of `screenshotId` when given), a key or chord (`ComputerService/Keyboard` press or hotkey; names such as `enter`, `ctrl`, `cmd`, or one character), or typed text.
- **Ending.** Stopping a Space run in the room is `unshare_space` too: it ends the share, never the Space in Cua. `unshare_space`, `stop_sharing` (from the room or the machine), unlinking and closing the bridge end every shared Space and cut every view. A Space problem never stops terminal sharing: errors from Cua or the gateway are logged, not passed to the bridge's error handler.

Verified live on 2026-11-02 with `cua` 0.10.0 and a local Linux Space (Ubuntu 24.04 in a gVisor container under Cua's built-in runtime, no Cua account): listing and connecting through the CLI and the credential store; view-only and driver tickets; Cua's own viewer page loaded in Electron through the gateway on `http://127.0.0.1` (a secure context, so WebCodecs decoded the desktop), the view-only toolbar without the keyboard and clipboard buttons the driver's has; closing the route dropping both open views to "Reconnecting…" and the path to 404; a 1280×800 JPEG screenshot (48,228 base64 characters), a click in screenshot pixels, typed text, a chord and a scroll. Also checked with the CLI directly: a view-only ticket can't call `ComputerService/Pointer`, and its `OpenMedia` asking for full input comes back `SESSION_POLICY_VIEW_ONLY`.

## Rex tabs

A Rex tab is a tab in [Rex](https://www.superlogical.com/rex) whose program runs through the bridge, so the room can show it as a terminal while the person keeps using it in Rex (ADR 0019). Code: `src/rex/`. Rex tabs are offered on macOS and Linux, with Rex's CLI found as `UPLINK_REX`, else `rex` on PATH, else `~/.local/bin/rex`, else the CLI inside `/Applications/Rex Beta.app` (where `~/.local/bin/rex` pointed on the Mac this was checked on). A bridge that has them lists `rex-tabs` in `register_machine.tools`. Every Rex call passes `--autostart=false`, so the bridge never starts a Rex server, and, when `REX_SERVER` is set, `-S` with it: given only the variable, Rex's CLI goes on to the computer's own server when the named one is gone (seen with Rex 0.0.1793741575 on 2026-11-04).

- **Why a tab needs the bridge.** Rex documents no live stream of a tab's output: `data.connect`'s `/api/data` framing isn't documented and `rex block stream` says "not implemented" (API revision 10), while `format` and `rex capture` return the whole screen and scrollback per call, with no event when output changes. So the program runs under `uplink-bridge rex-host`, on a pty of its own inside the tab. `rex-host` passes everything through to and from the tab, and connects to the bridge over the private local socket (`rex_host`, then JSON lines both ways); while the tab is shared it sends the bridge the output and takes the driver's input. A tab opened in Rex directly can't be shared, and the bridge reports only how many there are.
- **Opening one.** `uplink-bridge rex-open [--session S] [--cwd DIR] [--title T] -- COMMAND` opens a tab that runs `rex-host -- COMMAND` (no command: the person's shell), beside the tab it runs in (`REX_SESSION`), else in the "Uplink Room" session, made when missing. Running `uplink-bridge rex-host [-- COMMAND]` in any Rex tab does the same in that tab. Neither needs a running bridge: `rex-host` tries to connect every 5 seconds, and its program runs either way.
- **Finding them.** The bridge looks at Rex every 30 seconds and when a host connects or leaves: `rex ls --json` and `rex window ls -s SESSION --json` for each session, which give only labels and ids. After the room's `room_features` lists `rex` (a room from before refuses `rex_found`), it sends `rex_found` when what it would report changes: whether Rex answered, each connected tab with its session and tab labels, its command and folder, the terminal sharing it if one does, and the number of other terminal tabs. `uplink-bridge rex-tabs` lists the same tabs.
- **Sharing one.** The room's `share_rex_tab` (from `rex.share`, which only whoever the machine belongs to can call) or `uplink-bridge share-rex TAB [--access LEVEL]` (TAB is the tab's id, its last four or more characters, or its label) shares a tab as a terminal: `terminal_started` with `tool: "rex"`, the tab's id as `localRef`, and, once the room's `room_features` lists `rex`, `rex: { sessionRef, tabRef }`, so the room knows it's a Rex tab even when the share comes before the first `rex_found` that lists it (a `rex_found` also marks a shared tab the room didn't know was one). It uses no slot; access is clamped to the machine's limit; the driver is whoever shared it, under the usual driver and wheel rules. The room's view starts with the tab's last 256 KiB of output, cut at a line start, and the program gets one resize so a full-screen program draws its screen again. Ending the share (`stop_terminal`, `uplink-bridge unshare-rex TAB`, stopping sharing, unlinking, the bridge closing) only stops the output: the program keeps running in Rex, and the tab can be shared again. `unshare-rex` refuses a run the room started In Rex, since ending its share ends it: stop the run in the room instead (as `rex.stopSharing` refuses it too). Failures are `terminal_start_failed` with `rex_unavailable`, `rex_tab_not_found`, `rex_tab_shared` or `sharing_stopped`.
- **Runs In Rex.** A `start_terminal` with `inRex` opens `rex new "Uplink Room" --window TITLE` (or `rex window new -s <that session> TITLE --focus=false` once it exists), with `-c` the run's folder (`~` is this machine's home) and `--interactive`, so the program finds what the person's tabs find on PATH; its command is `rex-host --terminal ID --socket PATH --command COMMAND`, with `--user-shell` for a shell's one-shot command and `--no-color` for one that runs without colors. The run waits up to 20 seconds for the host to connect, then fails with `rex_tab_failed` and closes the tab; Rex not answering is `rex_unavailable`, and a profile is `profile_not_supported` (Rex starts the tab with its own environment). As in a plain terminal, a shell's one-shot command runs in the person's own shell as a login and interactive one (`$SHELL -l -i -c`), and it and a shell an agent opens (`noColor`) run with `NO_COLOR=1`. It is a room-started terminal: it uses a slot as any does, and `stop_terminal`, stopping sharing or the bridge closing (or losing the host's connection) ends its program and closes its tab.
- **Size.** A Rex tab's program has its tab's size. The driver's `resize_terminal` becomes `rex block call -s SESSION -b TAB resize`, which Rex applies at once only when no Rex app owns the tab; while a Rex app has it open, the app's size stays. The bridge sends the size Rex gives the tab as `terminal_size` (after `room_features`), and the app draws the terminal at that size.
- **Ending.** A tab closed in Rex, or Rex quitting, hangs up `rex-host`, which ends its program: `terminal_ended` with `reason: "stopped"`. A program that exits on its own reports its exit code, as any terminal does.
- **Status.** Each Rex tab the bridge shares is followed with `rex events` on its own session and block (see Adapters), so the run shows its program status. The `program_status` snapshot is taken once the stream is live: Rex's `events -s` prints its own `client_connected` first (seen with Rex 0.0.1793741575), and a Rex that doesn't gets the snapshot after 2 seconds. So a status reported before the stream started is in the snapshot, and one after it comes through the stream.
- **Terminal replies.** Rex's server answers a program's terminal queries itself, with no Rex app open, so for a Rex tab the bridge drops the room screen's automatic replies (`input` with `reply`, in `terminalReplies.ts`'s shapes): the program gets one answer per query. Typing always passes (ADR 0019).
- **Output on the way out.** A run the room started streams from its first byte, and the bridge holds that output until the share takes it, so a command that prints and exits at once still shows, before its exit. A host whose program exited has 2 seconds in all to deliver what's queued and the exit, then its socket is cut, so a bridge that stopped reading can't hold the tab open. Kept output is trimmed by UTF-8 bytes on a whole character, and every terminal's output goes out well formed (`toWellFormed`): Convex refuses a string with half a surrogate pair, and with it the whole batch.
- **Options.** `rex-open` and `rex-host` read their own options only before `--`; after it, `--cwd` or `--command` belong to the command.

Checked live on 2026-11-04 with Rex 0.0.1793741575 (API revision 10) on a throwaway Rex server (`rex server run --listen unix://… --state-dir … --restore=false` with an empty config, reached through `REX_SERVER`), with the bridge from this branch: a tab opened with `rex-open` found and reported with its labels, shared, Rex's own program status (OSC 7501 from the program) reported as a question, the driver's input echoed and a teammate's refused, the driver's resize applied by Rex (read back with `block call size`), unsharing leaving the program running, a run In Rex creating the "Uplink Room" session and reporting exit code 3, stopping a run closing its tab, `rex block close` and stopping the Rex server each ending a run as Stopped, and `rex_unavailable` once Rex was gone. The same flow ran through a local Convex deployment with throwaway users (`rex.found`, `rex.share`, `terminals.input` and `terminals.output`, `rex.stopSharing`, `runs.start` via rex, `runs.stop`).

## Verification

```sh
pnpm --filter @uplink-room/bridge test
pnpm --filter @uplink-room/bridge typecheck
```

CI runs them on ubuntu, macos and windows runners. The terminals in the tests run `test/tools/term.mjs`, a small Node program, instead of shell builtins, so the same tests drive a Unix pty and ConPTY. The herdr and tmux tests skip on Windows, where those adapters aren't loaded; Rex and T3 Code use `.cmd` shims there. Every `expect.poll` waits up to 20 seconds (`vitest.config.ts`), since a process can take seconds to start on a loaded runner. On Windows, node-pty prints `AttachConsole failed` when its helper, which lists a console's processes so `kill()` can end them, can't attach because the console is already gone. That isn't noise. node-pty 1.1.0 then waits 5 seconds and kills the shell's old pid, which Windows may have given to another process by then: in CI it killed room-client's vitest (#34, `lib/conpty_console_list_agent.js` and `lib/windowsPtyAgent.js` in node-pty 1.1.0, [microsoft/node-pty#952](https://github.com/microsoft/node-pty/issues/952)). PR #41 (merged) patches node-pty so the helper reports an empty list and the fallback kills nothing. A standalone install gets node-pty unpatched from npm, so on Windows `src/terminal.ts` also replaces node-pty's console listing when it loads: any helper failure, or no answer in 5 seconds, lists nothing (#44). Closing the console ends the processes attached to it, but not one the shell's program started detached, with no console, which could outlive a stopped terminal (#43). On Windows, stopping a terminal therefore runs `taskkill /PID <shell pid> /T /F` first, and then node-pty's `kill()`. The tree kill runs in the background, through one long-lived Windows PowerShell helper, started with the first terminal, that holds the process open and kills it only if it started while node-pty was spawning the shell (starting a PowerShell process per kill blocked the bridge for about a second each time, up to 2.9 s, under NETWORK SERVICE on sthopc01): node-pty reports a shell's exit a second or more after Windows may have given its pid to another process. node-pty's `kill()` follows once the tree kill is done, or after 5 seconds, and `close()` waits for all terminals' kills together within its usual 2 seconds. Each request to the helper gets its answer within 5 seconds or counts as failed: a helper that takes longer, or whose stdin breaks, is ended with its own process tree, and the next request starts a new one. Kills end shells one at a time, and a terminal starts or resizes only once node-pty has reported the last such exit: node-pty 1.1.0 changes its list of terminals from each terminal's exit thread without a lock ([microsoft/node-pty#921](https://github.com/microsoft/node-pty/issues/921), fixed in 1.2.0-beta.18), and a stopped terminal's shell ending while the next terminal started crashed the process with an access violation. A start waits for those kills before it takes the profile queue, so profile expiry and deletion never wait behind one, and it checks the profile again right before the spawn. A profile's cleanup that is out of time moves its terminal's kill to the front of the line; that kill still waits for the one in progress, which takes at most 9 seconds (5 for the tree kill, 2 for each exit report). node-pty also holds `kill()` back until the terminal's first output, and on Windows 11 build 22000 under a service account (the CI runner on sthopc01) ConPTY sends none for a program that prints nothing, so the bridge stops that wait before it kills (#61). Once a shell has exited, node-pty can't close its console ([microsoft/node-pty#965](https://github.com/microsoft/node-pty/issues/965), unfixed in 1.1.0 and 1.2.0-beta.18), so every terminal whose program exited on its own, and every stop whose tree kill ended the shell first, left its `conhost.exe` running until the bridge exited. So a second after node-pty reports a terminal's exit, `src/windowsConsoles.ts` ends that terminal's console host, through a second PowerShell helper of its own, whose requests wait while a kill runs or the first helper is busy, so it never delays or resets a stop. It runs at the bridge's own priority. At below-normal, on a machine busy at normal priority (as CI is, running several packages' tests at once), Windows ran it only now and then as a starved thread: a binding took up to 20 s, so a terminal whose shell exited sooner was never bound and its console host never ended. Right after the spawn, while the shell is alive, that helper binds the terminal to its own console host: the shell's console host as Windows reports it, if it is a child of the bridge that started during the spawn. It records that process's pid and start time, every later step requires exactly that process, and a terminal it couldn't bind is never cleaned up. If the helper fails or times out, it asks again 30 seconds later, then less and less often, until the shell's exit is reported. A window of time alone can't tell two terminals started within it apart. It ends that console host only once nothing is attached to its console. Ending a console host doesn't end the programs attached to it, the way closing the console does, so it must not leave one behind. The check looks at every process that could be attached (in the console's session, started since the terminal, and descended from its shell or of unknown parentage) and keeps the console host whenever one of them can't be read, or exited after the check began; the kill checks again right before it. After a stop, programs still attached are ended first: one the tree kill can't reach (its parent had already exited) otherwise keeps running. A terminal whose program exited on its own keeps what is still attached, and so does its console host until that has exited; a console host that stays is looked at again 30 seconds later, then less and less often. Each bound terminal is also recorded in `consoles/` in the bridge's home, one small file per bridge process, named for the Windows account it runs as (if the helper fails to say which, it is asked again the next time a terminal is bound, and the record then gets every bound terminal whose console host may still be there); a bridge that starts ends the console hosts an earlier bridge of the same account left when it died with terminals open (on build 22000, 4 of 5 crashed bridges left one; on 26100, none did), under the same rules, and touches nothing else. A console host it can't open is never taken for gone: its record stays. One that stays is looked at again later, like any other. `test/terminal.test.ts` and `test/windowsConsoles.test.ts` cover these fixes, including a pid another process took before node-pty reported the exit, a console host that ends after its terminal exits while a running terminal's stays, one that stays while a program it can't read is attached, a stopped terminal's attached program that the tree kill can't reach, and a crashed bridge's console host; bridge tests check that a stopped shell's detached child is gone within 3 seconds, that closing ends a terminal that never printed, that slow tree kills hold up neither other terminals' output nor `close()`, and that a profile's folder outlasts every terminal started in it, stopped ones included.

`test/config.test.ts` covers the config lock (four processes writing at once lose no change; a dead holder's lock is taken over, a live one waited on) and `pair` refusing while a bridge runs.
